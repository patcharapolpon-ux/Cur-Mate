# Pipeline Orchestrator

Skill นี้เป็น **orchestrator** ที่รวมงานของ 3 skill เดิม (`requirement-intake`, `feature-journey-sync` เฉพาะส่วนแตกฟีเจอร์/journey ใหม่จาก backlog, `test-design-builder`) ให้ทำงานต่อเนื่องกันในคำสั่งเดียว ครอบคลุม 6 ชั้นของ pipeline:

**Requirement (01-spec) → Backlog → Feature List (MoSCoW) → User Journey (Mermaid diagram + mapping กลับไปยัง requirement) → Acceptance Criteria (Given-When-Then) → Test Plan → Test Case**

เหตุผลที่ต้องเป็น skill (ไม่ใช่ sub agent): ใน Claude Code มีแต่ skill (main loop) เท่านั้นที่เรียก Agent tool ไล่ทีละ sub agent ได้ ส่วน sub agent เองไม่มีสิทธิ์เรียก sub agent ตัวอื่นต่อ — ดังนั้น skill นี้จึงทำหน้าที่ไล่เรียก **agent ที่มีอยู่แล้วทั้ง 6 ตัว** (`requirement-writer`, `feature-list-writer`, `user-journey-writer`, `acceptance-criteria-writer`, `test-plan-writer`, `test-case-writer`) ตามลำดับ ไม่ได้สร้าง agent เขียนไฟล์ตัวใหม่ขึ้นมาเพิ่ม

**ขอบเขตที่ไม่ครอบคลุม**:
- **Prototype** — ไม่อยู่ในสายนี้ ถ้าผู้ใช้ต้องการ prototype ด้วย ให้แนะนำรัน skill `prototype-builder` แยกต่างหากหลังจบ pipeline นี้ (prototype ต้องถามเรื่อง Folder Version ใหม่/แก้ไขของเดิมทุกครั้งที่มีเวอร์ชันอยู่แล้ว ซึ่งขัดกับเป้าหมาย "ทำต่อเนื่องไม่หยุดถาม" ของ skill นี้)
- **การตรวจสอบ/ซ่อมความสอดคล้องของเอกสารเดิมที่ไม่มีการเปลี่ยนแปลงใหม่** — ถ้าผู้ใช้แค่อยากเช็คว่าเอกสารที่มีอยู่แล้วสอดคล้องกันหรือไม่โดยไม่มี requirement ใหม่ ให้ใช้ skill `feature-journey-sync` แทน (skill นี้ใช้เมื่อมีการเปลี่ยนแปลง/requirement ใหม่ที่ต้องไหลผ่านทุกชั้นจนจบเป็นเอกสารชุดทดสอบ)
- **อย่าเรียก agent `backlog-consistency-auditor` จาก skill นี้** — สงวนไว้เฉพาะ skill `feature-journey-sync` เท่านั้น

ทุกจุดที่ไม่แน่ใจหรือข้อมูลไม่พอ ให้ถามผู้ใช้ก่อนเสมอ — **ห้ามเดาแทนผู้ใช้ในจุดที่กระทบผลลัพธ์เอกสารอย่างมีนัยสำคัญ** **ข้อแตกต่างสำคัญจาก skill อื่น**: ที่นี่ต้อง **รวบรวมคำถามชี้แจงของทุกชั้นที่เกี่ยวข้องเป็นชุดเดียว แล้วถามครั้งเดียวก่อนเริ่มลงมือ** (ไม่ใช่ถามแยกทีละชั้นระหว่างทาง) และเมื่อผู้ใช้ยืนยันแผนรวมแล้ว ให้ไล่เรียก agent ต่อเนื่องจนจบโดย**ไม่หยุดถามซ้ำอีก** ทุกคำถามเลือกทาง (ไม่ใช่คำถามยืนยัน) ต้องมีตัวเลือกอย่างน้อย 3 แนวทางเสมอ พร้อมเหตุผล ข้อดี ข้อเสีย และคำแนะนำอันดับแรก (ผู้ใช้ยังเลือก "Other" เพิ่มเองได้เสมออยู่แล้ว)

## ขั้นตอน

### 1. กำหนดจุดเริ่มต้น (entry point)

ถ้าคำขอของผู้ใช้ยังไม่ชัดเจน ให้ถามด้วย `AskUserQuestion` ว่าจะเริ่มจากชั้นไหน:

- **Requirement ดิบใหม่ทั้งหมด** (แนะนำถ้าผู้ใช้เล่า requirement ใหม่มาในคำขอ) — ทำครบทุกชั้นตั้งแต่ขั้นตอน 2
- **มี Requirement/Backlog อยู่แล้ว อยากรันต่อตั้งแต่ Feature List** — ผู้ใช้ต้องระบุ backlog item/spec ที่จะใช้เป็นฐาน ข้ามไปขั้นตอน 4
- **มี Feature List/User Journey อยู่แล้ว อยากรันต่อเฉพาะชุดทดสอบ (AC + Test Plan + Test Case)** — ผู้ใช้ต้องระบุฟีเจอร์/backlog item ที่จะทำ ข้ามไปขั้นตอน 6

### 2. รับ requirement ดิบ + ตัดสินใจสร้างใหม่/แก้ไขเดิม (เฉพาะเริ่มจาก requirement ใหม่)

ทำเหมือนขั้นตอน 1-2 ของ skill `requirement-intake` (`.claude/skills/requirement-intake/SKILL.md`): ใช้ requirement ที่ผู้ใช้ส่งมา, สำรวจ `docs/01-requirements/backlog.md` และ `docs/01-requirements/01-spec/*.md` เพื่อหาเอกสารซ้ำซ้อน/เกี่ยวข้อง แล้ววิเคราะห์ว่าเป็นกรณี "แก้ไขเอกสารเดิม", "สร้างเอกสารใหม่ + archive เอกสารเดิม", หรือ "สร้างเอกสารใหม่ปกติ"

### 3. สำรวจเอกสารต้นทางทั้งสายเพื่อวางแผนชั้นถัดๆ ไป

อ่านเพิ่มเติมให้ครบตามจุดเริ่มต้นที่เลือกในขั้นตอน 1 (ข้ามส่วนที่ไม่เกี่ยวข้องได้):

- `docs/01-requirements/02-plan/feature-list.md` (ถ้ามี) — เพื่อรู้ว่ามีฟีเจอร์อะไรอยู่แล้ว จะได้ไม่ซ้ำเลข/ชื่อ
- ไฟล์ user journey เดิมใน `docs/02-design/01-prototypes/*-user-journey-*.md` (ถ้ามี)
- เอกสารทดสอบเดิม (ถ้ามี): `docs/03-testing/01-test-plan/acceptance-criteria.md`, `test-plan.md`, `test-cases/*.md`

ใช้ข้อมูลนี้วิเคราะห์ตามตรรกะเดียวกับ:
- **ประเภท ข. (แตกฟีเจอร์/journey ใหม่)** ของ skill `feature-journey-sync` (`.claude/skills/feature-journey-sync/SKILL.md` ขั้นตอน 3) — จัดกลุ่ม FR เป็นฟีเจอร์, ร่าง MoSCoW, จัดกลุ่มฟีเจอร์เป็น journey ตาม persona/ลำดับเหตุการณ์
- ขั้นตอนที่ 4 ของ skill `test-design-builder` (`.claude/skills/test-design-builder/SKILL.md`) — ร่างสถานการณ์ Given-When-Then ต่อ Backlog Item, หัวข้อ Test Plan มาตรฐาน, test case แบบ step-by-step ต่อฟีเจอร์

### 4. ถามคำถามชี้แจงของทุกชั้นรวมเป็นชุดเดียว

รวบรวมทุกจุดที่กำกวม/ขาดข้อมูลจากทุกชั้นที่เกี่ยวข้อง (ไม่ใช่ถามทีละชั้นแยกกัน) เช่น:

- (ถ้าเริ่มจาก requirement ใหม่) ขอบเขต/ผู้ใช้เป้าหมาย/edge case ที่ยังกำกวมของ requirement — ตามข้อ 3 ของ `requirement-intake`
- ระดับ MoSCoW ของฟีเจอร์ที่ spec ยังไม่ยืนยัน priority ชัดเจน, การจัดกลุ่ม FR เป็นฟีเจอร์/journey ที่แบ่งได้มากกว่า 1 แบบ — ตามข้อ 4 ของ `feature-journey-sync`
- ระดับความละเอียดของ negative/edge case ที่ต้องการให้ AC/test case ครอบคลุม, ประเภท Non-functional Testing ที่ต้องการใน Test Plan, Test Environment — ตามข้อ 5 ของ `test-design-builder`

ใช้ `AskUserQuestion` ถามเป็นชุดๆ (เรียกได้หลายครั้งถ้าคำถามขึ้นกับคำตอบก่อนหน้า) จนกว่าจะมีข้อมูลพอร่างแผนรวมในขั้นตอนที่ 5 ได้อย่างสมบูรณ์ — **เป้าหมายคือถามให้ครบภายในช่วงนี้ช่วงเดียว ไม่กลับมาถามแทรกอีกหลังยืนยันแผนแล้ว**

### 5. ร่างแผนรวมทั้งสายแล้วเสนอให้ผู้ใช้ยืนยันครั้งเดียว (ห้ามข้าม)

สรุปแผนเป็นข้อความเดียวให้เห็นภาพรวมทั้ง 6 ชั้นก่อนเสมอ (เฉพาะชั้นที่อยู่ในสโคปตามจุดเริ่มต้นที่เลือก):

- **Requirement/Backlog**: สร้างใหม่หรือแก้ไขเดิม พร้อมสรุป FR หลัก
- **Feature List**: รายชื่อฟีเจอร์ที่จะเพิ่ม/แก้ไข พร้อมระดับ MoSCoW
- **User Journey**: รายชื่อ journey ที่จะสร้าง พร้อม flow คร่าวๆ และฟีเจอร์ที่ครอบคลุม
- **Acceptance Criteria**: รายชื่อ Backlog Item x ฟีเจอร์ที่จะเพิ่ม พร้อมจำนวนสถานการณ์โดยประมาณ
- **Test Plan**: หัวข้อ/ส่วนที่จะสร้างใหม่หรืออัปเดต
- **Test Case**: รายชื่อไฟล์ต่อฟีเจอร์ที่จะสร้าง/อัปเดต

จากนั้นใช้ `AskUserQuestion` ถามยืนยันเป็นขั้นสุดท้ายก่อนดำเนินการ เช่น ตัวเลือก "ยืนยัน รันทั้งสายตามแผนนี้ต่อเนื่องจนจบ (Recommended)" และ "ขอปรับแผนก่อน" — ถ้าผู้ใช้เลือกขอปรับ ให้กลับไปคุยรายละเอียดที่ต้องการเปลี่ยนแล้วเสนอแผนใหม่ซ้ำจนกว่าจะได้รับการยืนยัน

### 6. ไล่เรียก sub agent ตามลำดับจนจบ โดยไม่หยุดถามซ้ำ

**อย่าเขียนหรือแก้ไขไฟล์ใดๆ เองใน skill นี้** เมื่อผู้ใช้ยืนยันแผนแล้วเท่านั้น ให้เรียก Agent tool **เรียงลำดับตามนี้เสมอ** (ข้ามชั้นที่ไม่อยู่ในสโคปตามจุดเริ่มต้นที่เลือกในขั้นตอน 1 ได้ แต่ห้ามสลับลำดับของชั้นที่เหลือ เพราะชั้นถัดไปต้องอ้างอิงข้อมูลของชั้นก่อนหน้าที่อัปเดตแล้ว):

1. **`requirement-writer`** — เรียกครั้งเดียว (เฉพาะกรณีเริ่มจาก requirement ใหม่) ส่งข้อมูลตามที่ระบุใน `.claude/agents/requirement-writer.md`
2. **`feature-list-writer`** — เรียกครั้งเดียว ส่งฟีเจอร์/MoSCoW ที่วิเคราะห์และยืนยันแล้ว
3. **`user-journey-writer`** — เรียก**ทีละ journey เท่านั้น เรียงลำดับ ห้ามเรียกขนานกัน** (ทุกครั้งแก้ `feature-list.md` และ `01-prototypes/index.md` ไฟล์เดียวกัน)
4. **`acceptance-criteria-writer`** — เรียกครั้งเดียว ส่ง Backlog Item/ฟีเจอร์/สถานการณ์ทั้งหมดในสโคป
5. **`test-plan-writer`** — เรียกครั้งเดียว
6. **`test-case-writer`** — เรียก**ทีละฟีเจอร์เท่านั้น เรียงลำดับ ห้ามเรียกขนานกัน** (ทุกครั้งแก้ manifest `test-cases/index.md` ไฟล์เดียวกัน) ส่ง AC ID ที่เกี่ยวข้องจากผลลัพธ์ของ agent ข้อ 4

หลังเรียก agent แต่ละตัวเสร็จ ให้อ่านผลลัพธ์ที่ agent นั้นส่งกลับ (path ไฟล์ที่สร้าง/แก้ไข) แล้วนำไปใช้เป็น context ต่อให้ agent ถัดไปทันที **ไม่ต้องหยุดรอถามผู้ใช้ระหว่างทาง** ไล่จนครบทุกชั้นในสโคป

### 7. รายงานผลกลับผู้ใช้

สรุปให้ผู้ใช้ทราบแบบกระชับ **ครั้งเดียวหลังจบทั้งสาย** แยกตามชั้น พร้อมลิงก์ไฟล์ (markdown link relative path) ของทุกไฟล์ที่สร้าง/แก้ไขในแต่ละชั้นที่อยู่ในสโคป (spec/backlog, feature-list, user journey ทุกไฟล์, acceptance-criteria.md, test-plan.md, ไฟล์ test-cases ทุกไฟล์, ไฟล์ log ของวันนี้) และถ้าระหว่างสำรวจข้อมูลพบว่าเอกสารเดิมนอกสโคปมีจุดล้าสมัย/ไม่สอดคล้อง (เช่น prototype เดิมอ้างอิงฟีเจอร์ที่เปลี่ยนชื่อ) ให้แนะนำท้ายรายงานว่าควรรัน `feature-journey-sync` หรือ `prototype-builder` ต่อ

## ข้อควรจำ

- **ห้ามข้ามขั้นตอนถามคำถามรวม (ข้อ 4) และขั้นตอนยืนยันแผนรวม (ข้อ 5)** ไม่ว่าสโคปจะเล็กแค่ไหน — แต่ทั้งสองขั้นตอนนี้ต้องทำ**ครั้งเดียวรวมกันทั้งสาย** ไม่แยกถามทีละชั้น
- **ห้ามหยุดถามคำถามใหม่ระหว่างขั้นตอนที่ 6** (หลังยืนยันแผนแล้ว) — ถ้าระหว่างเรียก agent พบว่าข้อมูลที่ให้ไว้ไม่พอจริงๆ ให้ agent ตัดสินใจอย่างสมเหตุสมผลเองแล้วบันทึกสมมติฐานไว้ในเอกสาร (ตามที่ระบุไว้ใน agent แต่ละตัว) แทนการหยุดถามผู้ใช้กลางคัน
- **ห้ามเรียก `user-journey-writer` หรือ `test-case-writer` มากกว่า 1 ตัวพร้อมกันแบบขนาน** เรียงลำดับทีละรายการเสมอ เพราะแก้ไฟล์ manifest เดียวกันทุกครั้ง
- เนื้อหาเอกสารทั้งหมดต้องเป็นภาษาไทยตาม `CLAUDE.md` (ยกเว้นชื่อระดับ MoSCoW, Given/When/Then, mermaid syntax และ slug/technical term)
- ห้ามลบเอกสาร/แถว/หัวข้อเดิม ให้ทำเครื่องหมายล้าสมัยแทนเสมอ (รายละเอียดอยู่ใน agent แต่ละตัวที่ถูกเรียก)
- การอ้างอิงข้ามเอกสารใน `.md` ของ vault ใช้ Obsidian wikilink แบบ relative path เสมอ
- agent ทั้ง 6 ตัวเป็นผู้เขียนไฟล์จริงทั้งหมดเท่านั้น — skill นี้ทำหน้าที่กำหนดจุดเริ่มต้น/สำรวจข้อมูล/ถามคำถามรวม/ยืนยันแผนรวม/ไล่เรียง agent เท่านั้น ไม่เขียนไฟล์เอง
- ไม่มี sub agent ใหม่สำหรับ skill นี้โดยเฉพาะ — ใช้ agent ที่มีอยู่แล้วทั้งหมด (ดูเหตุผลในหัวข้อบนสุด)
