# Prototype Builder

Skill นี้แปลงข้อมูลที่มีอยู่ในสาย **Requirement (01-spec) → Backlog → Feature List → User Journey** ของโปรเจกต์ Curmate ให้กลายเป็น **Prototype** — ไฟล์ HTML mockup ที่มองเห็นภาพหน้าจอจริงได้ เก็บเป็น Folder Version ใต้ `docs/02-design/01-prototypes/` และอ้างอิง Design System กลางที่ `docs/02-design/01-prototypes/DESIGN.md` เสมอ

ผู้ใช้อาจสั่งให้ครอบคลุมทั้งหมด หรือเจาะจงเฉพาะบางฟีเจอร์/journey/spec ก็ได้ — ทั้งสองกรณีต้องผ่านขั้นตอนเสนอแผนและรอการยืนยันก่อนสร้างจริงเหมือนกัน **ห้ามข้ามขั้นตอนเสนอแผนไม่ว่ากรณีใด**

ทุกจุดที่ไม่แน่ใจหรือข้อมูลไม่พอ ให้ถามผู้ใช้ก่อนเสมอ — **ห้ามเดาแทนผู้ใช้ในจุดที่กระทบผลลัพธ์เอกสารอย่างมีนัยสำคัญ** ทุกคำถามเลือกทาง (ไม่ใช่คำถามยืนยัน) ต้องมีตัวเลือกอย่างน้อย 3 แนวทางเสมอ พร้อมเหตุผล ข้อดี ข้อเสีย และคำแนะนำอันดับแรก (ผู้ใช้ยังเลือก "Other" เพิ่มเองได้เสมออยู่แล้ว)

## ขั้นตอน

### 1. ตรวจสอบ Design System ก่อนเสมอ (design-system-first)

- Glob หา `docs/02-design/01-prototypes/DESIGN.md`
- **ถ้ามีอยู่แล้ว**: เปิดอ่านทั้งไฟล์ เพื่อใช้เป็นข้อมูลอ้างอิงเวลาร่างแผนหน้าจอ (ยังไม่ต้องส่งให้ agent ทั้งไฟล์ก็ได้ เพราะ agent จะเปิดอ่านเองอีกครั้ง)
- **ถ้ายังไม่มี**: ต้องถามผู้ใช้ก่อนสร้าง ด้วย `AskUserQuestion` อย่างน้อย 2 คำถาม:
  1. ทิศทางสไตล์/บุคลิกแบรนด์ — เสนออย่างน้อย 3 แนวทาง (เช่น Professional/Trustworthy, Friendly/Approachable, Minimal/Neutral) พร้อมข้อดี/ข้อเสีย และคำแนะนำอันดับแรกโดยพิจารณาจากลักษณะผู้ใช้งานที่ปรากฏใน backlog/spec ที่มีอยู่
  2. สีหลักและฟอนต์ที่ต้องการ (รับเป็น hex/คำอธิบายสี หรือ "ให้ระบบเลือกให้เหมาะกับทิศทางที่เลือกในข้อ 1" เป็นหนึ่งในตัวเลือก) — ถ้าผู้ใช้แนบภาพตัวอย่าง/โลโก้มาในข้อความ ให้ใช้ Read ดูภาพนั้นประกอบการตัดสินใจสีด้วย
- เก็บคำตอบทั้งหมดไว้ส่งต่อให้ agent ในขั้นตอนที่ 6 (agent เป็นผู้สร้างไฟล์ `DESIGN.md` จริง ไม่ใช่ skill นี้)

### 2. กำหนดสโคป (ระบุเจาะจงได้)

- ถ้าผู้ใช้ระบุเจาะจงมาแล้วในคำขอ (ชื่อฟีเจอร์/journey/spec เฉพาะ) ใช้ตามนั้นได้เลย
- ถ้าไม่ได้ระบุ ให้อ่าน `docs/01-requirements/backlog.md` และ `docs/01-requirements/02-plan/feature-list.md` (ถ้ามี) มาสรุปเป็นตัวเลือกแล้วถามผู้ใช้ด้วย `AskUserQuestion` ว่าต้องการสโคปแบบใด เช่น "ทั้งหมดที่มีอยู่ (แนะนำถ้ายังไม่เคยทำ prototype มาก่อน)", "เฉพาะฟีเจอร์ Must have", "เจาะจงเลือกเอง (ระบุชื่อฟีเจอร์)"
- อ่านเอกสารต้นทางในสโคปที่เลือกให้ครบ: ไฟล์ spec ที่เกี่ยวข้องใน `docs/01-requirements/01-spec/`, entry ที่เกี่ยวข้องใน `feature-list.md`, ไฟล์ user journey ที่เกี่ยวข้องใน `docs/02-design/01-prototypes/*-user-journey-*.md` (Mermaid diagram + mapping) — ใช้ข้อมูลนี้ร่างรายชื่อหน้าจอ (screens) ที่ควรมีใน prototype พร้อมเนื้อหา/ส่วนประกอบคร่าวๆ ของแต่ละหน้าจอ

### 3. ตรวจโฟลเดอร์เดิม + ถามเรื่องเวอร์ชันทุกครั้งที่มีของเดิมอยู่แล้ว

- Glob หาโฟลเดอร์ที่ตรงรูปแบบ `docs/02-design/01-prototypes/*-prototype-v*` (โฟลเดอร์ ไม่ใช่ไฟล์)
- **ไม่มีเลย** → เป็นเวอร์ชันแรก สร้างเวอร์ชัน 1 ไปได้เลยโดยไม่ต้องถามข้อนี้
- **มีอยู่แล้วอย่างน้อย 1 เวอร์ชัน** → ต้องถามผู้ใช้ **ทุกครั้งที่เรียกใช้งานซ้ำ** ด้วย `AskUserQuestion` ไม่ว่าจะเคยถามคำถามนี้มาก่อนในบทสนทนาก่อนหน้าหรือไม่ก็ตาม: จะ "สร้าง Folder Version ใหม่" หรือ "แก้ไข Folder เวอร์ชันล่าสุด" — พร้อมให้คำแนะนำประกอบเสมอ:
  - แนะนำ **สร้างเวอร์ชันใหม่** เมื่อ: มีการเปลี่ยนแปลงกว้าง/เพิ่มฟีเจอร์ใหม่จำนวนมาก, ต้องการเก็บเวอร์ชันก่อนหน้าไว้เทียบ/อ้างอิง, มีการเปลี่ยนทิศทาง design ทั้งชุด
  - แนะนำ **แก้ไขเวอร์ชันล่าสุด** เมื่อ: ปรับแก้เล็กน้อยในสโคปเดิม, แก้ไขข้อผิดพลาด/ข้อความ, เพิ่มหน้าจอที่ขาดในเวอร์ชันปัจจุบันโดยไม่เปลี่ยนทิศทาง design, เวอร์ชันล่าสุดยังไม่เคยถูกนำไปให้ผู้อื่นรีวิว
  - ประเมินให้คำแนะนำอันดับแรกจากลักษณะการเปลี่ยนแปลงที่ผู้ใช้อธิบายมา ณ ตอนนั้น

### 4. ร่างแผนแล้วเสนอให้ผู้ใช้ยืนยันก่อนเสมอ (ห้ามข้าม)

ก่อนมอบหมายให้ agent สร้างไฟล์จริง ต้องสรุปแผนเป็นข้อความให้ผู้ใช้เห็นภาพรวมก่อนเสมอ ประกอบด้วย:

- สโคปที่จะครอบคลุม (ฟีเจอร์/journey/spec ใดบ้าง)
- รายชื่อหน้าจอ (screens) ที่จะสร้าง/แก้ไข พร้อมอ้างอิงแหล่งที่มาของแต่ละหน้าจอ (feature/journey/spec)
- ตำแหน่งโฟลเดอร์ปลายทาง (เวอร์ชันใหม่เลขที่เท่าไหร่ หรือแก้ไขโฟลเดอร์เดิม path ไหน)
- จะต้องสร้าง `DESIGN.md` ใหม่หรือใช้ของเดิมที่มีอยู่

จากนั้นใช้ `AskUserQuestion` ถามยืนยันเป็นขั้นสุดท้ายก่อนดำเนินการ เช่น ตัวเลือก "ยืนยัน สร้างตามแผนนี้ (Recommended)" และ "ขอปรับแผนก่อน" — ถ้าผู้ใช้เลือกขอปรับ ให้กลับไปคุยรายละเอียดที่ต้องการเปลี่ยนแล้วเสนอแผนใหม่ซ้ำจนกว่าจะได้รับการยืนยัน

### 5. ถามคำถามชี้แจงจุดที่ไม่แน่ใจ (ระหว่างขั้นตอน 2-4)

สำหรับทุกจุดที่กำกวมหรือขาดข้อมูล เช่น การจัดกลุ่ม FR/feature เป็นหน้าจอ (กรณีแบ่งได้มากกว่า 1 แบบสมเหตุสมผล), เนื้อหา/ฟิลด์ที่ควรอยู่ในหน้าจอที่ spec ไม่ได้ระบุรายละเอียดไว้ชัด, ลำดับหน้าจอที่ไม่ชัดจาก journey ให้ใช้ `AskUserQuestion`

**กฎสำคัญ: ทุกคำถามที่เป็นการเลือกทาง (ไม่ใช่คำถามยืนยันแผน) ต้องมีตัวเลือกอย่างน้อย 3 แนวทางเสมอ** พร้อมคำอธิบายเหตุผล ข้อดี ข้อเสีย ของแต่ละแนวทาง และให้ตัวเลือกที่แนะนำมาเป็นอันดับแรกพร้อมระบุว่าแนะนำเพราะอะไร

ถามเป็นชุดๆ จนกว่าจะมีข้อมูลพอร่างแผนในขั้นตอนที่ 4 ได้อย่างสมบูรณ์

### 6. มอบหมายให้ agent `prototype-writer` สร้าง/แก้ไขไฟล์จริง

**อย่าเขียนหรือแก้ไขไฟล์ใดๆ เองใน skill นี้** เมื่อผู้ใช้ยืนยันแผนแล้วเท่านั้น ให้เรียก Agent tool โดยระบุ `subagent_type: "prototype-writer"` พร้อมส่ง context ให้ครบตามที่ agent ต้องการ (ดู "อินพุตที่คุณควรได้รับในคำสั่ง" ใน `.claude/agents/prototype-writer.md`):

- วันที่ปัจจุบันในรูปแบบ `YYYYMMDD`
- สถานะ Design System (มีอยู่แล้ว หรือคำตอบเรื่องสไตล์/สี/ฟอนต์/โลโก้จากขั้นตอนที่ 1 ถ้ายังไม่มี)
- การตัดสินใจเรื่อง Folder Version จากขั้นตอนที่ 3 (สร้างใหม่เลขที่เท่าไหร่ หรือ path ของโฟลเดอร์เดิม)
- สรุปสโคป และรายชื่อหน้าจอที่ยืนยันแล้วทั้งหมดพร้อมรายละเอียด/แหล่งอ้างอิงของแต่ละหน้าจอ (ระบุด้วยว่าหน้าจอใดใหม่ หน้าจอใดแก้ไขของเดิม)

### 7. รายงานผลกลับผู้ใช้

สรุปให้ผู้ใช้ทราบแบบกระชับ พร้อมลิงก์ไฟล์ (markdown link relative path) ไปยัง:
- `DESIGN.md` (ถ้าสร้าง/แก้ไขในรอบนี้)
- manifest `index.md` ของโฟลเดอร์เวอร์ชัน และไฟล์ `.html` ทุกไฟล์ที่สร้าง/แก้ไข
- `docs/02-design/01-prototypes/index.md`
- ไฟล์ log ของวันนี้

## ข้อควรจำ

- **ห้ามข้ามขั้นตอนเสนอแผนและรอยืนยัน (ข้อ 4)** ไม่ว่าสโคปจะเล็กแค่ไหน หรือผู้ใช้จะเคยยืนยันแผนคล้ายกันมาก่อนในบทสนทนาเดียวกันก็ตาม
- **ต้องถามเรื่อง Folder Version ใหม่/แก้ไขของเดิม (ข้อ 3) ทุกครั้ง** ที่มีโฟลเดอร์ prototype อยู่แล้วอย่างน้อย 1 เวอร์ชัน — ไม่ใช่ถามครั้งแรกครั้งเดียวแล้วจำคำตอบไปใช้ตลอด
- เนื้อหาเอกสารทั้งหมดต้องเป็นภาษาไทยตาม `CLAUDE.md` (รวมถึงข้อความ UI ใน mockup HTML)
- ห้ามลบเอกสาร/โฟลเดอร์เวอร์ชันเดิม ให้เก็บไว้เป็นประวัติเสมอ
- การอ้างอิงข้ามเอกสาร `.md` ของ vault ใช้ Obsidian wikilink แบบ relative path เสมอ
- ทุก prototype ต้องอ้างอิง design tokens จริงจาก `DESIGN.md` ห้ามให้ agent เดาสี/ฟอนต์เอง
- agent `prototype-writer` เป็นผู้เขียนไฟล์จริงทั้งหมดเท่านั้น (DESIGN.md, ไฟล์ .html, manifest, index, log) — skill นี้ทำหน้าที่สำรวจข้อมูล/ถามคำถาม/ยืนยันแผนเท่านั้น
