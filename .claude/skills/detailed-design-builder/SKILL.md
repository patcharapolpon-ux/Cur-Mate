# Detailed Design Builder

Skill นี้แปลงข้อมูลที่มีอยู่ในสาย **High-Level Architecture (component) + Database Schema (entity) + API Spec (operation)** ของโปรเจกต์ Curmate ให้กลายเป็น **Detailed Design** — เอกสาร conceptual ที่อธิบายลำดับการโต้ตอบ (sequence flow) ของแต่ละ operation ว่าข้อมูลไหลผ่าน actor/component/entity ใดบ้าง ตามลำดับอย่างไร มีกฎ/ตรรกะทางธุรกิจเพิ่มเติมอะไรนอกจาก pre/post-condition ระดับสูง และเมื่อเกิดข้อผิดพลาดแต่ละกรณีจะเกิดอะไรขึ้น โดย**ไม่ผูกมัดกับ technical stack** เก็บเป็นไฟล์เดียวต่อโปรเจกต์ที่ `docs/02-design/02-technical/detailed-design.md`

เอกสารนี้อยู่**ปลายสุดของสาย 02-technical** — ต่อจาก High-Level Architecture, Database Schema และ API Spec เสมอ operation หนึ่งตัวใน `api-spec.md` ควรมี sequence design ที่ตรงกัน 1 รายการในเอกสารนี้ (ใช้รหัส `OP-NN-NN` เดียวกัน)

ผู้ใช้อาจสั่งให้ครอบคลุมทุก operation ที่มีอยู่ หรือเจาะจงเฉพาะบางกลุ่ม/operation ก็ได้ — ทั้งสองกรณีต้องผ่านขั้นตอนเสนอแผนและรอการยืนยันก่อนสร้าง/แก้ไขจริงเหมือนกัน **ห้ามข้ามขั้นตอนเสนอแผนไม่ว่ากรณีใด**

ทุกจุดที่ไม่แน่ใจหรือข้อมูลไม่พอ ให้ถามผู้ใช้ก่อนเสมอ — **ห้ามเดาแทนผู้ใช้ในจุดที่กระทบผลลัพธ์เอกสารอย่างมีนัยสำคัญ** ทุกคำถามเลือกทาง (ไม่ใช่คำถามยืนยัน) ต้องมีตัวเลือกอย่างน้อย 3 แนวทางเสมอ พร้อมเหตุผล ข้อดี ข้อเสีย และคำแนะนำอันดับแรก (ผู้ใช้ยังเลือก "Other" เพิ่มเองได้เสมออยู่แล้ว) — ถ้าผู้ใช้ตอบว่าไม่แน่ใจ/ให้ตัดสินใจให้ ให้เลือกตัวเลือกที่แนะนำ (Recommended) แทนแล้วแจ้งผู้ใช้ในแผนว่าเลือกให้ด้วยเหตุผลอะไร

**ข้อควรรู้เรื่องขอบเขต**: skill นี้ทำเฉพาะเอกสารระดับ conceptual เท่านั้น (ไม่ระบุเทคโนโลยี/protocol/framework จริง) — ถ้าผู้ใช้ขอให้ลงรายละเอียดระดับนั้น ให้แจ้งว่าอยู่นอกสโคปของ skill นี้แทนการเดาลงไปในเอกสาร conceptual (การเลือกเทคโนโลยีจริงใช้ skill `tech-stack-builder`) — **อย่าเรียก agent `backlog-consistency-auditor` จากสกิลนี้** สงวนไว้เฉพาะ skill `feature-journey-sync` เท่านั้น (auditor ไม่ครอบคลุมเอกสารในโฟลเดอร์ `02-technical` อยู่แล้ว)

**เสริมความเหมาะสมด้วย Tech Stack (ถ้ามี)**: ถ้ามี `docs/02-design/02-technical/tech-stack.md` อยู่แล้ว ให้ใช้เป็นข้อมูลเสริม**ไม่บังคับ**เพื่อทำให้ sequence diagram ในเอกสารนี้ "เหมาะสมและลงรายละเอียดยิ่งขึ้น" ตามลักษณะระบบจริง — โดย**แปลงเป็นลักษณะเชิงแนวคิด/บทบาทก่อนใช้เสมอ ห้ามคัดลอกชื่อเทคโนโลยีจริงจาก tech-stack.md มาใส่ในเอกสารนี้เด็ดขาด** (กฎ "ห้ามระบุชื่อเทคโนโลยีจริง" ในข้อควรจำยังคงบังคับใช้อยู่เหมือนเดิมทุกประการ) ดูรายละเอียดวิธีดึงและใช้ลักษณะเหล่านี้ในขั้นตอนที่ 1 และ 3 ด้านล่าง ถ้ายังไม่มี `tech-stack.md` ให้ทำงานตามปกติโดยไม่ต้องรอ

## ขั้นตอน

### 1. ตรวจไฟล์เดิมและไฟล์ต้นทางก่อนเสมอ (existing-first + prerequisite check)

- Glob หา `docs/02-design/02-technical/detailed-design.md`, `docs/02-design/02-technical/api-spec.md`, `docs/02-design/02-technical/database-schema.md`, `docs/02-design/02-technical/high-level-architecture.md`, `docs/02-design/02-technical/tech-stack.md`
- **ถ้ามี `detailed-design.md` อยู่แล้ว**: เปิดอ่านทั้งไฟล์ก่อนเสมอ เพื่อรู้ว่า operation ใดมี sequence design อยู่แล้วบ้าง (จะได้ต่อยอด ไม่ใช่เขียนซ้ำ/ขัดแย้งของเดิม)
- **ถ้ายังไม่มี `api-spec.md` เลย**: เอกสารนี้ต้องอ้างอิง operation จาก API Spec เสมอ ไม่มี operation ก็ไม่มีอะไรให้ทำ sequence design ให้ — แจ้งผู้ใช้ตรงๆ ว่า skill นี้ต้องมี `api-spec.md` ก่อน แนะนำให้รัน skill `api-database-design-builder` เพื่อสร้าง API Spec ก่อน แล้วค่อยกลับมาเรียก skill นี้ต่อ **ไม่ต้องดำเนินการต่อ** (ไม่ใช่คำถามเลือกทาง เป็นเงื่อนไขที่ทำต่อไม่ได้จริง)
- **ถ้ายังไม่มี `high-level-architecture.md` และ/หรือ `database-schema.md`**: ยังพอทำงานต่อได้ แต่แจ้งผู้ใช้ว่า component/entity บางส่วนใน diagram จะต้องระบุเป็น "ยังไม่กำหนด" ไปก่อน และแนะนำให้รัน skill `architecture-builder`/`api-database-design-builder` ให้ครบก่อนถ้าต้องการผลลัพธ์ที่สมบูรณ์ — ให้ผู้ใช้ยืนยันผ่าน `AskUserQuestion` ว่าจะทำต่อแบบข้อมูลไม่ครบ หรือหยุดไปทำเอกสารต้นทางให้ครบก่อน
- **ถ้ามี `tech-stack.md`**: เปิดอ่านทั้งไฟล์แล้วดึง**ลักษณะเชิงสถาปัตยกรรมเชิงแนวคิด**ที่มีผลต่อ sequence diagram เช่น ระบบมีแนวโน้มประมวลผลแบบทันที (synchronous) หรือมีบางส่วนประมวลผลเบื้องหลัง/ผ่านตัวกลางส่งข้อความ (asynchronous, จาก Hosting & Deployment/Real-time layer), ใช้บริการยืนยันตัวตนภายนอกหรือจัดการเอง (จาก Authentication layer), มีการแยกที่เก็บไฟล์ออกจาก data store หลักหรือไม่ (จาก File Storage layer) — จดบันทึกลักษณะเหล่านี้ไว้ใช้ในขั้นตอนที่ 3 (แปลงเป็นภาษาแนวคิดแล้วเท่านั้น ไม่ใช่ชื่อ product) **ถ้ายังไม่มี `tech-stack.md` ให้ข้ามส่วนนี้ไปเลย ไม่ใช่เงื่อนไขบังคับ**

### 2. กำหนดสโคปของ operation

- ถ้าผู้ใช้ระบุเจาะจงมาแล้วในคำขอ (ชื่อ/รหัส operation หรือกลุ่มเฉพาะ) ใช้ตามนั้นได้เลย
- ถ้าไม่ได้ระบุ ให้อ่าน `api-spec.md` ทั้งไฟล์มาสรุปรายชื่อกลุ่ม/operation ทั้งหมด แล้วถามผู้ใช้ด้วย `AskUserQuestion` ว่าต้องการสโคปแบบใด เช่น "ทุก operation ที่มีอยู่ใน api-spec.md ตอนนี้ (แนะนำถ้ายังไม่เคยทำ detailed design มาก่อน)", "เฉพาะกลุ่ม/operation ที่ระบุ", "เจาะจงเลือกเอง"
- ถ้า `detailed-design.md` มีอยู่แล้ว ให้ตัดรายชื่อ operation ที่มี sequence design สมบูรณ์แล้วออกจากสโคปเริ่มต้น (เว้นแต่ผู้ใช้ขอให้ทบทวน/แก้ไขของเดิม)

### 3. วิเคราะห์ sequence flow ต่อ operation

สำหรับแต่ละ operation ในสโคป:

- อ่านหัวข้อของ operation นั้นใน `api-spec.md` ให้ครบ (คำอธิบาย, Actor, Entity ที่เกี่ยวข้อง, Input, Output, Pre-condition, Post-condition, กรณีข้อผิดพลาด)
- กำหนดว่า component ใดจาก `high-level-architecture.md` มีส่วนร่วมในการประมวลผล operation นี้ (โดยทั่วไปคือ component ที่รับ input จากผู้ใช้ + component ที่ตัดสินใจ/ประมวลผลตามกฎธุรกิจ + component ที่เก็บข้อมูล/เข้าถึง entity)
- ลำดับการโต้ตอบ: actor → component รับ input → (ถ้ามีการตรวจสอบ/ตัดสินใจ) component ประมวลผล → entity ที่ถูกอ่าน/บันทึก → ผลลัพธ์กลับไปยัง actor — ปรับตามความซับซ้อนจริงของ operation นั้น
- กฎ/ตรรกะทางธุรกิจเชิงแนวคิดที่ควรระบุเพิ่มจาก pre/post-condition ที่มีอยู่แล้ว (เช่น เงื่อนไขการตัดสินใจแตกทาง, การคำนวณ/ตรวจสอบที่ post-condition ของ api-spec พูดถึงแต่ยังไม่ได้อธิบายว่าเกิดขึ้นที่ไหน/อย่างไร)
- แปลงแต่ละ "กรณีข้อผิดพลาด/Exception" ที่ระบุใน `api-spec.md` ให้เป็น alternative/error flow ระบุว่าขั้นตอนไหนล้มเหลว ตรวจพบที่ component ใด ผลลัพธ์คืออะไร (ถ้า `api-spec.md` ระบุว่า operation นั้นยังไม่กำหนดกรณีข้อผิดพลาด ให้คงระบุ "ยังไม่กำหนด" เช่นเดียวกัน ไม่ต้องเดาเพิ่ม)
- **ถ้ามีลักษณะเชิงสถาปัตยกรรมจาก `tech-stack.md`** (ดึงมาในขั้นตอนที่ 1) ให้ใช้ประกอบการตัดสินใจต่อไปนี้ (ยังคงเป็นชื่อ participant เชิงบทบาททั้งหมด ห้ามระบุชื่อเทคโนโลยีจริง): operation ที่ใช้เวลานาน/มีลักษณะประมวลผลเบื้องหลัง → เพิ่ม participant เชิงบทบาท เช่น "ตัวกลางส่งข้อความ" หรือ "คิวงานเบื้องหลัง" ในไดอะแกรม แล้วแสดงว่า component หลักส่งต่องานให้ประมวลผลภายหลังอย่างไร; operation ที่ต้องยืนยันตัวตนและ tech-stack ระบุว่าใช้บริการภายนอก → เพิ่ม participant "บริการยืนยันตัวตนภายนอก" ในจุดที่ตรวจสอบสิทธิ์; operation ที่เกี่ยวข้องกับไฟล์และ tech-stack ระบุว่าแยกที่เก็บไฟล์ → เพิ่ม participant "ที่เก็บไฟล์" แยกจาก Data Store หลักในไดอะแกรม

จุดที่กำกวมหรือมีมากกว่า 1 ทางเลือกสมเหตุสมผลในขั้นตอนนี้ (เช่น operation หนึ่งมี component ที่เป็นไปได้มากกว่า 1 ตัวที่จะทำหน้าที่ตรวจสอบเงื่อนไข, ควรแตก sequence เป็นหลาย diagram ย่อยหรือรวมเป็น diagram เดียวพร้อมโน้ต alternative, ระดับความละเอียดของขั้นตอนที่ควรแสดงในไดอะแกรม) ให้ถามผู้ใช้ตามกฎ 3 ทางเลือกในข้อ 4

### 4. ถามคำถามชี้แจงจุดที่ไม่แน่ใจ (ระหว่างขั้นตอน 2-3)

ใช้ `AskUserQuestion` **ทุกคำถามที่เป็นการเลือกทาง (ไม่ใช่คำถามยืนยันแผน) ต้องมีตัวเลือกอย่างน้อย 3 แนวทางเสมอ** พร้อมคำอธิบายเหตุผล ข้อดี ข้อเสีย ของแต่ละแนวทาง และให้ตัวเลือกที่แนะนำมาเป็นอันดับแรกพร้อมระบุว่าแนะนำเพราะอะไร ถามเป็นชุดๆ จนกว่าจะมีข้อมูลพอร่างแผนในขั้นตอนที่ 5 ได้อย่างสมบูรณ์

หากผู้ใช้ตอบว่าไม่มั่นใจ/ให้ตัดสินใจแทน ให้เลือกตัวเลือกที่แนะนำ (Recommended) ของคำถามนั้นแทนการถามซ้ำ แล้วระบุไว้ในแผนช่วงข้อ 5 ว่าจุดใดเลือกให้แทนผู้ใช้ด้วยเหตุผลอะไร เพื่อให้ผู้ใช้ยังเห็นและปรับได้ตอนยืนยันแผน

### 5. ร่างแผนแล้วเสนอให้ผู้ใช้ยืนยันก่อนเสมอ (ห้ามข้าม)

ก่อนมอบหมายให้ agent สร้างไฟล์จริง ต้องสรุปแผนเป็นข้อความให้ผู้ใช้เห็นภาพรวมก่อนเสมอ ประกอบด้วย:

- สโคป operation ที่จะครอบคลุม (รหัส + ชื่อ ตาม `api-spec.md`)
- ต่อ operation แต่ละตัว: actor/component/entity ที่จะอยู่ใน sequence diagram พร้อมลำดับคร่าวๆ, กฎ/ตรรกะทางธุรกิจเพิ่มเติม (ถ้ามี), alternative/error flow ที่จะครอบคลุม
- จุดใดที่เลือกให้แทนผู้ใช้ (จากข้อ 4) พร้อมเหตุผล
- ถ้าใช้ลักษณะเชิงสถาปัตยกรรมจาก `tech-stack.md` ประกอบการตัดสินใจ ให้ระบุไว้ว่าใช้ลักษณะใด (เช่น "เพิ่ม participant ตัวกลางส่งข้อความ เพราะ tech-stack ระบุลักษณะประมวลผลเบื้องหลังไว้") เพื่อให้ผู้ใช้เห็นที่มาและปรับได้ตอนยืนยัน
- เป็นการสร้างไฟล์ใหม่ หรืออัปเดตไฟล์เดิม (ระบุว่าจะเพิ่ม/แก้ไขส่วนใด)

จากนั้นใช้ `AskUserQuestion` ถามยืนยันเป็นขั้นสุดท้ายก่อนดำเนินการ เช่น ตัวเลือก "ยืนยัน สร้าง/อัปเดตตามแผนนี้ (Recommended)" และ "ขอปรับแผนก่อน" — ถ้าผู้ใช้เลือกขอปรับ ให้กลับไปคุยรายละเอียดที่ต้องการเปลี่ยนแล้วเสนอแผนใหม่ซ้ำจนกว่าจะได้รับการยืนยัน

### 6. มอบหมายให้ agent `detailed-design-writer` สร้าง/แก้ไขไฟล์จริง

**อย่าเขียนหรือแก้ไขไฟล์ใดๆ เองใน skill นี้** เมื่อผู้ใช้ยืนยันแผนแล้วเท่านั้น ให้เรียก Agent tool โดยระบุ `subagent_type: "detailed-design-writer"` พร้อมส่ง context ให้ครบตามที่ agent ต้องการ (ดู "อินพุตที่คุณควรได้รับในคำสั่ง" ใน `.claude/agents/detailed-design-writer.md`):

- วันที่ปัจจุบันในรูปแบบ `YYYY-MM-DD`
- รายชื่อกลุ่ม operation ที่ยืนยันแล้ว (ตรงกับกลุ่มใน `api-spec.md`)
- ต่อ operation แต่ละตัวที่ยืนยันแล้ว: รหัส+ชื่อ operation, actor/component/entity และลำดับการโต้ตอบที่ยืนยันแล้ว, กฎ/ตรรกะทางธุรกิจเพิ่มเติมที่ยืนยันแล้ว (ถ้ามี), alternative/error flow ต่อกรณีข้อผิดพลาดที่ยืนยันแล้ว
- ลักษณะเชิงสถาปัตยกรรมจาก `tech-stack.md` ที่ใช้ประกอบการตัดสินใจ (ถ้ามี — ส่งเป็นแนวคิดเท่านั้น)

### 7. รายงานผลกลับผู้ใช้

สรุปให้ผู้ใช้ทราบแบบกระชับ พร้อมลิงก์ไฟล์ (markdown link relative path) ไปยัง:
- `docs/02-design/02-technical/detailed-design.md`
- `docs/02-design/02-technical/index.md` (ถ้าอัปเดตครั้งแรก)
- ไฟล์ log ของวันนี้

ถ้าระหว่างทำงานพบว่ามี operation ใน `api-spec.md` ที่ยังไม่มี component/entity ต้นทางชัดเจน (เพราะ `high-level-architecture.md`/`database-schema.md` ยังไม่ครบ) ให้ระบุไว้ในรายงานว่าควรรัน skill ที่เกี่ยวข้องให้ครบก่อน แล้วค่อยกลับมาเรียก skill นี้ต่อเพื่อเติมส่วนที่ยังไม่กำหนด

## ข้อควรจำ

- **ห้ามข้ามขั้นตอนเสนอแผนและรอยืนยัน (ข้อ 5)** ไม่ว่าสโคปจะเล็กแค่ไหน หรือผู้ใช้จะเคยยืนยันแผนคล้ายกันมาก่อนในบทสนทนาเดียวกันก็ตาม
- **ห้ามระบุชื่อเทคโนโลยี/framework/library/protocol/database engine เฉพาะเจาะจงในเอกสารนี้เด็ดขาด** เอกสารต้องอยู่ในระดับ conceptual เสมอ — ถ้าผู้ใช้พูดถึงชื่อ stack มาระหว่างคุย หรือถ้าอ่าน `tech-stack.md` มาประกอบการตัดสินใจ ให้แปลงเป็นแนวคิด/หน้าที่ก่อนส่งต่อให้ agent เสมอ — tech-stack.md เป็นแค่ข้อมูลเสริมที่ทำให้ตัดสินใจได้เหมาะสมขึ้น ไม่ใช่ใบอนุญาตให้ระบุชื่อจริง
- เนื้อหาเอกสารทั้งหมดต้องเป็นภาษาไทยตาม `CLAUDE.md`
- Detailed Design มีไฟล์เดียวต่อโปรเจกต์เสมอ เป็น living document — ห้ามลบเนื้อหา/operation เดิม ให้ทำเครื่องหมายล้าสมัยแทนเมื่อของเดิมเลิกใช้
- การอ้างอิงข้ามเอกสาร `.md` ของ vault ใช้ Obsidian wikilink แบบ relative path เสมอ
- agent `detailed-design-writer` เป็นผู้เขียนไฟล์จริงทั้งหมดเท่านั้น (detailed-design.md, index, log) — skill นี้ทำหน้าที่สำรวจข้อมูล/ถามคำถาม/ยืนยันแผนเท่านั้น
- **skill นี้ต้องมี `api-spec.md` อยู่แล้วเสมอจึงทำงานได้** ถ้ายังไม่มีให้แจ้งผู้ใช้ไปรัน `api-database-design-builder` ก่อน ไม่ใช่การเดา operation ขึ้นมาเอง
