# Tech Stack Builder

Skill นี้ทำหน้าที่ **สัมภาษณ์ผู้ใช้แบบเข้มข้น** เพื่อเก็บบริบทโปรเจกต์ที่จำเป็นต่อการเลือกเทคโนโลยี (ซึ่งส่วนใหญ่**ไม่มีอยู่ในเอกสารใดของ vault มาก่อน** — เช่น ขนาด/ความถนัดของทีม งบประมาณ hosting ที่มีอยู่ timeline) ผสานกับข้อมูลเชิงเทคนิคที่มีอยู่แล้วในสาย **High-Level Architecture (component) + Database Schema (entity/ปริมาณข้อมูล) + API Spec/Detailed Design (operation ที่ซับซ้อน/real-time) + Requirement (non-functional requirement)** แล้วช่วยผู้ใช้**ตัดสินใจเลือกเทคโนโลยีจริงต่อ layer** (Frontend, Backend, Database, Authentication, File Storage, Real-time/Notification, Hosting & Deployment, CI/CD ฯลฯ) ก่อนมอบหมายให้ agent เขียนเป็นเอกสาร **Tech Stack** ที่ `docs/02-design/02-technical/tech-stack.md`

เอกสารนี้**ตรงข้ามกับเอกสารอื่นใน `02-technical`** — เอกสารอื่นทุกฉบับเป็น conceptual และห้ามระบุชื่อเทคโนโลยีจริง แต่เอกสารนี้คือที่เดียวที่ระบุชื่อเทคโนโลยี/framework/library/บริการจริงอย่างเจาะจง

ผู้ใช้อาจสั่งให้ทำทั้งหมดทุก layer หรือเจาะจงเฉพาะบาง layer (เช่น "ช่วยเลือก database ให้หน่อย") ก็ได้ — ทั้งสองกรณีต้องผ่านขั้นตอนสัมภาษณ์บริบท เสนอทางเลือก และเสนอแผนรอการยืนยันก่อนสร้าง/แก้ไขจริงเหมือนกัน **ห้ามข้ามขั้นตอนเสนอแผนไม่ว่ากรณีใด**

**ทุกคำถามที่เป็นการเลือกทาง (ไม่ใช่คำถามยืนยัน) ต้องมีตัวเลือกอย่างน้อย 3 แนวทางเสมอ** พร้อมเหตุผล ข้อดี ข้อเสีย และคำแนะนำอันดับแรก (ผู้ใช้ยังเลือก "Other" เพิ่มเองได้เสมออยู่แล้ว) — ถ้าผู้ใช้ตอบว่าไม่แน่ใจ/ให้ตัดสินใจให้ ให้เลือกตัวเลือกที่แนะนำ (Recommended) แทนแล้วแจ้งผู้ใช้ในแผนว่าเลือกให้ด้วยเหตุผลอะไร

**ข้อควรรู้เรื่องขอบเขต**: skill นี้ผูกมัดกับ technical stack จริงโดยเจตนา (ต่างจาก skill อื่นใน `02-technical`) — **อย่าเรียก agent `backlog-consistency-auditor` จากสกิลนี้** สงวนไว้เฉพาะ skill `feature-journey-sync` เท่านั้น (auditor ไม่ครอบคลุมเอกสารในโฟลเดอร์ `02-technical` อยู่แล้ว)

## ขั้นตอน

### 1. ตรวจไฟล์เดิมและไฟล์ต้นทางก่อนเสมอ (existing-first + prerequisite check)

- Glob หา `docs/02-design/02-technical/tech-stack.md`, `docs/02-design/02-technical/high-level-architecture.md`, `docs/02-design/02-technical/database-schema.md`, `docs/02-design/02-technical/api-spec.md`, `docs/02-design/02-technical/detailed-design.md`, และไฟล์ requirement ใน `docs/01-requirements/01-spec/`
- **ถ้ามี `tech-stack.md` อยู่แล้ว**: เปิดอ่านทั้งไฟล์ก่อนเสมอ เพื่อรู้ว่า layer ใดตัดสินใจไปแล้ว บริบทโปรเจกต์ที่เคยเก็บไว้คืออะไร (จะได้ไม่ถามซ้ำสิ่งที่ตอบแล้ว และต่อยอด ไม่ใช่ขัดแย้งของเดิม)
- **ถ้ายังไม่มี `high-level-architecture.md`**: ยังพอทำงานต่อได้ (ตอบคำถามเจาะจงเฉพาะ layer ได้โดยไม่ต้องมี component mapping) แต่แจ้งผู้ใช้ว่าหัวข้อ "Component ที่เกี่ยวข้อง" ต่อ layer จะต้องระบุเป็น "ยังไม่กำหนด" ไปก่อน และแนะนำให้รัน skill `architecture-builder` ก่อนถ้าต้องการผลลัพธ์ที่สมบูรณ์ — ให้ผู้ใช้ยืนยันผ่าน `AskUserQuestion` ว่าจะทำต่อแบบข้อมูลไม่ครบ หรือหยุดไปทำเอกสารต้นทางให้ครบก่อน
- ถ้ามี `database-schema.md`/`api-spec.md`/`detailed-design.md`/ไฟล์ spec ใน `01-spec/` ให้อ่านคร่าวๆ เพื่อดึงสัญญาณที่มีผลต่อการเลือกเทคโนโลยี (เช่น ความสัมพันธ์ข้อมูลซับซ้อนแค่ไหน มี operation แบบ real-time/ไฟล์แนบไหม non-functional requirement ที่ระบุไว้แล้ว เช่น จำนวนผู้ใช้พร้อมกัน)

### 2. กำหนดสโคปของ layer

- ถ้าผู้ใช้ระบุเจาะจงมาแล้วในคำขอ (เช่น "เฉพาะ database") ใช้ตามนั้นได้เลย
- ถ้าไม่ได้ระบุ ให้ถามผู้ใช้ด้วย `AskUserQuestion` ว่าต้องการสโคปแบบใด เช่น "ทุก layer ที่จำเป็น (แนะนำถ้ายังไม่เคยทำ tech stack มาก่อน)", "เฉพาะ layer ที่ระบุ", "เจาะจงเลือกเอง" — layer มาตรฐานที่ควรเสนอให้เลือก: Frontend, Backend, Database, Authentication, File Storage, Real-time/Notification, Hosting & Deployment, CI/CD (ปรับเพิ่ม/ตัดตามลักษณะโปรเจกต์จริงที่เห็นจาก high-level-architecture.md ถ้ามี)
- ถ้า `tech-stack.md` มีอยู่แล้ว ให้ตัดรายชื่อ layer ที่ตัดสินใจแล้วออกจากสโคปเริ่มต้น (เว้นแต่ผู้ใช้ขอให้ทบทวน/เปลี่ยนใจของเดิม)

### 3. สัมภาษณ์บริบทโปรเจกต์ (ทำก่อนเสนอทางเลือกเทคโนโลยีต่อ layer — ห้ามข้าม)

ใช้ `AskUserQuestion` ถามเป็นชุด (แบ่งเป็นหลายรอบได้ แต่ต้องครบทุกหัวข้อก่อนเข้าขั้นตอน 4) ครอบคลุมอย่างน้อย:

1. **ทีมพัฒนา** — ขนาดทีมกี่คน และถนัด/มีประสบการณ์กับภาษา/framework อะไรอยู่แล้วบ้าง (มีผลมากต่อการแนะนำ เพราะ stack ที่ทีม "เขียนได้จริง" สำคัญกว่า stack ที่ดีที่สุดในทางทฤษฎี)
2. **งบประมาณ/Hosting ที่มี** — มีงบ cloud ไหม หรือต้องพึ่ง free tier/มหาวิทยาลัยมี server ให้ใช้อยู่แล้วหรือไม่
3. **Timeline** — กำหนดส่ง/ระยะเวลาที่เหลือในการพัฒนา (โปรเจกต์ที่เวลาจำกัดควรเอนไปทาง stack ที่ทีมถนัด/ตั้งค่าเร็ว มากกว่า stack ใหม่ที่ต้องเรียนรู้)
4. **แพลตฟอร์มเป้าหมาย** — web อย่างเดียว, web + mobile, PWA ฯลฯ
5. **ผู้ใช้/Scale คาดการณ์** — จำนวนผู้ใช้พร้อมกันโดยประมาณ, ปริมาณข้อมูล, มี operation ที่ต้อง real-time (แจ้งเตือนทันที, chat) ไหม (ถ้ามี non-functional requirement ระบุไว้แล้วใน `01-spec` ให้ยืนยันกับผู้ใช้แทนการถามซ้ำ)
6. **ความอ่อนไหวของข้อมูล/ข้อกำหนดพิเศษ** — มีข้อมูลส่วนบุคคล/นักศึกษาที่ต้องระวังเรื่องความเป็นส่วนตัวไหม ต้องเชื่อมต่อระบบภายนอกของมหาวิทยาลัย (เช่น ระบบ SSO/ทะเบียน) ไหม
7. **ข้อบังคับ/ข้อห้ามด้านเทคโนโลยี** — มีเงื่อนไขจากรายวิชา/อาจารย์ที่ปรึกษาที่บังคับหรือห้ามใช้เทคโนโลยีบางตัวไหม ต้อง open-source/ฟรีทั้งหมดหรือไม่

ถ้าคำตอบของผู้ใช้ในหัวข้อใดยังไม่ชัดเจนพอที่จะใช้ตัดสินใจต่อ (เช่น ตอบ "ไม่รู้", "ไม่แน่ใจ") ให้เสนอทางเลือกอย่างน้อย 3 แนวทางสำหรับหัวข้อนั้นเองพร้อมข้อดี/ข้อเสีย (ไม่ใช่ปล่อยผ่าน) เช่น ถามเรื่อง hosting แล้วผู้ใช้ไม่แน่ใจ ให้เสนอ 3 แนวทาง (เช่น free-tier cloud / มหาวิทยาลัยมี server ให้ / เจาะจงยังไม่ตัดสินใจตอนนี้) พร้อมข้อดีข้อเสียแต่ละทาง

### 4. เสนอทางเลือกเทคโนโลยีต่อ layer (อย่างน้อย 3 ทางเลือกพร้อมข้อดี/ข้อเสียเสมอ)

สำหรับแต่ละ layer ในสโคป:

- นำบริบทจากขั้นตอน 3 มาประกอบกับสัญญาณเชิงเทคนิคที่มี (component จาก high-level-architecture, ความซับซ้อนของ entity/relationship จาก database-schema, ลักษณะ operation จาก api-spec/detailed-design, non-functional requirement จาก 01-spec) เพื่อร่างทางเลือกเทคโนโลยีที่เหมาะสมอย่างน้อย 3 ทางเลือก
- ใช้ `AskUserQuestion` เสนอทางเลือกทั้ง 3+ ทาง โดยแต่ละทางเลือกต้องระบุ:
  - ชื่อเทคโนโลยี/framework/library/บริการจริง
  - ข้อดี (ผูกกับบริบทของผู้ใช้ในขั้นตอน 3 โดยตรง ไม่ใช่ข้อดีทั่วไปลอยๆ)
  - ข้อเสีย/ข้อจำกัด (ผูกกับบริบทเดียวกัน)
  - ทางเลือกที่แนะนำให้ระบุ "(Recommended)" ต่อท้ายพร้อมเหตุผลสั้นๆ ว่าทำไมเหมาะกับบริบทนี้ที่สุด
- ถ้าผู้ใช้ตอบว่าไม่มั่นใจ/ให้ตัดสินใจแทน ให้เลือกตัวเลือกที่แนะนำ (Recommended) แทนการถามซ้ำ แล้วระบุไว้ในแผนช่วงข้อ 5 ว่า layer ใดเลือกให้แทนผู้ใช้ด้วยเหตุผลอะไร
- ถ้า layer หนึ่งมีความสัมพันธ์บังคับกับ layer อื่น (เช่น เลือก framework บาง framework แล้วมีฐานข้อมูล/ORM ที่เข้ากันได้ดีเป็นพิเศษ) ให้ระบุความสัมพันธ์นี้ไว้ในคำอธิบายตัวเลือกด้วย เพื่อให้ผู้ใช้ตัดสินใจ layer ถัดไปได้สอดคล้องกัน

### 5. ร่างแผนแล้วเสนอให้ผู้ใช้ยืนยันก่อนเสมอ (ห้ามข้าม)

ก่อนมอบหมายให้ agent สร้างไฟล์จริง ต้องสรุปแผนเป็นข้อความให้ผู้ใช้เห็นภาพรวมก่อนเสมอ ประกอบด้วย:

- สรุปบริบทโปรเจกต์ที่เก็บได้จากขั้นตอน 3 ทั้งหมด
- ต่อ layer แต่ละตัวในสโคป: เทคโนโลยีที่เลือก, เหตุผล, ทางเลือกอื่นที่พิจารณา (สรุปสั้น)
- จุดใดที่เลือกให้แทนผู้ใช้ (จากข้อ 3-4) พร้อมเหตุผล
- เป็นการสร้างไฟล์ใหม่ หรืออัปเดตไฟล์เดิม (ระบุว่าจะเพิ่ม/แก้ไขส่วนใด)

จากนั้นใช้ `AskUserQuestion` ถามยืนยันเป็นขั้นสุดท้ายก่อนดำเนินการ เช่น ตัวเลือก "ยืนยัน สร้าง/อัปเดตตามแผนนี้ (Recommended)" และ "ขอปรับแผนก่อน" — ถ้าผู้ใช้เลือกขอปรับ ให้กลับไปคุยรายละเอียดที่ต้องการเปลี่ยนแล้วเสนอแผนใหม่ซ้ำจนกว่าจะได้รับการยืนยัน

### 6. มอบหมายให้ agent `tech-stack-writer` สร้าง/แก้ไขไฟล์จริง

**อย่าเขียนหรือแก้ไขไฟล์ใดๆ เองใน skill นี้** เมื่อผู้ใช้ยืนยันแผนแล้วเท่านั้น ให้เรียก Agent tool โดยระบุ `subagent_type: "tech-stack-writer"` พร้อมส่ง context ให้ครบตามที่ agent ต้องการ (ดู "อินพุตที่คุณควรได้รับในคำสั่ง" ใน `.claude/agents/tech-stack-writer.md`):

- วันที่ปัจจุบันในรูปแบบ `YYYY-MM-DD`
- บริบท/ปัจจัยการตัดสินใจของโปรเจกต์ที่ยืนยันแล้วทั้งหมด (ทีม, งบประมาณ/hosting, timeline, แพลตฟอร์มเป้าหมาย, scale, ข้อจำกัดพิเศษ)
- รายชื่อ layer ที่ยืนยันแล้ว ต่อ layer แต่ละตัว: เทคโนโลยีที่เลือก, เหตุผล, component ที่เกี่ยวข้อง (ถ้ามี), ทางเลือกอื่นที่พิจารณาพร้อมข้อดี/ข้อเสีย/เหตุผลที่ไม่เลือก

### 7. รายงานผลกลับผู้ใช้

สรุปให้ผู้ใช้ทราบแบบกระชับ พร้อมลิงก์ไฟล์ (markdown link relative path) ไปยัง:
- `docs/02-design/02-technical/tech-stack.md`
- `docs/02-design/02-technical/index.md` (ถ้าอัปเดตครั้งแรก)
- ไฟล์ log ของวันนี้

ถ้าระหว่างทำงานพบว่า high-level-architecture/database-schema/api-spec/detailed-design ยังไม่ครบ (ทำให้บาง layer ไม่มี component mapping ชัดเจน) ให้ระบุไว้ในรายงานว่าควรรัน skill ที่เกี่ยวข้องให้ครบก่อน แล้วค่อยกลับมาเรียก skill นี้ต่อเพื่อเติมส่วนที่ยังไม่กำหนด

## ข้อควรจำ

- **ห้ามข้ามขั้นตอนสัมภาษณ์บริบท (ข้อ 3) และขั้นตอนเสนอแผนรอยืนยัน (ข้อ 5)** ไม่ว่าสโคปจะเล็กแค่ไหน หรือผู้ใช้จะเคยยืนยันแผนคล้ายกันมาก่อนในบทสนทนาเดียวกันก็ตาม
- **ทุกคำถามเลือกทางต้องมีอย่างน้อย 3 ตัวเลือกพร้อมข้อดี/ข้อเสียเสมอ** ทั้งคำถามเรื่องบริบทโปรเจกต์ที่ไม่ชัดเจน และคำถามเรื่องเทคโนโลยีต่อ layer — ห้ามถามแบบเปิดกว้างเฉยๆ โดยไม่มีตัวเลือกให้พิจารณา
- เอกสาร `tech-stack.md` เป็นเอกสารเดียวใน `02-technical` ที่**ต้อง**ระบุชื่อเทคโนโลยีจริง — อย่าเผลอเขียนแบบ conceptual/ไม่ระบุชื่อเหมือน skill อื่น
- เนื้อหาที่คุยกับผู้ใช้และเอกสารทั้งหมดต้องเป็นภาษาไทยตาม `CLAUDE.md`
- Tech Stack มีไฟล์เดียวต่อโปรเจกต์เสมอ เป็น living document — ห้ามลบเนื้อหา/layer เดิม ให้ทำเครื่องหมายล้าสมัยแทนเมื่อของเดิมเลิกใช้
- การอ้างอิงข้ามเอกสาร `.md` ของ vault ใช้ Obsidian wikilink แบบ relative path เสมอ
- agent `tech-stack-writer` เป็นผู้เขียนไฟล์จริงทั้งหมดเท่านั้น (tech-stack.md, index, log) — skill นี้ทำหน้าที่สัมภาษณ์/เสนอทางเลือก/ยืนยันแผนเท่านั้น
