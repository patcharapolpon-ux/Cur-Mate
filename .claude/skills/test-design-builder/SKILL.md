# Test Design Builder

Skill นี้แปลงข้อมูลที่มีอยู่ในสาย **Requirement (01-spec) → Backlog → Feature List → User Journey** ของโปรเจกต์ Curmate ให้กลายเป็นเอกสารชุดทดสอบ 3 ประเภทใน `docs/03-testing/01-test-plan/`:

1. **Acceptance Criteria** (`acceptance-criteria.md`) — สถานการณ์ทดสอบรูปแบบ Given-When-Then จัดกลุ่มตาม **Backlog Item**
2. **Test Plan** (`test-plan.md`) — กลยุทธ์การทดสอบภาพรวมของทั้งโปรเจกต์ **ไฟล์เดียว** (scope, ประเภทการทดสอบ, environment, risk management, entry/exit criteria)
3. **Test Case** (`test-cases/{feature-slug}.md`) — ขั้นตอนทดสอบแบบ step-by-step **ต่อฟีเจอร์**

ผู้ใช้อาจสั่งให้ครอบคลุมทั้งหมด หรือเจาะจงเฉพาะ backlog item/ฟีเจอร์/spec บางรายการก็ได้ — ทั้งสองกรณีต้องผ่านขั้นตอนสำรวจข้อมูล ถามคำถามชี้แจง และเสนอแผนให้ยืนยันก่อนเสมอ

ทุกจุดที่ไม่แน่ใจหรือข้อมูลไม่พอ ให้ถามผู้ใช้ก่อนเสมอ — **ห้ามเดาแทนผู้ใช้ในจุดที่กระทบผลลัพธ์เอกสารอย่างมีนัยสำคัญ** ทุกคำถามเลือกทาง (ไม่ใช่คำถามยืนยัน) ต้องมีตัวเลือกอย่างน้อย 3 แนวทางเสมอ พร้อมเหตุผล ข้อดี ข้อเสีย และคำแนะนำอันดับแรก (ผู้ใช้ยังเลือก "Other" เพิ่มเองได้เสมออยู่แล้ว)

## ขั้นตอน

### 1. กำหนดสโคป (ระบุเจาะจงได้)

- ถ้าผู้ใช้ระบุเจาะจงมาแล้วในคำขอ (backlog item/ฟีเจอร์/spec เฉพาะ หรือประเภทเอกสารเฉพาะอย่าง เช่น "ทำแค่ test case ของฟีเจอร์ X") ใช้ตามนั้นได้เลย
- ถ้าไม่ได้ระบุ ให้อ่าน `docs/01-requirements/backlog.md` และ `docs/01-requirements/02-plan/feature-list.md` มาสรุปเป็นตัวเลือกแล้วถามผู้ใช้ด้วย `AskUserQuestion` ว่าต้องการสโคปแบบใด เช่น "ทั้งหมดที่มีอยู่ (แนะนำถ้ายังไม่เคยทำชุดทดสอบมาก่อน)", "เฉพาะฟีเจอร์/Backlog Item ที่เป็น Must have", "เจาะจงเลือกเอง (ระบุ backlog item/ฟีเจอร์)"
- ถามด้วยว่าต้องการให้ทำครบทั้ง 3 ประเภทเอกสาร หรือเฉพาะบางประเภท (ถ้าผู้ใช้ไม่ได้ระบุมาแล้วในคำขอ)

### 2. ตรวจสอบความพร้อมของเอกสารต้นทางก่อนเริ่ม

- Glob/Read ตรวจว่า `docs/01-requirements/02-plan/feature-list.md` มีอยู่จริงและครอบคลุม backlog item ในสโคป — ถ้ายังไม่มีฟีเจอร์ที่จำเป็นเลย ให้แจ้งผู้ใช้ว่าต้องรัน skill `feature-journey-sync` ก่อนเพื่อแตก backlog เป็นฟีเจอร์ (ไม่ต้องรันเองแทน แค่แนะนำ)
- สังเกตคร่าวๆ ว่า feature-list/journey ดูสอดคล้องกับ spec ปัจจุบันหรือไม่ (เช่น อ้างอิง FR ที่ยังมีอยู่จริง) — ถ้าพบสัญญาณล้าสมัยชัดเจน ให้แจ้งผู้ใช้และแนะนำให้รัน `feature-journey-sync` ก่อนเพื่อความถูกต้องของเอกสารทดสอบที่จะสร้างต่อ แต่ไม่บังคับ ถ้าผู้ใช้ยืนยันจะทำต่อเลยก็ทำตามสโคปที่ระบุ
- อย่าเรียก agent `backlog-consistency-auditor` จาก skill นี้ — agent นั้นสงวนไว้เฉพาะ skill `feature-journey-sync` เท่านั้น

### 3. สำรวจเอกสารต้นทางและเอกสารทดสอบที่มีอยู่แล้ว

อ่านให้ครบตามสโคปที่กำหนด:

- `docs/01-requirements/backlog.md` และไฟล์ spec ที่เกี่ยวข้องใน `docs/01-requirements/01-spec/*.md` (Functional Requirements, Non-functional Requirements, ขอบเขต, สมมติฐาน/คำถามที่เปิดไว้)
- `docs/01-requirements/02-plan/feature-list.md`
- ไฟล์ user journey และ prototype ที่เกี่ยวข้องใน `docs/02-design/01-prototypes/` (ถ้ามี)
- เอกสารทดสอบที่มีอยู่แล้ว (ถ้ามี): `docs/03-testing/01-test-plan/acceptance-criteria.md`, `docs/03-testing/01-test-plan/test-plan.md`, `docs/03-testing/01-test-plan/test-cases/*.md` — เพื่อรู้ว่าอะไรมีอยู่แล้ว (ไม่ทำซ้ำ) และอะไรต้องเพิ่ม/อัปเดต

### 4. วิเคราะห์เนื้อหาที่ต้องสร้าง/อัปเดต — แยกตามประเภทเอกสาร

**Acceptance Criteria**: สำหรับแต่ละ Backlog Item ในสโคป จัดกลุ่มฟีเจอร์ที่เกี่ยวข้อง (จาก feature-list) แล้วร่างสถานการณ์ Given-When-Then อย่างน้อย 1 happy path ต่อฟีเจอร์ และ negative/edge case เท่าที่ spec ให้รายละเอียดไว้ชัดเจน (validation, error state, boundary, การบังคับก่อนดำเนินการต่อ)

**Test Plan**: ร่างเนื้อหาตามหัวข้อมาตรฐาน (scope, ประเภทการทดสอบ, environment, risk management, entry/exit criteria) — รวบรวม Non-functional Requirement และ "สมมติฐาน/คำถามที่เปิดไว้" จากทุก spec ในสโคปมาเป็นข้อมูลตั้งต้นของ Risk Management

**Test Case**: สำหรับแต่ละฟีเจอร์ในสโคป ร่าง test case แบบ step-by-step อย่างน้อย 1 รายการต่อ AC ที่เกี่ยวข้อง โดยดึงลำดับขั้นตอนจริงจาก user journey/prototype (ถ้ามี) มาใช้เป็นขั้นตอนทดสอบ

### 5. ถามคำถามชี้แจงจุดที่ไม่แน่ใจ

สำหรับทุกจุดที่กำกวมหรือขาดข้อมูล ใช้ `AskUserQuestion` เช่น:

- ระดับความละเอียดของ negative/edge case ที่ต้องการให้ AC/test case ครอบคลุม (เช่น เฉพาะที่ spec ระบุชัดเจน vs. ให้เดาเพิ่มเติมตามสามัญสำนึกด้าน QA)
- ต้องการให้ Test Plan ระบุ Non-functional Testing ประเภทใดบ้าง (เช่น เฉพาะที่มีข้อมูลใน spec vs. เพิ่ม security/performance เป็นมาตรฐานทั่วไปด้วย)
- Test Environment ที่จะใช้จริง (ถ้าผู้ใช้ยังไม่เคยให้ข้อมูลมาก่อน) — เสนอทางเลือกเช่น "ยังไม่กำหนด ระบุไว้ว่ารอข้อมูล (แนะนำถ้ายังไม่มี infrastructure จริง)", "ใช้ค่ากลางทั่วไปที่เหมาะกับ web application", "ผู้ใช้ระบุเอง"
- กรณีเอกสารทดสอบเดิมมีอยู่แล้วแต่ backlog/spec ที่อ้างอิงเปลี่ยนไปจนเนื้อหาเดิมอาจไม่ตรงอีกต่อไป (แนวทางแก้มีมากกว่า 1 ทาง เช่น ทำเครื่องหมายล้าสมัยแล้วเพิ่มใหม่ vs. แก้ไขของเดิมตรงจุด)

**กฎสำคัญ: ทุกคำถามที่เป็นการเลือกทาง (ไม่ใช่คำถามยืนยันแผน) ต้องมีตัวเลือกอย่างน้อย 3 แนวทางเสมอ** พร้อมคำอธิบายเหตุผล ข้อดี ข้อเสีย ของแต่ละแนวทาง และให้ตัวเลือกที่แนะนำมาเป็นอันดับแรกพร้อมระบุว่าแนะนำเพราะอะไร

ถามเป็นชุดๆ จนกว่าจะมีข้อมูลพอร่างแผนในขั้นตอนที่ 6 ได้อย่างสมบูรณ์

### 6. ร่างแผนแล้วเสนอให้ผู้ใช้ยืนยันก่อนเสมอ (ห้ามข้าม)

ก่อนมอบหมายให้ agent สร้างไฟล์จริง ต้องสรุปแผนเป็นข้อความให้ผู้ใช้เห็นภาพรวมก่อนเสมอ ประกอบด้วย:

- สโคปที่จะครอบคลุม (backlog item/ฟีเจอร์ใดบ้าง) และประเภทเอกสารที่จะสร้าง/อัปเดต (AC / Test Plan / Test Case หรือครบทั้ง 3)
- สำหรับ Acceptance Criteria: รายชื่อ Backlog Item x ฟีเจอร์ที่จะเพิ่ม/แก้ไข พร้อมจำนวนสถานการณ์โดยประมาณ
- สำหรับ Test Plan: หัวข้อ/ส่วนที่จะสร้างใหม่หรืออัปเดต (สร้างครั้งแรกทั้งไฟล์ หรืออัปเดตเฉพาะ scope/risk บางส่วน)
- สำหรับ Test Case: รายชื่อไฟล์ต่อฟีเจอร์ที่จะสร้าง/อัปเดต

จากนั้นใช้ `AskUserQuestion` ถามยืนยันเป็นขั้นสุดท้ายก่อนดำเนินการ เช่น ตัวเลือก "ยืนยัน สร้างตามแผนนี้ (Recommended)" และ "ขอปรับแผนก่อน" — ถ้าผู้ใช้เลือกขอปรับ ให้กลับไปคุยรายละเอียดที่ต้องการเปลี่ยนแล้วเสนอแผนใหม่ซ้ำจนกว่าจะได้รับการยืนยัน

### 7. มอบหมายให้ sub agent เขียน/แก้ไขเอกสารจริง ตามลำดับ

**อย่าเขียนหรือแก้ไขไฟล์ใดๆ เองใน skill นี้** เมื่อผู้ใช้ยืนยันแผนแล้วเท่านั้น ให้เรียก Agent tool ตามลำดับนี้เสมอ (ห้ามสลับลำดับ เพราะชั้นถัดไปต้องอ้างอิงข้อมูลของชั้นก่อนหน้าที่อัปเดตแล้ว):

1. **`acceptance-criteria-writer`** — เรียกครั้งเดียว ส่ง Backlog Item/ฟีเจอร์/สถานการณ์ทั้งหมดในสโคปที่วิเคราะห์และยืนยันแล้วจากขั้นตอนที่ 4-6 (ข้ามขั้นตอนนี้ได้เฉพาะกรณีผู้ใช้ระบุชัดว่าไม่ต้องการ Acceptance Criteria รอบนี้ และมี AC เดิมครบอยู่แล้วสำหรับฟีเจอร์ในสโคป)
2. **`test-plan-writer`** — เรียกครั้งเดียว ส่งขอบเขต/ประเด็น NFR/risk ที่วิเคราะห์แล้ว (ข้ามได้ถ้าผู้ใช้ระบุชัดว่าไม่ต้องการอัปเดต Test Plan รอบนี้)
3. **`test-case-writer`** — เรียก**ทีละฟีเจอร์เท่านั้น เรียงลำดับ ห้ามเรียกขนานกัน** (เพราะทุกครั้งต้องแก้ manifest `test-cases/index.md` ไฟล์เดียวกัน) ส่ง AC ID ที่เกี่ยวข้องของฟีเจอร์นั้น (จากผลลัพธ์ของ agent ข้อ 1) และ journey/prototype ที่เกี่ยวข้อง

### 8. รายงานผลกลับผู้ใช้

สรุปให้ผู้ใช้ทราบแบบกระชับ พร้อมลิงก์ไฟล์ (markdown link relative path) ไปยัง:
- `docs/03-testing/01-test-plan/acceptance-criteria.md` (ถ้าสร้าง/แก้ไข)
- `docs/03-testing/01-test-plan/test-plan.md` (ถ้าสร้าง/แก้ไข)
- ไฟล์ `test-cases/*.md` ทุกไฟล์ที่สร้าง/แก้ไข และ `test-cases/index.md`
- `docs/03-testing/01-test-plan/index.md` (ถ้าอัปเดต) และไฟล์ log ของวันนี้

## ข้อควรจำ

- **ห้ามข้ามขั้นตอนเสนอแผนและรอยืนยัน (ข้อ 6)** ไม่ว่าสโคปจะเล็กแค่ไหน
- **ห้ามเรียก `test-case-writer` มากกว่า 1 ตัวพร้อมกันแบบขนาน** เรียงลำดับทีละฟีเจอร์เสมอ เพราะทุกครั้งแก้ manifest ไฟล์เดียวกัน
- เนื้อหาเอกสารทั้งหมดต้องเป็นภาษาไทยตาม `CLAUDE.md` (ยกเว้น Given/When/Then, slug/technical term)
- ห้ามลบเอกสาร/สถานการณ์/แถว test case เดิม ให้ทำเครื่องหมายล้าสมัยแทนเสมอ (ดูรายละเอียดใน agent แต่ละตัว)
- การอ้างอิงข้ามเอกสารใช้ Obsidian wikilink แบบ relative path เสมอ
- agent `acceptance-criteria-writer` / `test-plan-writer` / `test-case-writer` เป็นผู้เขียนไฟล์จริงทั้งหมดเท่านั้น — skill นี้ทำหน้าที่สำรวจข้อมูล/ถามคำถาม/ยืนยันแผนเท่านั้น
- ถ้าพบว่า feature-list/user journey ล้าสมัยเทียบกับ spec ปัจจุบันระหว่างสำรวจข้อมูล ให้แจ้งผู้ใช้และแนะนำ skill `feature-journey-sync` แต่ไม่บังคับให้รันก่อนเสมอไป
