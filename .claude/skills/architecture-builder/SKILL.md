# Architecture Builder

Skill นี้แปลงข้อมูลที่มีอยู่ในสาย **Requirement (01-spec) → Feature List → User Journey** ของโปรเจกต์ Curmate ให้กลายเป็น **High-Level Architecture** — เอกสาร conceptual ที่อธิบายว่าระบบประกอบด้วย component/actor อะไร ข้อมูลไหลระหว่างกันอย่างไรตาม user journey แต่ละเส้น โดย**ไม่ผูกมัดกับ technical stack** เก็บเป็นไฟล์เดียวต่อโปรเจกต์ที่ `docs/02-design/02-technical/high-level-architecture.md`

ผู้ใช้อาจสั่งให้ครอบคลุมทั้งหมด หรือเจาะจงเฉพาะบางฟีเจอร์/journey ก็ได้ — ทั้งสองกรณีต้องผ่านขั้นตอนเสนอแผนและรอการยืนยันก่อนสร้าง/แก้ไขจริงเหมือนกัน **ห้ามข้ามขั้นตอนเสนอแผนไม่ว่ากรณีใด**

ทุกจุดที่ไม่แน่ใจหรือข้อมูลไม่พอ ให้ถามผู้ใช้ก่อนเสมอ — **ห้ามเดาแทนผู้ใช้ในจุดที่กระทบผลลัพธ์เอกสารอย่างมีนัยสำคัญ** ทุกคำถามเลือกทาง (ไม่ใช่คำถามยืนยัน) ต้องมีตัวเลือกอย่างน้อย 3 แนวทางเสมอ พร้อมเหตุผล ข้อดี ข้อเสีย และคำแนะนำอันดับแรก (ผู้ใช้ยังเลือก "Other" เพิ่มเองได้เสมออยู่แล้ว)

**ข้อควรรู้เรื่องขอบเขต**: skill นี้ทำเฉพาะเอกสารระดับ conceptual (ไม่ผูกกับ stack) เท่านั้น ส่วนเอกสารเชิงเทคนิคจริง (database schema, API design, การเลือกเทคโนโลยี/library) เป็นคนละไฟล์ใน `docs/02-design/02-technical/` ที่ยังไม่มี agent/skill เฉพาะดูแล — ถ้าผู้ใช้ขอให้ลงรายละเอียดระดับนั้น ให้แจ้งว่าอยู่นอกสโคปของ skill นี้แทนการเดาลงไปในเอกสาร conceptual — **อย่าเรียก agent `backlog-consistency-auditor` จากสกิลนี้** สงวนไว้เฉพาะ skill `feature-journey-sync` เท่านั้น เพื่อให้มีจุดตรวจสอบความสอดคล้องของทั้งสายอยู่ที่เดียวเสมอ

## ขั้นตอน

### 1. ตรวจไฟล์เดิมก่อนเสมอ (existing-first)

- Glob หา `docs/02-design/02-technical/high-level-architecture.md`
- **ถ้ามีอยู่แล้ว**: เปิดอ่านทั้งไฟล์ก่อนเสมอ เพื่อรู้ว่ามี component/entity/journey ใดถูกบันทึกไว้แล้วบ้าง (จะได้ต่อยอด ไม่ใช่เขียนซ้ำ/ขัดแย้งของเดิม)
- **ถ้ายังไม่มี**: เป็นการสร้างครั้งแรก ไปข้อ 2 ได้เลย

### 2. กำหนดสโคป (ระบุเจาะจงได้)

- ถ้าผู้ใช้ระบุเจาะจงมาแล้วในคำขอ (ชื่อฟีเจอร์/journey เฉพาะ) ใช้ตามนั้นได้เลย
- ถ้าไม่ได้ระบุ ให้อ่าน `docs/01-requirements/01-spec/*.md`, `docs/01-requirements/02-plan/feature-list.md` (ถ้ามี) และไฟล์ user journey ใน `docs/02-design/01-prototypes/*-user-journey-*.md` มาสรุปเป็นตัวเลือกแล้วถามผู้ใช้ด้วย `AskUserQuestion` ว่าต้องการสโคปแบบใด เช่น "ทั้งหมดที่มีอยู่ (แนะนำถ้ายังไม่เคยทำ architecture มาก่อน)", "เฉพาะฟีเจอร์/journey ที่ระบุ", "เจาะจงเลือกเอง"
- อ่านเอกสารต้นทางในสโคปที่เลือกให้ครบ เพื่อใช้ระบุ component/actor ที่ควรมี, journey ที่ต้องทำ data flow diagram, และ conceptual data entity ที่เกี่ยวข้อง
- ถ้าพบระหว่างสำรวจว่าไฟล์ `high-level-architecture.md` เดิม (ที่อยู่นอกสโคปที่ผู้ใช้ขอในรอบนี้) มีจุดอ้างอิงฟีเจอร์/journey/FR ผิดหรือล้าสมัยเทียบกับ requirement/feature-list/journey ปัจจุบัน ให้แจ้งผู้ใช้และแนะนำให้รัน skill `feature-journey-sync` ต่อเพื่อซ่อมจุดนั้น (ไม่บังคับ ถ้าผู้ใช้ยืนยันจะทำสโคปที่ขอไว้ต่อเลยก็ทำได้)

### 3. วิเคราะห์ component/actor เชิงแนวคิด

- จัดกลุ่ม Functional Requirement/ฟีเจอร์ที่เกี่ยวข้องกันให้เป็น "component" เชิงบทบาท (role-based) เช่น component ที่รับ input จากผู้ใช้, component ที่ประมวลผล/ตัดสินใจตามกฎธุรกิจ, component ที่เก็บข้อมูล, component ที่แจ้งเตือน —**ห้ามตั้งชื่อ/เลือก component ตามเทคโนโลยีหรือ product จริง**
- ระบุ actor ทั้งหมด (ผู้ใช้แต่ละบทบาท + ระบบภายนอกที่เกี่ยวข้อง ถ้ามี)
- ระบุ conceptual data entity หลักที่ต้องมี (ชื่อ + คำอธิบาย + component เจ้าของ) จากข้อมูลที่ spec/feature-list พูดถึง
- พิจารณาว่า user journey ใดบ้างที่ควรมี data flow diagram (โดยทั่วไปคือ journey ทั้งหมดที่อยู่ในสโคป)

จุดที่กำกวมหรือมีมากกว่า 1 ทางเลือกสมเหตุสมผลในขั้นตอนนี้ (เช่น การแบ่ง component ว่าจะรวมหรือแยกหน้าที่ใดหน้าที่หนึ่งเป็น component เดี่ยว, ระดับความละเอียดของ diagram ภาพรวม, การตั้งชื่อ entity ที่ spec ไม่ได้ระบุไว้ชัด) ให้ถามผู้ใช้ตามกฎ 3 ทางเลือกในข้อ 5

### 4. ร่างแผนแล้วเสนอให้ผู้ใช้ยืนยันก่อนเสมอ (ห้ามข้าม)

ก่อนมอบหมายให้ agent สร้างไฟล์จริง ต้องสรุปแผนเป็นข้อความให้ผู้ใช้เห็นภาพรวมก่อนเสมอ ประกอบด้วย:

- สโคปที่จะครอบคลุม (ฟีเจอร์/journey ใดบ้าง)
- รายชื่อ component/actor เชิงแนวคิดที่จะอยู่ใน diagram ภาพรวม พร้อมหน้าที่รับผิดชอบสั้นๆ ของแต่ละตัว
- รายชื่อ user journey ที่จะทำ data flow diagram ให้ (อ้างอิงไฟล์ journey ต้นทาง)
- รายชื่อ conceptual data entity ที่จะบันทึก
- ระบบภายนอกที่เกี่ยวข้อง (ถ้ามี)
- เป็นการสร้างไฟล์ใหม่ หรืออัปเดตไฟล์เดิม (ระบุว่าจะเพิ่ม/แก้ไขส่วนใด)

จากนั้นใช้ `AskUserQuestion` ถามยืนยันเป็นขั้นสุดท้ายก่อนดำเนินการ เช่น ตัวเลือก "ยืนยัน สร้าง/อัปเดตตามแผนนี้ (Recommended)" และ "ขอปรับแผนก่อน" — ถ้าผู้ใช้เลือกขอปรับ ให้กลับไปคุยรายละเอียดที่ต้องการเปลี่ยนแล้วเสนอแผนใหม่ซ้ำจนกว่าจะได้รับการยืนยัน

### 5. ถามคำถามชี้แจงจุดที่ไม่แน่ใจ (ระหว่างขั้นตอน 2-4)

สำหรับทุกจุดที่กำกวมหรือขาดข้อมูล เช่น:

- การจัดกลุ่ม FR/ฟีเจอร์เป็น component (กรณีแบ่งได้มากกว่า 1 แบบสมเหตุสมผล)
- ระดับความละเอียดของ diagram ภาพรวม (เช่น ควรแยก component ย่อยหรือควบรวมเป็นก้อนใหญ่)
- การตั้งชื่อ/ขอบเขตของ conceptual data entity ที่ spec ไม่ได้ระบุไว้ชัด
- ระบบภายนอกที่ spec พูดถึงแต่ยังไม่ชัดว่าเป็นข้อเท็จจริงทางธุรกิจ (ใช้ชื่อจริงได้) หรือเป็นทางเลือกด้าน stack (ต้องเขียนเชิงบทบาทแทน)
- ประเด็น quality attribute เชิงแนวคิดที่ spec ไม่ได้ระบุไว้

ใช้ `AskUserQuestion` **ทุกคำถามที่เป็นการเลือกทาง (ไม่ใช่คำถามยืนยันแผน) ต้องมีตัวเลือกอย่างน้อย 3 แนวทางเสมอ** พร้อมคำอธิบายเหตุผล ข้อดี ข้อเสีย ของแต่ละแนวทาง และให้ตัวเลือกที่แนะนำมาเป็นอันดับแรกพร้อมระบุว่าแนะนำเพราะอะไร

ถามเป็นชุดๆ จนกว่าจะมีข้อมูลพอร่างแผนในขั้นตอนที่ 4 ได้อย่างสมบูรณ์

### 6. มอบหมายให้ agent `high-level-architecture-writer` สร้าง/แก้ไขไฟล์จริง

**อย่าเขียนหรือแก้ไขไฟล์ใดๆ เองใน skill นี้** เมื่อผู้ใช้ยืนยันแผนแล้วเท่านั้น ให้เรียก Agent tool โดยระบุ `subagent_type: "high-level-architecture-writer"` พร้อมส่ง context ให้ครบตามที่ agent ต้องการ (ดู "อินพุตที่คุณควรได้รับในคำสั่ง" ใน `.claude/agents/high-level-architecture-writer.md`):

- วันที่ปัจจุบันในรูปแบบ `YYYY-MM-DD`
- รายชื่อ component/actor เชิงแนวคิดที่ยืนยันแล้วทั้งหมด พร้อมหน้าที่รับผิดชอบ
- รายชื่อ user journey ที่ยืนยันแล้วพร้อม path ไฟล์ journey ต้นทาง
- รายชื่อ conceptual data entity ที่ยืนยันแล้ว พร้อม component เจ้าของ
- ระบบภายนอกที่เกี่ยวข้อง (ถ้ามี) พร้อมระบุว่าใช้ชื่อจริงได้หรือต้องเขียนเชิงบทบาท
- ประเด็น quality attribute เชิงแนวคิดที่ยืนยันแล้ว (ถ้ามี)

### 7. รายงานผลกลับผู้ใช้

สรุปให้ผู้ใช้ทราบแบบกระชับ พร้อมลิงก์ไฟล์ (markdown link relative path) ไปยัง:
- `docs/02-design/02-technical/high-level-architecture.md`
- `docs/02-design/02-technical/index.md` (ถ้าอัปเดตครั้งแรก)
- ไฟล์ log ของวันนี้

ถ้าระหว่างทำงานพบว่ามีฟีเจอร์/journey ที่ยังไม่มี user journey รองรับเลย (จึงยังทำ data flow diagram ให้ไม่ได้) ให้ระบุไว้ในรายงานว่าควรรัน skill `feature-journey-sync` เพื่อสร้าง journey นั้นก่อน แล้วค่อยกลับมาเรียก skill นี้ต่อ

## ข้อควรจำ

- **ห้ามข้ามขั้นตอนเสนอแผนและรอยืนยัน (ข้อ 4)** ไม่ว่าสโคปจะเล็กแค่ไหน หรือผู้ใช้จะเคยยืนยันแผนคล้ายกันมาก่อนในบทสนทนาเดียวกันก็ตาม
- **ห้ามระบุชื่อเทคโนโลยี/framework/library/database/cloud product เฉพาะเจาะจงในเอกสารนี้เด็ดขาด** เอกสารต้องอยู่ในระดับ conceptual เสมอ — ถ้าผู้ใช้พูดถึงชื่อ stack มาระหว่างคุย ให้แปลงเป็นบทบาท/หน้าที่เชิงแนวคิดก่อนส่งต่อให้ agent
- เนื้อหาเอกสารทั้งหมดต้องเป็นภาษาไทยตาม `CLAUDE.md`
- High-Level Architecture มีไฟล์เดียวต่อโปรเจกต์เสมอ เป็น living document — ห้ามลบเนื้อหา/component/journey/entity เดิม ให้ทำเครื่องหมายล้าสมัยแทนเมื่อของเดิมเลิกใช้
- การอ้างอิงข้ามเอกสาร `.md` ของ vault ใช้ Obsidian wikilink แบบ relative path เสมอ
- agent `high-level-architecture-writer` เป็นผู้เขียนไฟล์จริงทั้งหมดเท่านั้น (high-level-architecture.md, index, log) — skill นี้ทำหน้าที่สำรวจข้อมูล/ถามคำถาม/ยืนยันแผนเท่านั้น
- **ห้ามใช้ skill นี้เขียนรายละเอียดเชิงเทคนิคจริง** (database schema, API design, การเลือกเทคโนโลยี/library) — ถ้าผู้ใช้ต้องการเอกสารระดับนั้น ให้แจ้งว่าอยู่นอกสโคปของ skill นี้
