# Release Plan Builder

Skill นี้แปลงข้อมูลที่มีอยู่ในสาย **Requirement (01-spec) → Backlog → Feature List (MoSCoW)** ของโปรเจกต์ Curmate ให้กลายเป็นเอกสารวางแผนการทำงาน 2 ระดับใน `docs/01-requirements/`:

- **Release Plan** (`02-plan/release-plan.md`) — แบ่งฟีเจอร์ทั้งหมดออกเป็น phase/release ตามลำดับเวลาที่จะลงมือทำ พร้อมกลยุทธ์การแบ่งและเหตุผล ดูแลโดย agent `release-plan-writer` (เอกสารเดียวต่อโปรเจกต์ เป็น living document)
- **Task Breakdown** (`03-task/{NN}-{phase-slug}.md`) — แตก phase แต่ละตัวออกเป็น task list ที่ลงมือทำได้จริง พร้อมสถานะ/ผู้รับผิดชอบ/deadline ดูแลโดย agent `task-breakdown-writer` (ไฟล์แยกต่อ phase)

ผู้ใช้อาจสั่งให้ทำทั้งสองระดับ (วาง release plan แล้วแตก task ต่อทันที) หรือเจาะจงเฉพาะระดับใดระดับหนึ่งก็ได้ (เช่น "ขอแค่แบ่ง phase ก่อน ยังไม่ต้องแตก task" หรือ "มี release plan อยู่แล้ว ขอแตก task ของ Phase 2 เพิ่ม") — ทุกกรณีต้องผ่านขั้นตอนสัมภาษณ์/เสนอทางเลือกและเสนอแผนรอการยืนยันก่อนสร้าง/แก้ไขจริงเหมือนกัน **ห้ามข้ามขั้นตอนเสนอแผนไม่ว่ากรณีใด**

**ทุกจุดที่เป็นการเลือกทาง (ไม่ใช่คำถามยืนยัน) ต้องมีตัวเลือกอย่างน้อย 3 แนวทางเสมอ** พร้อมเหตุผล ข้อดี ข้อเสีย และคำแนะนำอันดับแรก (ผู้ใช้ยังเลือก "Other" เพิ่มเองได้เสมออยู่แล้ว) — ถ้าผู้ใช้ตอบว่าไม่แน่ใจ/ให้ตัดสินใจให้ ให้เลือกตัวเลือกที่แนะนำ (Recommended) แทนแล้วแจ้งผู้ใช้ในแผนว่าเลือกให้ด้วยเหตุผลอะไร **ห้ามเดาแทนผู้ใช้ในจุดที่กระทบผลลัพธ์เอกสารอย่างมีนัยสำคัญ**

**อย่าเรียก agent `backlog-consistency-auditor` จากสกิลนี้** สงวนไว้เฉพาะ skill `feature-journey-sync` เท่านั้น (auditor ยังไม่ครอบคลุมเอกสาร `02-plan/release-plan.md` และ `03-task/*.md` ในสายตรวจสอบปัจจุบัน — ถ้าผู้ใช้ต้องการให้ auditor ครอบคลุมด้วย ให้แจ้งว่าเป็นการเปลี่ยนแปลง agent `backlog-consistency-auditor` ซึ่งอยู่นอกสโคปของ skill นี้ และควรทำเป็นคำขอแยกต่างหาก)

## ขั้นตอน

### 1. ตรวจไฟล์เดิมและไฟล์ต้นทางก่อนเสมอ (existing-first + prerequisite check)

- Glob หา `docs/01-requirements/02-plan/release-plan.md`, `docs/01-requirements/02-plan/feature-list.md`, `docs/01-requirements/backlog.md`, ไฟล์ requirement ใน `docs/01-requirements/01-spec/`, และไฟล์ task breakdown ที่มีอยู่ใน `docs/01-requirements/03-task/*.md`
- **ถ้ายังไม่มี `feature-list.md`**: เอกสารนี้เป็นแหล่งอ้างอิงหลักของทั้งสองระดับ (release plan อ้างฟีเจอร์เป็นตัวแบ่ง phase, task breakdown อ้างฟีเจอร์เป็น field บังคับ) — แจ้งผู้ใช้ว่าควรรัน skill `feature-journey-sync` เพื่อสร้าง feature list ก่อน แล้วใช้ `AskUserQuestion` ถามว่าจะหยุดไปทำ feature list ก่อน หรือยืนยันจะทำต่อโดยผู้ใช้ระบุรายชื่อฟีเจอร์เองในคำสั่งแทน (ถ้าเลือกทำต่อ ให้ระบุในเอกสารว่าฟีเจอร์เหล่านี้ยังไม่ได้ยืนยันผ่าน feature-list.md อย่างเป็นทางการ)
- **ถ้ามี `release-plan.md` อยู่แล้ว**: เปิดอ่านทั้งไฟล์ก่อนเสมอ เพื่อรู้ว่ามี phase ใดวางแผนไว้แล้ว กลยุทธ์การแบ่งที่เคยเลือกไว้คืออะไร (จะได้ไม่ถามซ้ำสิ่งที่ตัดสินใจแล้ว และต่อยอด ไม่ใช่ขัดแย้งของเดิม)
- **ถ้ามีไฟล์ใน `03-task/` อยู่แล้ว**: เปิดอ่านไฟล์ของ phase ที่เกี่ยวข้องกับสโคปรอบนี้ เพื่อรู้ว่ามีงานใดอยู่แล้วบ้าง (จะได้เพิ่ม/แก้ไข ไม่ใช่สร้างซ้ำ)

### 2. กำหนดสโคปของงาน (ระดับ + phase/ฟีเจอร์ที่เกี่ยวข้อง)

ใช้ `AskUserQuestion` ถ้าคำขอเดิมของผู้ใช้ยังไม่ชัดเจนว่าต้องการระดับใด:

- "ทั้งสองระดับ: วาง Release Plan แล้วแตก Task Breakdown ต่อทันที (แนะนำถ้ายังไม่เคยวางแผนมาก่อน)"
- "เฉพาะ Release Plan (แบ่ง phase อย่างเดียว ยังไม่แตก task)"
- "เฉพาะ Task Breakdown ของ phase ที่ระบุ (ต้องมี `release-plan.md` อยู่แล้ว — ถ้ายังไม่มีให้แจ้งผู้ใช้และเสนอทำ Release Plan ก่อน)"

จากนั้นกำหนดสโคปของเนื้อหา:
- ถ้าผู้ใช้ระบุเจาะจงมาแล้ว (เช่น "เฉพาะฟีเจอร์ 01-05" หรือ "เฉพาะ Phase 2") ใช้ตามนั้นได้เลย
- ถ้าไม่ได้ระบุและเป็นการทำ Release Plan ใหม่ทั้งหมด ให้ถือว่าสโคปคือฟีเจอร์ทั้งหมดใน `feature-list.md` (ยกเว้นฟีเจอร์ที่ถูกทำเครื่องหมาย `Won't have (this time)`)
- ถ้าเป็นการแตก Task Breakdown ให้ยืนยันกับผู้ใช้ว่าจะทำครบทุก phase ที่ยังไม่มี task breakdown หรือเจาะจงบาง phase

### 3. สัมภาษณ์กลยุทธ์การแบ่ง Phase/Release (ทำก่อนเสมอถ้าสโคปมี Release Plan — ห้ามข้าม)

ถ้า `release-plan.md` ยังไม่มีอยู่ (หรือผู้ใช้ขอทบทวนกลยุทธ์ใหม่) ให้ใช้ `AskUserQuestion` เสนอแนวทางการแบ่ง phase/release อย่างน้อย 3 แนวทาง เช่น:

1. **แบ่งตามลำดับความสำคัญ MoSCoW** (Must have ทั้งหมดก่อนเป็น Phase แรก, Should/Could have ตามมา) — ข้อดี: สอดคล้องกับ `feature-list.md` ที่มีอยู่แล้วโดยตรง ได้ MVP ที่ใช้งานได้จริงเร็วที่สุด; ข้อเสีย: อาจไม่คำนึงถึง dependency ทางเทคนิคระหว่างฟีเจอร์ (บาง Should have อาจเป็นรากฐานของ Must have อื่น)
2. **แบ่งตาม dependency/ความเสี่ยงทางเทคนิค** (ทำฟีเจอร์ที่เป็นรากฐานหรือความเสี่ยงสูงสุดก่อน ไม่ว่าจะเป็น MoSCoW ระดับใด) — ข้อดี: ลดความเสี่ยงที่โปรเจกต์จะติดขัดกลางทางเพราะเจอปัญหาทางเทคนิคช้าเกินไป; ข้อเสีย: อาจไม่ได้ส่งมอบคุณค่าที่ผู้ใช้เห็นผลเร็วที่สุด
3. **แบ่งตาม user journey/persona** (ทำให้ครบ 1 journey/บทบาทผู้ใช้ก่อน ค่อยขึ้น journey ถัดไป) — ข้อดี: แต่ละ phase ส่งมอบ flow การใช้งานที่ครบสมบูรณ์ ทดสอบ/สาธิตได้เป็นเรื่องราว; ข้อเสีย: ฟีเจอร์/โครงสร้างพื้นฐานที่ใช้ร่วมกันหลาย journey อาจต้องทำซ้ำหรือวางแผนล่วงหน้าให้ดี
4. **แบ่งตามกรอบเวลาคงที่ (timeboxed)** (กำหนดจำนวน phase/ระยะเวลาต่อ phase ตายตัวจาก deadline แล้วเติมฟีเจอร์เท่าที่ทำได้ตามลำดับความสำคัญ) — ข้อดี: คาดการณ์ timeline ได้ชัดเจน เหมาะกับโปรเจกต์ที่มี deadline ตายตัว (เช่น กำหนดส่งงานวิชา); ข้อเสีย: ขอบเขตของแต่ละ phase ไม่แน่นอน อาจต้องตัดฟีเจอร์ออกกลางทางถ้าประเมินเวลาไม่แม่นยำ

ระบุแนวทางที่แนะนำ (Recommended) พร้อมเหตุผลตามบริบทที่เห็นจาก spec/feature-list (เช่น ถ้ามี deadline ชัดเจนในเอกสาร ให้แนะนำแนวทาง 4; ถ้าไม่มีข้อจำกัดพิเศษ ให้แนะนำแนวทาง 1 เพราะสอดคล้องกับ MoSCoW ที่มีอยู่แล้วโดยตรง) ถ้าผู้ใช้ต้องการแนวทางผสมกัน (เช่น MoSCoW เป็นหลักแต่ปรับลำดับตาม dependency) ให้บันทึกเป็นแนวทางที่เลือกแบบผสมได้ พร้อมอธิบายกติกาการผสมให้ชัดเจน

ถ้า `release-plan.md` มีอยู่แล้วและผู้ใช้แค่ต้องการเพิ่ม phase ใหม่ (ไม่ทบทวนกลยุทธ์) ให้ข้ามขั้นตอนนี้ไปและใช้กลยุทธ์เดิมที่บันทึกไว้ต่อ

### 4. ร่างขอบเขตของแต่ละ Phase

- นำกลยุทธ์จากขั้นตอน 3 มาจัดกลุ่มฟีเจอร์ในสโคป (จากขั้นตอน 2) เป็น phase ร่างเบื้องต้น พร้อมชื่อ/เป้าหมายต่อ phase
- ถ้ามีจุดที่กำกวม (เช่น ฟีเจอร์หนึ่งเข้าได้ทั้ง phase A และ B, จำนวน phase ที่เหมาะสมมีมากกว่า 1 ทางเลือกสมเหตุสมผล, milestone/ช่วงเวลาต่อ phase ที่ผู้ใช้ยังไม่ระบุ) ให้ถามผู้ใช้ตามกฎ 3 ทางเลือกในขั้นตอน 6
- ระบุ dependency ระหว่าง phase ให้ชัดเจน (phase ใดต้องรอ phase ใดเสร็จก่อน พร้อมเหตุผล)

### 5. ร่างรายการงานย่อยต่อ Phase (เฉพาะถ้าสโคปมี Task Breakdown)

สำหรับแต่ละ phase ในสโคป:

- แตกฟีเจอร์ที่รวมอยู่ใน phase นั้นออกเป็นงานย่อยที่ลงมือทำได้จริง โดยพิจารณาจากคำอธิบายฟีเจอร์ใน `feature-list.md` และ FR ที่เกี่ยวข้องใน `01-spec/*.md`
- ถ้ามีเอกสารเชิงเทคนิคอยู่แล้ว (`docs/02-design/02-technical/*.md`) ให้อ่านประกอบเพื่อแตกงานตามความเป็นจริงมากขึ้นได้ (เช่น งานออกแบบ, งานฝั่ง backend/frontend, งานทดสอบ) แต่ไม่บังคับต้องมี
- จุดที่กำกวม (เช่น ควรแตกฟีเจอร์หนึ่งเป็นกี่งานย่อย, ระดับความละเอียดของงานที่ผู้ใช้ต้องการ, ผู้รับผิดชอบ/deadline ที่ยังไม่ระบุ) ให้ถามผู้ใช้ตามกฎ 3 ทางเลือกในขั้นตอน 6 — ตัวอย่างทางเลือกสำหรับ "ระดับความละเอียดของงาน":
  1. **แตกงานระดับหยาบต่อฟีเจอร์** (1-2 งานต่อฟีเจอร์ เช่น "ออกแบบ+พัฒนาฟีเจอร์ X", "ทดสอบฟีเจอร์ X") — ข้อดี: ดูแลง่าย เหมาะกับทีมเล็ก/ทำคนเดียว; ข้อเสีย: ไม่เห็นความคืบหน้าย่อยระหว่างทาง
  2. **แตกงานระดับกลางตามขั้นตอนการพัฒนา** (เช่น ออกแบบ UI, พัฒนา backend, พัฒนา frontend, เชื่อมต่อ, ทดสอบ แยกเป็นงานย่อยต่อฟีเจอร์) — ข้อดี: ติดตามความคืบหน้าได้ละเอียดขึ้น เหมาะกับทีมที่แบ่งบทบาทกัน; ข้อเสีย: จำนวนงานเยอะขึ้น ดูแล manifest มากขึ้น
  3. **แตกงานระดับละเอียดตาม FR ย่อยของแต่ละฟีเจอร์** — ข้อดี: ครอบคลุมทุกรายละเอียดที่ spec ระบุไว้ ไม่ตกหล่น; ข้อเสีย: ใช้เวลาวางแผนนานและอาจละเอียดเกินความจำเป็นสำหรับโปรเจกต์ขนาดเล็ก

### 6. ถามคำถามชี้แจงจุดที่ไม่แน่ใจ (ระหว่างขั้นตอน 3-5)

ใช้ `AskUserQuestion` **ทุกคำถามที่เป็นการเลือกทาง (ไม่ใช่คำถามยืนยันแผน) ต้องมีตัวเลือกอย่างน้อย 3 แนวทางเสมอ** พร้อมคำอธิบายเหตุผล ข้อดี ข้อเสีย ของแต่ละแนวทาง และให้ตัวเลือกที่แนะนำมาเป็นอันดับแรกพร้อมระบุว่าแนะนำเพราะอะไร ถามเป็นชุดๆ จนกว่าจะมีข้อมูลพอร่างแผนในขั้นตอนที่ 7 ได้อย่างสมบูรณ์ — ถ้าผู้ใช้ตอบว่าไม่แน่ใจ/ให้ตัดสินใจแทน ให้เลือกตัวเลือกที่แนะนำแล้วระบุไว้ในแผนว่าเลือกให้แทนผู้ใช้ด้วยเหตุผลอะไร

### 7. ร่างแผนแล้วเสนอให้ผู้ใช้ยืนยันก่อนเสมอ (ห้ามข้าม)

ก่อนมอบหมายให้ agent สร้างไฟล์จริง ต้องสรุปแผนเป็นข้อความให้ผู้ใช้เห็นภาพรวมก่อนเสมอ ประกอบด้วย:

- (ถ้าสโคปมี Release Plan) กลยุทธ์การแบ่ง phase ที่เลือก พร้อมเหตุผลและทางเลือกอื่นที่พิจารณาโดยสรุป, รายชื่อ phase ทั้งหมดพร้อมเป้าหมาย/ฟีเจอร์ที่รวม/milestone/dependency, เป็นการสร้างไฟล์ใหม่หรืออัปเดตไฟล์เดิม
- (ถ้าสโคปมี Task Breakdown) ต่อ phase แต่ละตัวในสโคป: รายการงานย่อยทั้งหมดพร้อมฟีเจอร์อ้างอิง/สถานะ/ผู้รับผิดชอบ-deadline (ถ้ามี), เป็นไฟล์ใหม่หรืออัปเดตไฟล์เดิม
- จุดใดที่เลือกให้แทนผู้ใช้ (จากขั้นตอน 3-6) พร้อมเหตุผล

จากนั้นใช้ `AskUserQuestion` ถามยืนยันเป็นขั้นสุดท้ายก่อนดำเนินการ เช่น ตัวเลือก "ยืนยัน สร้าง/อัปเดตตามแผนนี้ (Recommended)" และ "ขอปรับแผนก่อน" — ถ้าผู้ใช้เลือกขอปรับ ให้กลับไปคุยรายละเอียดที่ต้องการเปลี่ยนแล้วเสนอแผนใหม่ซ้ำจนกว่าจะได้รับการยืนยัน

### 8. มอบหมายให้ agent เขียนไฟล์จริง (เรียงลำดับเสมอ: release-plan-writer ก่อน แล้วจึงตามด้วย task-breakdown-writer ทีละ phase)

**อย่าเขียนหรือแก้ไขไฟล์ใดๆ เองใน skill นี้** เมื่อผู้ใช้ยืนยันแผนแล้วเท่านั้น ให้เรียก Agent tool ตามลำดับนี้:

1. ถ้าสโคปมี Release Plan: เรียก Agent tool โดยระบุ `subagent_type: "release-plan-writer"` พร้อมส่ง context ตามที่ agent ต้องการ (ดู "อินพุตที่คุณควรได้รับในคำสั่ง" ใน `.claude/agents/release-plan-writer.md`): วันที่ปัจจุบัน, กลยุทธ์การแบ่งที่ยืนยันแล้ว (พร้อมทางเลือกอื่นที่พิจารณา), รายชื่อ phase ทั้งหมดที่ยืนยันแล้วพร้อมรายละเอียด
2. ถ้าสโคปมี Task Breakdown: รอ `release-plan-writer` เสร็จก่อน (ถ้าทำคู่กันในรอบนี้) แล้วเรียก Agent tool โดยระบุ `subagent_type: "task-breakdown-writer"` **ทีละ phase เท่านั้น เรียงลำดับ ห้ามเรียกขนานกัน** (ทุกครั้งแก้ manifest `03-task/index.md` ไฟล์เดียวกัน) พร้อมส่ง context ตามที่ agent ต้องการ (ดู "อินพุตที่คุณควรได้รับในคำสั่ง" ใน `.claude/agents/task-breakdown-writer.md`): วันที่ปัจจุบัน, phase ที่รับผิดชอบ (เลข+ชื่อ+เป้าหมาย), รายการงานย่อยทั้งหมดของ phase นั้นที่ยืนยันแล้ว

### 9. รายงานผลกลับผู้ใช้

สรุปให้ผู้ใช้ทราบแบบกระชับ พร้อมลิงก์ไฟล์ (markdown link relative path) ไปยัง:
- `docs/01-requirements/02-plan/release-plan.md` (ถ้าทำ)
- `docs/01-requirements/03-task/{NN}-{phase-slug}.md` ทุกไฟล์ที่สร้าง/แก้ไข (ถ้าทำ)
- `docs/01-requirements/02-plan/index.md` และ `docs/01-requirements/03-task/index.md` (ถ้าอัปเดตครั้งแรก)
- ไฟล์ log ของวันนี้

ถ้าระหว่างทำงานพบว่า `feature-list.md` ยังไม่ครบหรือมีฟีเจอร์ที่ spec เปลี่ยนไปแล้วแต่ feature-list ยังไม่อัปเดต ให้ระบุไว้ในรายงานว่าควรรัน skill `feature-journey-sync` ก่อน แล้วค่อยกลับมาเรียก skill นี้ต่อเพื่อเติมส่วนที่ยังไม่ครบ

## ข้อควรจำ

- **ห้ามข้ามขั้นตอนสัมภาษณ์กลยุทธ์ (ข้อ 3, เฉพาะตอนสร้างใหม่/ทบทวน) และขั้นตอนเสนอแผนรอยืนยัน (ข้อ 7)** ไม่ว่าสโคปจะเล็กแค่ไหน หรือผู้ใช้จะเคยยืนยันแผนคล้ายกันมาก่อนในบทสนทนาเดียวกันก็ตาม
- **ทุกคำถามเลือกทางต้องมีอย่างน้อย 3 ตัวเลือกพร้อมข้อดี/ข้อเสียเสมอ** ทั้งคำถามเรื่องกลยุทธ์การแบ่ง phase, ขอบเขตของแต่ละ phase, และระดับความละเอียดของ task breakdown — ห้ามถามแบบเปิดกว้างเฉยๆ โดยไม่มีตัวเลือกให้พิจารณา
- **ห้ามเรียก `task-breakdown-writer` มากกว่า 1 ตัวพร้อมกันแบบขนาน** เรียงลำดับทีละ phase เสมอ เพราะแก้ไฟล์ manifest เดียวกันทุกครั้ง
- เนื้อหาที่คุยกับผู้ใช้และเอกสารทั้งหมดต้องเป็นภาษาไทยตาม `CLAUDE.md`
- Release Plan มีไฟล์เดียวต่อโปรเจกต์เสมอ เป็น living document — ห้ามลบ phase เดิม ให้ทำเครื่องหมายยกเลิกแทน; Task Breakdown มีไฟล์แยกต่อ phase แต่ละไฟล์ก็เป็น living document เช่นกัน — ห้ามลบแถวงานเดิม ให้เปลี่ยนสถานะเป็น "ยกเลิก" แทน
- การอ้างอิงข้ามเอกสาร `.md` ของ vault ใช้ Obsidian wikilink แบบ relative path เสมอ
- agent `release-plan-writer` และ `task-breakdown-writer` เป็นผู้เขียนไฟล์จริงทั้งหมดเท่านั้น (เอกสารหลัก, index, log) — skill นี้ทำหน้าที่สำรวจข้อมูล/สัมภาษณ์กลยุทธ์/ถามคำถาม/ยืนยันแผนเท่านั้น
