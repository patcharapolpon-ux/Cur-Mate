# ระบบยืนยันตัวตนและจัดการบทบาทผู้ใช้ (Authentication & User Role Management)

## บริบท / ที่มา

เอกสาร spec ทั้ง 4 ฉบับที่มีอยู่ก่อนหน้านี้ในระบบ Curmate อ้างถึงกลุ่มผู้ใช้งาน (actor) หลายกลุ่มโดยไม่เคยนิยามว่าผู้ใช้เหล่านี้ login/มีบัญชีผู้ใช้งานอย่างไร ได้แก่:

- **"แอดมิน"** ที่จัดการฐานความรู้เกณฑ์มาตรฐานหลักสูตรใน [[20260823-02-criteria-knowledge-base]] และเป็นผู้เพิ่มรายชื่อหลักสูตร/สำนักวิชาใน [[20260904-04-executive-curriculum-dashboard]]
- **"ผู้ใช้งานทั่วไป"** (เจ้าหน้าที่/อาจารย์ผู้จัดทำหลักสูตร) ที่อัปโหลดตรวจสอบเอกสาร มคอ.2 ใน [[20260812-01-tqf2-consistency-check]] และใช้แชทบอทให้คำแนะนำใน [[20260823-03-advisory-chatbot]]
- **"ผู้บริหาร"** ที่ดูแดชบอร์ดวิเคราะห์ข้อมูลหลักสูตรแบบ read-only ใน [[20260904-04-executive-curriculum-dashboard]] ซึ่งเอกสารดังกล่าวได้ทิ้งคำถามเปิดไว้ตรงๆ ในหัวข้อความต้องการที่ไม่ใช่เชิงฟังก์ชันและหัวข้อสมมติฐานว่า "ยังไม่มีข้อมูลเรื่อง Authentication/บัญชีผู้ใช้ของผู้บริหาร (บัญชีแยกต่างหาก หรือ SSO/ระบบเดียวกับผู้ใช้กลุ่มอื่น)" และยังไม่ยืนยันว่า "แอดมิน" ที่จัดการหลักสูตร/สำนักวิชาในฟีเจอร์นั้นเป็นแอดมินคนเดียวกับที่จัดการฐานความรู้เกณฑ์มาตรฐานหรือเป็นบทบาทย่อยแยกต่างหาก

เอกสารนี้เป็นคำตอบของคำถามเปิดทั้งสองข้อดังกล่าวโดยตรง และเป็น requirement พื้นฐาน (foundational) ที่ spec ทั้ง 4 ฉบับข้างต้นพึ่งพาอยู่แล้วโดยปริยาย จึงควรมี wikilink อ้างอิงไป-กลับกับทุกฉบับ

แนวคิดของเอกสารนี้ได้รับแรงบันดาลใจจากการที่ผู้ใช้ทดลองสร้างระบบ Firebase Authentication และระบบจัดการบทบาทผู้ใช้ (role management) ในโค้ดตัวอย่างการบ้านเรียน (`homework/curmate-mvp-v2/` — ไม่ใช่ส่วนหนึ่งของแอปพลิเคชัน Curmate จริง และไม่ได้อยู่ใน pipeline เอกสารนี้) แล้วนำแนวคิดเชิงธุรกิจที่พิสูจน์ใช้ได้จริงกลับมาเขียนใหม่เป็น requirement เชิงแนวคิดสำหรับ Curmate โดยเฉพาะ **เอกสารนี้จงใจไม่กล่าวถึงรายละเอียดทางเทคนิคใดๆ** (เช่น จะใช้ผู้ให้บริการ/ไลบรารียืนยันตัวตนใด โครงสร้างฐานข้อมูลผู้ใช้) เนื่องจากยังไม่ถึงขั้นตอนตัดสินใจ tech stack ของโปรเจกต์หลัก — รายละเอียดเหล่านั้นส่งต่อให้ขั้นตอนออกแบบเชิงเทคนิคใน [[../../02-design/02-technical/index|02-technical]]

## ความต้องการเชิงฟังก์ชัน (Functional Requirements)

1. **สมัครสมาชิกและเข้าสู่ระบบ**: ผู้ใช้ทุกคนในระบบสมัครสมาชิกด้วยอีเมลและรหัสผ่าน และสามารถเข้าสู่ระบบ/ออกจากระบบ (login/logout) ได้ด้วยบัญชีดังกล่าว
2. **ระบบบัญชีเดียวครอบคลุมผู้ใช้งานทุกกลุ่ม**: ใช้ระบบบัญชี/การเข้าสู่ระบบชุดเดียวกันครอบคลุมผู้ใช้งานทั้ง 3 กลุ่มที่ spec อื่นอ้างถึง ได้แก่ แอดมิน, ผู้ใช้งานทั่วไป (เจ้าหน้าที่/อาจารย์ผู้จัดทำหลักสูตร) และผู้บริหาร โดย**ไม่แยกระบบ SSO ต่างหากสำหรับผู้บริหาร** — บทบาท (role) เป็นเพียงคุณสมบัติหนึ่งของโปรไฟล์ผู้ใช้ที่ผูกกับบัญชี ไม่ใช่ระบบบัญชีแยกกัน ข้อนี้ตอบคำถามเปิดเรื่อง "Authentication/บัญชีผู้ใช้ของผู้บริหาร" ที่ [[20260904-04-executive-curriculum-dashboard]] ทิ้งไว้
3. **นิยาม "แอดมิน" เป็นบทบาทเดียวกันข้ามทุกฟีเจอร์**: บทบาท "แอดมิน" เป็นบทบาทเดียวกันเป๊ะ (ไม่ใช่สิทธิ์ย่อยแยกต่างหาก) ที่มีสิทธิ์สูงสุดในระบบ ครอบคลุมทั้งการจัดการฐานความรู้เกณฑ์มาตรฐานหลักสูตรตาม [[20260823-02-criteria-knowledge-base]] และการจัดการรายชื่อหลักสูตร/สำนักวิชาสำหรับแดชบอร์ดผู้บริหารตาม [[20260904-04-executive-curriculum-dashboard]] ข้อนี้ตอบคำถามเปิดที่ [[20260904-04-executive-curriculum-dashboard]] เคยตั้งไว้ว่า "แอดมินคนเดียวกันเป๊ะหรือสิทธิ์ย่อยแยกต่างหาก"
4. **การจัดการบทบาทผู้ใช้โดยแอดมิน**: แอดมิน (สิทธิ์สูงสุด) สามารถเลื่อน/ปรับบทบาทของผู้ใช้คนอื่นในระบบได้ (เช่น ปรับผู้ใช้งานทั่วไปให้เป็นแอดมิน หรือปรับบทบาทเป็นผู้บริหาร)
5. **ข้อจำกัดสำคัญ — ห้ามแก้ไขบทบาทของตัวเอง**: แอดมินไม่สามารถแก้ไขบทบาทของบัญชีตัวเองได้ ไม่ว่าจะเป็นการลดสิทธิ์ตัวเองหรือกรณีใดก็ตาม เพื่อป้องกันไม่ให้ระบบเหลือผู้ใช้ที่มีบทบาทแอดมิน 0 คนโดยไม่ตั้งใจ (เช่น แอดมินคนสุดท้ายเผลอลดสิทธิ์ตัวเองแล้วไม่มีใครกู้คืนได้)

## ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-functional Requirements)

- **การบังคับสิทธิ์ต้องทำที่ backend เสมอ**: การตรวจสอบและบังคับสิทธิ์ (authorization) ตามบทบาทของผู้ใช้ต้องทำที่ระดับ backend/ชั้นข้อมูลเสมอ ไม่ใช่การซ่อน/ปิดกั้นองค์ประกอบ (element) เพียงแค่ฝั่ง UI/client เท่านั้น เพื่อป้องกันการเรียกใช้งาน API หรือเข้าถึงข้อมูลโดยตรงแบบข้าม UI (เช่น ผู้ใช้งานทั่วไปพยายามเรียก API จัดการฐานความรู้เกณฑ์มาตรฐานโดยตรงทั้งที่ UI ไม่แสดงปุ่มให้)

## ขอบเขต

### สิ่งที่ทำ (In scope — เวอร์ชันแรก)

- สมัครสมาชิกด้วยอีเมล+รหัสผ่าน, เข้าสู่ระบบ, ออกจากระบบ
- ระบบบัญชีเดียวครอบคลุมผู้ใช้งานทั้ง 3 กลุ่ม (แอดมิน/ผู้ใช้งานทั่วไป/ผู้บริหาร) โดยบทบาทเป็นคุณสมบัติของโปรไฟล์ผู้ใช้
- แอดมินเลื่อน/ปรับบทบาทของผู้ใช้คนอื่นได้ ยกเว้นบัญชีตัวเอง
- การบังคับสิทธิ์ระดับ backend สำหรับทุกฟีเจอร์ที่มีอยู่แล้วในระบบ (การจัดการฐานความรู้เกณฑ์มาตรฐาน, การอัปโหลดตรวจสอบ มคอ.2, การจัดการหลักสูตร/สำนักวิชาสำหรับแดชบอร์ดผู้บริหาร)

### สิ่งที่ไม่ทำ (Out of scope — เวอร์ชันแรก)

- กลไกทางเทคนิคของ authentication (จะใช้ผู้ให้บริการ/ไลบรารีใด) — ส่งต่อขั้นออกแบบเชิงเทคนิคใน [[../../02-design/02-technical/index|02-technical]]
- Single Sign-On (SSO) กับระบบภายในของมหาวิทยาลัย — ยังไม่มีข้อมูลว่าโปรเจกต์ต้องการหรือไม่
- การจัดการสิทธิ์แบบละเอียดระดับ permission ย่อยต่อฟีเจอร์ (fine-grained permission) — เวอร์ชันแรกใช้ระบบบทบาท (role) แบบคงที่ตามที่ระบุในข้อ 3 ของ FR เท่านั้น

## สมมติฐาน / คำถามที่เปิดไว้

- **รายชื่อ/จำนวนบทบาททั้งหมดของระบบยังไม่ยืนยัน**: เอกสารนี้เสนอแนวทางเริ่มต้นว่าน่าจะมีอย่างน้อย 3 บทบาทตามที่ spec อื่นอ้างถึงแล้ว คือ แอดมิน, ผู้ใช้งานทั่วไป (ผู้จัดทำหลักสูตร) และผู้บริหาร แต่ยังไม่ยืนยันชื่อ/จำนวนบทบาทสุดท้าย ต้องคุยยืนยันกับผู้ใช้อีกครั้งก่อนแตกเป็น feature-list ใน [[../02-plan/index|02-plan]]
- **การสร้างบัญชีแรกของระบบ (bootstrap แอดมินคนแรก)**: ยังไม่ตัดสินใจ มีอย่างน้อย 2 แนวทางที่เป็นไปได้ ซึ่งส่งต่อให้ตัดสินใจตอนออกแบบเชิงเทคนิค:
  - (ก) ตั้งบัญชีแอดมินแรกด้วยมือผ่านเบื้องหลังระบบ/ฐานข้อมูลโดยตรง (แบบง่าย ไม่ต้องมี UI พิเศษ)
  - (ข) มี provisioning flow ที่เป็นทางการ เช่น invite-only หรือ seed script ที่รันตอน deploy ระบบครั้งแรก
- **Audit trail การเปลี่ยนบทบาท**: ยังไม่ยืนยันว่าระบบต้องบันทึกประวัติหรือไม่ว่าแอดมินคนใดเปลี่ยนบทบาทของผู้ใช้คนใด เมื่อไหร่ (เช่น log การเปลี่ยนบทบาทเพื่อตรวจสอบย้อนหลัง)
- **Password reset / Email verification**: ยังไม่ยืนยันว่าฟีเจอร์ลืมรหัสผ่าน (password reset) และการยืนยันอีเมล (email verification) จำเป็นสำหรับ MVP เวอร์ชันแรกหรือไม่ หรือเลื่อนไปเวอร์ชันถัดไป
