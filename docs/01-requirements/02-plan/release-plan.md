# Release Plan

> เอกสารนี้แบ่งฟีเจอร์จาก [[feature-list|feature-list]] ออกเป็น phase/release ตามลำดับเวลาที่จะลงมือทำ พร้อมเหตุผลของการแบ่ง แต่ละ phase จะถูกแตกเป็นงานย่อยต่อใน [[../03-task/index|03-task]]

อ้างอิงจาก [[feature-list|feature-list]] และ [[../01-spec/index|01-spec]]

## 1. กลยุทธ์การแบ่ง Phase/Release

- **แนวทางที่เลือก**: แบ่งตามลำดับความสำคัญ MoSCoW — Must have ทั้งหมดอยู่ใน Phase 1, Should have อยู่ใน Phase 2, Could have อยู่ใน Phase 3
- **เหตุผล**: [[feature-list|feature-list]] จัดลำดับความสำคัญแบบ MoSCoW ไว้ครบทุกฟีเจอร์แล้ว (Must have 6 ฟีเจอร์, Should have 2 ฟีเจอร์, Could have 1 ฟีเจอร์) การแบ่ง phase ตามลำดับนี้โดยตรงทำให้ส่งมอบคุณค่าสูงสุดก่อนโดยไม่ต้องตีความเพิ่ม อีกทั้งเมื่อตรวจสอบ dependency ทางเทคนิคจริงจาก [[../../02-design/02-technical/high-level-architecture|high-level-architecture]], [[../../02-design/02-technical/database-schema|database-schema]] และ [[../../02-design/02-technical/api-spec|api-spec]] แล้วพบว่าลำดับ MoSCoW นี้ใช้งานได้จริงโดยไม่ต้องสลับฟีเจอร์ข้ามกลุ่มความสำคัญเลย (เช่น ฟีเจอร์ 08 ซึ่งเป็น Should have ต้องพึ่งกฎเกณฑ์สถานะ approved จากฟีเจอร์ 07 ซึ่งเป็น Must have อยู่แล้วโดยธรรมชาติ ไม่มีกรณีที่ฟีเจอร์ระดับความสำคัญต่ำกว่ากลับเป็นรากฐานของฟีเจอร์ระดับสูงกว่า) จึงเป็นเหตุผลสนับสนุนที่มาจากการตรวจสอบเชิงเทคนิคจริง ไม่ใช่การทำตาม MoSCoW เฉยๆ
- **ทางเลือกอื่นที่พิจารณา**:

  | ทางเลือก | ข้อดี | ข้อเสีย | เหตุผลที่ไม่เลือก |
  | --- | --- | --- | --- |
  | แบ่งตาม dependency/ความเสี่ยงทางเทคนิคล้วนๆ | โฟกัสที่ความเป็นไปได้ทางเทคนิคและลดความเสี่ยงของโครงสร้างระบบก่อน | ต้องวิเคราะห์ dependency graph แยกต่างหากจากที่ business ให้ความสำคัญ อาจทำให้ลำดับ phase ไม่สะท้อนคุณค่าทางธุรกิจ | ผลลัพธ์ที่ได้ใกล้เคียงกับการแบ่งตาม MoSCoW อยู่แล้ว (ตรวจสอบแล้วไม่มีฟีเจอร์ใดขัดแย้งกัน) จึงเลือก MoSCoW ที่เป็นรากฐานชัดเจนกว่าและสื่อสารกับผู้มีส่วนได้ส่วนเสียง่ายกว่า |
  | แบ่งตาม user journey/persona | เห็นภาพการส่งมอบคุณค่าให้แต่ละ persona ได้ชัดเจนเป็น flow เดียวจบ | ฟีเจอร์ 02 (เลือกชุดเกณฑ์มาตรฐาน) ถูกใช้ร่วมกันในหลาย user journey (ทั้งฝั่งตรวจสอบเอกสารและฝั่งแชทบอท) ทำให้แบ่งเป็น phase ตามลำดับตัวเลขยากขึ้นและอาจต้องทำฟีเจอร์เดียวกันซ้ำในหลาย phase | ความซับซ้อนที่เพิ่มขึ้นไม่คุ้มกับประโยชน์ เมื่อเทียบกับ MoSCoW ที่จัดลำดับไว้ชัดเจนแล้ว |
  | แบ่งตามกรอบเวลาคงที่ (timeboxed) | ควบคุมกำหนดการส่งมอบได้ชัดเจน วางแผนทรัพยากรล่วงหน้าได้ | ต้องมี deadline ที่ชัดเจนมากำหนดกรอบเวลาแต่ละ phase | เป็นโปรเจกต์วิชา ไม่มี deadline ตายตัวระบุไว้ในเอกสารต้นทาง จึงไม่มีข้อมูลตั้งต้นให้กำหนดกรอบเวลาคงที่ได้ |

## 3. รายละเอียดต่อ Phase

### Phase 1: MVP: แกนหลักที่ใช้งานได้ครบวงจร — `ยังไม่เริ่ม`

**เป้าหมาย**: ให้ระบบใช้งานได้ครบ flow จริงตั้งแต่ต้นจนจบ — แอดมินสร้างฐานความรู้เกณฑ์มาตรฐานและอนุมัติกฎเกณฑ์ที่ AI สกัดมาจนมีชุดเกณฑ์สถานะ active อย่างน้อย 1 ชุด → ผู้จัดทำหลักสูตรอัปโหลดเอกสาร มคอ.2 → ยืนยันข้อมูลรายวิชาที่สกัดได้ → เลือกชุดเกณฑ์ → กดเริ่มตรวจสอบความสอดคล้องภายในเล่มเดียวกัน → ดูรายงานสรุปผลตรวจสอบ

ผู้ใช้พิจารณาแล้วว่าไม่แตก Phase นี้เป็น Phase ย่อยเพิ่ม (เช่น 1a = ฐานความรู้, 1b = flow ตรวจสอบ) เพราะทั้ง 6 ฟีเจอร์นี้ยังไม่มี business value ที่ใช้งาน/demo ได้จริงถ้าขาดตัวใดตัวหนึ่งไป

**ฟีเจอร์ที่รวมอยู่ใน phase นี้**:
- 01. อัปโหลดและจัดการไฟล์ มคอ.2 (`Must have`)
- 02. เลือกชุดเกณฑ์มาตรฐานก่อนเริ่มตรวจสอบ/สนทนา (`Must have`)
- 03. ตรวจสอบความสอดคล้องภายในเล่มเดียวกัน (`Must have`)
- 05. รายงานผลตรวจสอบ (`Must have`)
- 06. จัดการฐานความรู้เกณฑ์มาตรฐานหลักสูตร (สร้างชุดเกณฑ์ + อัปโหลดเอกสาร) (`Must have`)
- 07. ตรวจสอบ แก้ไข และอนุมัติกฎเกณฑ์ที่ AI สกัดมา (`Must have`)

**Dependency**: เป็น Phase แรก ไม่มี Phase ก่อนหน้า แต่ภายใน Phase นี้เองมีลำดับการสร้างที่บังคับ (ไม่ใช่ dependency ข้าม Phase): ต้องทำฟีเจอร์ 06 (สร้างชุดเกณฑ์) ตามด้วย 07 (อนุมัติกฎเกณฑ์จนครบ ทำให้ชุดเกณฑ์เปลี่ยนสถานะเป็น active) ให้เสร็จก่อน จึงจะทดสอบ/ใช้งาน flow ของฟีเจอร์ 02→03→05 ได้ครบจริง เนื่องจาก operation "เริ่มตรวจสอบความสอดคล้อง" (OP-03-01 ใน [[../../02-design/02-technical/api-spec|api-spec]]) มี pre-condition บังคับว่าต้องเลือกชุดเกณฑ์สถานะ active อย่างน้อย 1 ชุดเสมอ — อ้างอิงเหตุผลนี้จาก [[../../02-design/02-technical/api-spec|api-spec]] และ [[../../02-design/02-technical/database-schema|database-schema]] (ฟิลด์สถานะ pending/active ของชุดเกณฑ์)

**ช่วงเวลา/Milestone โดยประมาณ**: ยังไม่กำหนด — ไม่มี deadline ตายตัวระบุไว้ในเอกสารต้นทาง (โปรเจกต์วิชา) ใช้แค่ลำดับก่อน-หลังของ Phase

**Task Breakdown**: ยังไม่แตกเป็น task

---

### Phase 2: Next: ขยายความสามารถตรวจสอบ — `ยังไม่เริ่ม`

**เป้าหมาย**: เพิ่มความลึก/ความกว้างของความสามารถตรวจสอบความสอดคล้อง ต่อยอดจาก Consistency Checking Engine เดิมที่สร้างใน Phase 1 โดยไม่ต้องเพิ่ม actor หรือ UI/journey ใหม่ (เป็นการขยาย operation OP-03-01 เดิมให้ครอบคลุมมากขึ้น)

**ฟีเจอร์ที่รวมอยู่ใน phase นี้**:
- 04. ตรวจสอบความสอดคล้อง/ซ้ำซ้อนข้ามเล่มหลักสูตร (cross-document) (`Should have`)
- 08. ตรวจสอบเนื้อหาจริงของหลักสูตรเทียบกับเกณฑ์มาตรฐาน (`Should have`)

**Dependency**: ต้องรอ Phase 1 เสร็จสมบูรณ์ก่อน เพราะต่อยอด operation ตรวจสอบความสอดคล้องเดิม และฟีเจอร์ 08 ต้องมีกฎเกณฑ์สถานะ approved จากฟีเจอร์ 07 (Phase 1) อยู่แล้วจึงจะเทียบเนื้อหาจริงได้

**ช่วงเวลา/Milestone โดยประมาณ**: ยังไม่กำหนด ใช้แค่ลำดับถัดจาก Phase 1

**Task Breakdown**: ยังไม่แตกเป็น task

---

### Phase 3: Future: ช่องทางเสริม — `ยังไม่เริ่ม`

**เป้าหมาย**: เพิ่มช่องทางสนทนาเสริมสำหรับผู้จัดทำหลักสูตร (ตอบคำถามเกี่ยวกับเกณฑ์มาตรฐาน + ให้คำแนะนำต่อเนื้อหาร่างที่พิมพ์/วางเข้ามาแบบทันที) แยกออกจาก flow ตรวจสอบหลักอย่างชัดเจน

**ฟีเจอร์ที่รวมอยู่ใน phase นี้**:
- 09. แชทบอทให้คำแนะนำระหว่างจัดทำหลักสูตร (รวม Q&A เกณฑ์มาตรฐาน) (`Could have`)

**Dependency**: ต้องรอ Phase 1 เสร็จก่อน (ใช้ชุดเกณฑ์สถานะ active และกฎเกณฑ์สถานะ approved ชุดเดียวกันกับ Phase 1 ผ่าน operation OP-06-01/OP-06-02/OP-06-03) แต่เป็นอิสระจาก Phase 2 โดยสิ้นเชิง (ไม่ได้ใช้ผลลัพธ์จากการตรวจสอบข้ามเล่มหรือตรวจสอบเนื้อหาจริง) จึงสลับลำดับกับ Phase 2 ได้หากต้องการในอนาคต — จัดไว้เป็น Phase สุดท้ายเพราะมีระดับความสำคัญเป็น Could have ต่ำสุด และตัวเอกสาร [[../../02-design/02-technical/api-spec|api-spec]] เองยังมีคำถามเปิดหลายจุดที่ยังไม่ยืนยัน (เช่น รูปแบบผลลัพธ์/error handling ของ OP-06-02, OP-06-03) ซึ่งควรรอความชัดเจนเพิ่มก่อนนำไปพัฒนาจริง

**ช่วงเวลา/Milestone โดยประมาณ**: ยังไม่กำหนด ใช้แค่ลำดับสุดท้าย

**Task Breakdown**: ยังไม่แตกเป็น task

## สมมติฐาน / คำถามที่เปิดไว้

- ทุก Phase ยังไม่มีช่วงเวลา/milestone ที่ยืนยันจากผู้ใช้ — เนื่องจากเป็นโปรเจกต์วิชาที่ไม่มี deadline ตายตัวระบุไว้ในเอกสารต้นทาง จึงระบุ "ยังไม่กำหนด" ไว้ทั้งหมด รอข้อมูลเพิ่มเติมจากผู้ใช้หากมีกรอบเวลาจริงในภายหลัง
- ยังไม่มีการแตก Task Breakdown ให้ Phase ใดเลยในรอบนี้ (นอกสโคปของคำสั่งที่ได้รับ) — รอ agent/skill `task-breakdown-writer` ดำเนินการต่อ
- Phase 2 และ Phase 3 ไม่มี dependency ระหว่างกันเอง (อิสระต่อกัน) แต่จัดลำดับ Phase 2 ก่อน Phase 3 ตามระดับความสำคัญ MoSCoW ที่ยืนยันแล้ว (Should have มาก่อน Could have) ไม่ใช่ตาม dependency ทางเทคนิค
