# 2026-08-23

- เก็บ requirement เพิ่มเติมจากผู้ใช้เรื่อง "การอัปโหลดไฟล์ มคอ.2 เข้าสู่ระบบตรวจสอบความสอดคล้อง" ผ่าน skill `requirement-intake` — เป็นการลงรายละเอียดของ FR ข้อ 1 ที่มีอยู่แล้ว ไม่ใช่ความต้องการใหม่ที่ขยายสโคป จึงเลือก**แก้ไขเอกสารเดิม**แทนการสร้างไฟล์ใหม่
- รายละเอียดที่เพิ่มเข้าไปใน FR ข้อ 1 มี 4 ประเด็น:
  1. สิทธิ์ผู้ใช้งานที่อัปโหลดได้ จำกัดเฉพาะเจ้าหน้าที่/อาจารย์ผู้จัดทำหลักสูตรเท่านั้น
  2. อัปโหลดได้ทีละ 1 ไฟล์ต่อครั้ง (ไม่รองรับ batch upload ในเวอร์ชันแรก) โดยระบบสะสมไฟล์ที่เคยอัปโหลดไว้เพื่อตรวจสอบข้ามเล่มในภายหลัง
  3. หากอัปโหลดไฟล์ของเล่มเดิมซ้ำ ระบบแทนที่ไฟล์เดิมทันที ไม่เก็บ version history ในเวอร์ชันแรก
  4. หากไฟล์ดึงข้อความไม่ได้ (เช่น PDF สแกนภาพล้วน) ระบบแจ้งเตือนและปฏิเสธไฟล์ตั้งแต่ขั้นตอนอัปโหลด ไม่ผ่านเข้าสู่ขั้นตอนตรวจสอบ

- ประเด็นสำคัญที่ตัดสินใจไว้:
  1. จุดประสงค์ของ AI ต่อ Knowledge Base มีสองแบบ คือ (ก) ใช้ตรวจสอบเนื้อหาจริงของหลักสูตรเทียบกับเกณฑ์ (เช่น ตรวจว่าหมวดวิชาไม่เกิน 24 หน่วยกิตตามที่เกณฑ์ระบุ) และ (ข) เปิดให้ถาม-ตอบ (Q&A) เกี่ยวกับเกณฑ์มาตรฐานได้โดยตรง
  2. Knowledge Base นี้คือกลไกที่ทำให้ FR ข้อ 3 ของเอกสารเดิมเป็นจริง จึงแก้ไขเอกสารเดิมเพิ่มประโยคอ้างอิง wikilink ไปยังเอกสารใหม่ต่อท้าย FR ข้อ 3
  3. การจัดกลุ่มเป็น "ชุดเกณฑ์" (criteria set) ทำได้ยืดหยุ่น ไม่ผูกตายตัวกับปี พ.ศ./ระดับการศึกษาเพียงอย่างเดียว แต่ละชุดมี metadata กำกับ และรองรับเลือกอ้างอิงได้มากกว่า 1 ชุดต่อการตรวจสอบหนึ่งครั้ง
  4. อัปโหลดได้หลายไฟล์ต่อหนึ่งชุดเกณฑ์ สะสมเป็นคลังเอกสารของชุดนั้นเรื่อยๆ (ต่างจากฟีเจอร์อัปโหลด มคอ.2 ที่แทนที่ไฟล์เดิม)

- เก็บ requirement เพิ่มเติมจากผู้ใช้เรื่อง "ขั้นตอนการเลือกชุดเกณฑ์ก่อนเริ่มตรวจสอบเอกสาร มคอ.2" ผ่าน skill `requirement-intake` — เป็นการลงรายละเอียด flow ของสิ่งที่ระบุคร่าวๆ ไว้แล้วในทั้ง [[../01-requirements/01-spec/20260812-01-tqf2-consistency-check|20260812-01-tqf2-consistency-check]] (FR ข้อ 3) และ [[../01-requirements/01-spec/20260823-02-criteria-knowledge-base|20260823-02-criteria-knowledge-base]] (FR ข้อ 2) ไม่ใช่ความต้องการใหม่ที่ขยายสโคป จึงเลือก**แก้ไขเอกสารเดิมทั้งสองไฟล์**แทนการสร้างไฟล์ใหม่หรือ archive เอกสารใดๆ
- ประเด็นที่ยืนยันและปรับปรุงในเอกสาร:
  1. **รูปแบบการเลือก**: เลือกได้หลายชุดเกณฑ์พร้อมกัน (multi-select) ต่อการตรวจสอบหนึ่งครั้ง สอดคล้องกับที่ระบุไว้แล้วใน FR ข้อ 2 ของเอกสาร Knowledge Base
  2. **ลำดับขั้นตอน**: ผู้ใช้งานทั่วไปต้องอัปโหลดไฟล์ มคอ.2 ก่อน แล้วจึงเลือกชุดเกณฑ์ที่ต้องการอ้างอิง (ได้มากกว่า 1 ชุด) ก่อนกดเริ่มตรวจสอบ ไม่ใช่เลือกชุดเกณฑ์ก่อนแล้วค่อยอัปโหลดไฟล์
  3. **การบังคับเลือก**: ระบบบังคับให้ผู้ใช้ต้องเลือกอย่างน้อย 1 ชุดเกณฑ์ก่อนจึงจะกดเริ่มตรวจสอบได้ ไม่อนุญาตให้เริ่มตรวจสอบโดยไม่มีชุดเกณฑ์อ้างอิงเลย เพื่อป้องกันการตรวจสอบที่ไม่มีไม้บรรทัดอ้างอิงเกณฑ์มาตรฐาน
  4. รายชื่อชุดเกณฑ์ที่ให้เลือกมาจากชุดเกณฑ์ที่แอดมินสร้าง/อัปโหลดไว้แล้วในฐานความรู้ (ตาม FR ข้อ 2 ของเอกสาร Knowledge Base) เช่น "เกณฑ์ ป.ตรี 65" หรือ "เกณฑ์ ป.โท 65"
- แก้ไข [[../01-requirements/01-spec/20260812-01-tqf2-consistency-check|20260812-01-tqf2-consistency-check]]: ปรับ FR ข้อ 3 บรรทัดแรกจาก "เลือกปี พ.ศ. และระดับการศึกษา" เป็น "เลือกชุดเกณฑ์ (criteria set)" พร้อมเพิ่มรายละเอียดลำดับขั้นตอนและการบังคับเลือกเป็นข้อย่อยใหม่ในข้อเดียวกัน และปรับถ้อยคำ FR ข้อ 4 กับหัวข้อขอบเขต (in scope) ให้อ้างอิง "ชุดเกณฑ์ที่ผู้ใช้เลือกไว้" แทน "ปี พ.ศ. และระดับการศึกษา" เพื่อความสอดคล้อง
- แก้ไข [[../01-requirements/01-spec/20260823-02-criteria-knowledge-base|20260823-02-criteria-knowledge-base]]: เสริมรายละเอียด flow (อัปโหลดก่อน-เลือกทีหลัง-บังคับเลือกอย่างน้อย 1 ชุด) เข้าไปใน FR ข้อ 2 และปรับหัวข้อ "สมมติฐาน/คำถามที่เปิดไว้" โดยตัดข้อที่ว่า "ยังไม่ได้กำหนด UI/UX ของการเลือกชุดเกณฑ์หลายชุด" ออก เหลือเฉพาะส่วนที่ยังไม่ตัดสินใจจริง คือหน้าตา UI เชิงกราฟิก ส่งต่อให้ [[../02-design/01-prototypes/index|01-prototypes]] ตัดสินใจ

- เก็บ requirement เพิ่มเติมจากผู้ใช้เรื่อง "การตรวจสอบ แก้ไข และอนุมัติ (Approve) กฎเกณฑ์ที่ AI สกัดออกมา ก่อนเปิดใช้งานชุดเกณฑ์" ผ่าน skill `requirement-intake` — เป็นการเพิ่มรายละเอียดขั้นตอนแอดมินตรวจสอบ/แก้ไข/อนุมัติกฎเกณฑ์ที่ AI สกัดมาจากเอกสาร ก่อนเปิดใช้งานชุดเกณฑ์ ถือเป็นส่วนขยายตามธรรมชาติของฟีเจอร์จัดการฐานความรู้เกณฑ์มาตรฐานที่มีอยู่แล้ว ไม่ใช่ความต้องการใหม่ที่ขยายสโคปจนเอกสารเดิมล้าสมัย จึงเลือก**แก้ไขเอกสารเดิม**แทนการสร้างไฟล์ใหม่หรือ archive เอกสารใดๆ
- ประเด็นที่ยืนยันและเพิ่มเข้าไปในเอกสาร:
  1. **ระดับการ Approve**: รองรับทั้งการ Approve เป็นรายข้อกฎเกณฑ์ (ทีละข้อ) และการ Approve รวดเดียวทั้งชุดเกณฑ์ (bulk approve)
  2. **สถานะของชุดเกณฑ์**: กำหนดสถานะอย่างน้อย 2 สถานะ คือ "รอตรวจสอบ (pending)" และ "อนุมัติแล้ว/เปิดใช้งาน (active)" ชุดเกณฑ์จะเปิดใช้งานจริงได้ก็ต่อเมื่อกฎเกณฑ์ทั้งหมดที่ AI สกัดมาผ่านการอนุมัติจากแอดมินแล้วเท่านั้น
  3. **การมองเห็นของผู้ใช้งานทั่วไป**: ชุดเกณฑ์สถานะ pending จะถูกซ่อนทันทีจากรายการชุดเกณฑ์ที่ผู้ใช้งานทั่วไปเลือกได้ตอนเริ่มตรวจสอบเอกสาร มคอ.2 ผู้ใช้งานทั่วไปเห็นเฉพาะชุดเกณฑ์สถานะ active เท่านั้น
  4. **กรณีอัปโหลดเอกสารเพิ่มเข้าชุดเกณฑ์ที่ active อยู่แล้ว**: กฎเกณฑ์เดิมที่อนุมัติแล้วยังใช้งานได้ตามปกติ ไม่ถูกกระทบ ส่วนกฎเกณฑ์ใหม่ที่สกัดได้จากเอกสารที่เพิ่งอัปโหลดเพิ่มจะถูกพักไว้ในสถานะ pending รอแอดมินตรวจสอบ/อนุมัติก่อนรวมเข้ากับกฎเกณฑ์ที่ใช้งานจริงของชุดนั้น (ไม่กระทบให้ทั้งชุดกลับไปเป็น pending)
- แก้ไข [[../01-requirements/01-spec/20260823-02-criteria-knowledge-base|20260823-02-criteria-knowledge-base]]: เพิ่ม FR ใหม่ข้อ 4 "การตรวจสอบ แก้ไข และอนุมัติ (Approve) กฎเกณฑ์ที่ AI สกัดออกมา ก่อนเปิดใช้งานชุดเกณฑ์" (แทรกอยู่ในลำดับ flow อัปโหลด → AI สกัดกฎเกณฑ์ → แอดมินตรวจสอบ/อนุมัติ → เปิดใช้งาน → นำไปตรวจสอบเนื้อหาจริง โดยเลื่อน FR เดิมข้อ 4-5 เป็นข้อ 5-6) เพิ่มแนวคิดสถานะ pending/active ผูกกับ FR ข้อ 2 (การจัดกลุ่มเป็นชุดเกณฑ์) เพิ่มรายการในขอบเขต (in scope) "หน้าจอแอดมินสำหรับตรวจสอบ/แก้ไข/อนุมัติกฎเกณฑ์ที่ AI สกัดมา ก่อนเปิดใช้งานชุดเกณฑ์" และเพิ่มคำถามเปิดใหม่ 3 ข้อในหัวข้อสมมติฐาน/คำถามที่เปิดไว้ (รูปแบบโครงสร้างข้อมูลของกฎเกณฑ์, ผลของการ "ปฏิเสธ" กฎเกณฑ์, หน้าตา UI ของหน้าจอตรวจสอบ/อนุมัติ)
- แก้ไข [[../01-requirements/01-spec/20260812-01-tqf2-consistency-check|20260812-01-tqf2-consistency-check]]: เพิ่มประโยคในบรรทัด FR ข้อ 3 ระบุว่ารายชื่อชุดเกณฑ์ที่ผู้ใช้งานทั่วไปเลือกได้เป็นเฉพาะชุดเกณฑ์ที่ผ่านการอนุมัติและอยู่ในสถานะเปิดใช้งาน (active) เท่านั้น พร้อม wikilink ไปยัง [[../01-requirements/01-spec/20260823-02-criteria-knowledge-base|20260823-02-criteria-knowledge-base]]

- เก็บ requirement ใหม่จากผู้ใช้เรื่อง "ระบบแชทบอทให้คำแนะนำระหว่างจัดทำหลักสูตร (Advisory Chatbot)" ผ่าน skill `requirement-intake` — ตัดสินใจ**สร้างเอกสารใหม่**ที่ [[../01-requirements/01-spec/20260823-03-advisory-chatbot|20260823-03-advisory-chatbot]] แทนการแก้ไขเอกสารเดิม เนื่องจากเป็น use case/ช่วงเวลาการใช้งานที่ต่างจากฟีเจอร์เดิมอย่างชัดเจน (ให้คำแนะนำ**ระหว่างร่างหลักสูตร ก่อนอัปโหลดไฟล์** ต่างจากฟีเจอร์ตรวจสอบเอกสารที่ต้องอัปโหลดไฟล์เต็มเล่มก่อนตาม [[../01-requirements/01-spec/20260812-01-tqf2-consistency-check|20260812-01-tqf2-consistency-check]]) และมีความสามารถที่ลึกกว่า FR ข้อ 6 (Q&A) ที่มีอยู่แล้วในเอกสาร [[../01-requirements/01-spec/20260823-02-criteria-knowledge-base|20260823-02-criteria-knowledge-base]] มาก (รองรับการรับเนื้อหาบางส่วนที่ผู้ใช้พิมพ์/วางเข้ามาเพื่อขอ feedback แบบ real-time ไม่ใช่แค่ถาม-ตอบความรู้ทั่วไป)
- ประเด็นสำคัญที่ตัดสินใจไว้:
  1. **ความสามารถของแชทบอท**: รองรับทั้ง (ก) ตอบคำถามทั่วไปเกี่ยวกับเกณฑ์มาตรฐานในฐานความรู้ และ (ข) รับเนื้อหาร่างบางส่วนที่ผู้ใช้พิมพ์/วางเข้ามาระหว่างร่างหลักสูตร แล้วให้ AI ช่วยตรวจสอบ/ให้คำแนะนำทันที โดยไม่ต้องอัปโหลดไฟล์เต็มเล่ม
  2. **การเลือกชุดเกณฑ์**: ก่อนเริ่มสนทนา ผู้ใช้ต้องเลือกชุดเกณฑ์ (criteria set) ที่ต้องการอ้างอิงก่อน ตาม flow เดียวกับฟีเจอร์ตรวจสอบเอกสาร และแสดงเฉพาะชุดเกณฑ์ที่มีสถานะ active เท่านั้น
  3. **ขอบเขตเนื้อหาที่ตอบได้**: จำกัดเฉพาะเนื้อหาในฐานความรู้ของชุดเกณฑ์ที่เลือกไว้เท่านั้น ไม่ตอบคำถามทั่วไปนอกขอบเขตนี้
  4. **กลุ่มผู้ใช้งาน**: เป็นผู้ใช้งานทั่วไป (เจ้าหน้าที่/อาจารย์ผู้จัดทำหลักสูตร) กลุ่มเดียวกับที่ใช้ฟีเจอร์ตรวจสอบเอกสาร ไม่ใช่กลุ่มผู้ใช้งานใหม่
  5. **แยกจากขั้นตอนตรวจสอบเอกสารทั้งเล่ม**: เป็นเพียงเครื่องมือช่วยระหว่างร่าง ไม่ทดแทนขั้นตอนตรวจสอบความสอดคล้องแบบเต็มเล่มที่ต้องอัปโหลดไฟล์ ผลจากแชทบอทเป็นคำแนะนำเบื้องต้นเท่านั้น ไม่ใช่ผลตรวจสอบอย่างเป็นทางการ
