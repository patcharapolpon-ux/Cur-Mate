# Database Schema

> เอกสารนี้เป็น **conceptual data model** สื่อสารโครงสร้างข้อมูลและความสัมพันธ์ระหว่าง entity **ไม่ผูกมัดกับ DBMS/technical stack จริง** — ห้ามระบุชื่อ engine ฐานข้อมูล/syntax เฉพาะเจาะจงในเอกสารนี้ ประเภทข้อมูลที่ใช้เป็นประเภทเชิงแนวคิดเท่านั้น (ดูตารางด้านล่าง) รายละเอียดการ implement จริงให้ดูในเอกสารแยกอื่นใน [[index|02-technical]]

อ้างอิงจาก [[../../01-requirements/01-spec/index|01-spec]] (โดยเฉพาะ [[../../01-requirements/01-spec/20260812-01-tqf2-consistency-check|20260812-01-tqf2-consistency-check]], [[../../01-requirements/01-spec/20260823-02-criteria-knowledge-base|20260823-02-criteria-knowledge-base]] และ [[../../01-requirements/01-spec/20260823-03-advisory-chatbot|20260823-03-advisory-chatbot]]), [[../../01-requirements/02-plan/feature-list|feature-list]] และ [[high-level-architecture|high-level-architecture]] (หัวข้อ 5 Conceptual Data Entities)

## ประเภทข้อมูลเชิงแนวคิดที่ใช้ในเอกสารนี้

| ประเภท | ความหมาย |
| --- | --- |
| Text | ข้อความสั้น/ยาว |
| Number | จำนวนเต็มหรือทศนิยม |
| Boolean | จริง/เท็จ |
| Date/Time | วันที่และ/หรือเวลา |
| Enum | ค่าคงที่ที่กำหนดไว้ล่วงหน้า (ระบุรายการค่าที่เป็นไปได้ในคำอธิบาย) |
| Reference | อ้างอิงไปยัง entity อื่น (ใช้แทน primary/foreign key) |
| File/Media | ไฟล์แนบ/รูปภาพ/เอกสาร |

## 1. ภาพรวมโครงสร้างข้อมูล

โมเดลข้อมูลนี้ครอบคลุมทั้ง 3 spec ของโปรเจกต์ Curmate ณ ตอนนี้ (การตรวจสอบความสอดคล้องเอกสาร มคอ.2 [[../../01-requirements/01-spec/20260812-01-tqf2-consistency-check|20260812-01-tqf2-consistency-check]], ฐานความรู้เกณฑ์มาตรฐาน [[../../01-requirements/01-spec/20260823-02-criteria-knowledge-base|20260823-02-criteria-knowledge-base]] และแชทบอทให้คำแนะนำ [[../../01-requirements/01-spec/20260823-03-advisory-chatbot|20260823-03-advisory-chatbot]]) แบ่งเป็น 3 กลุ่มแนวคิดหลัก:

- **กลุ่มเอกสารหลักสูตรและการสกัด/ยืนยันข้อมูลรายวิชา** — เอกสารหลักสูตร, ข้อมูลรายวิชาที่สกัดได้, จุดที่พบข้อมูลรายวิชาในเอกสาร
- **กลุ่มฐานความรู้เกณฑ์มาตรฐาน** — ชุดเกณฑ์, เอกสารเกณฑ์มาตรฐาน, กฎเกณฑ์
- **กลุ่มผลการตรวจสอบความสอดคล้อง** — รอบตรวจสอบความสอดคล้อง, รายการจุดที่ไม่สอดคล้อง

หลักการออกแบบเชิงแนวคิดที่ยึดถือ:

- **มนุษย์ยืนยันก่อน AI นำไปใช้จริงเสมอ** สะท้อนอยู่ในโมเดลผ่านฟิลด์สถานะยืนยัน/สถานะอนุมัติของ "จุดที่พบข้อมูลรายวิชาในเอกสาร" และ "กฎเกณฑ์" ตามลำดับ
- **ทุก entity มีตัวระบุเฉพาะ (identifier) โดยนัย** สำหรับให้ entity อื่นอ้างอิงกลับผ่านฟิลด์ประเภท Reference — เอกสารนี้ไม่ระบุชื่อ/รูปแบบของตัวระบุเฉพาะนั้นตรงๆ (เช่นจะใช้รหัสอัตโนมัติหรือฟิลด์ทางธุรกิจใด) เนื่องจากเป็นรายละเอียดการ implement ที่ผูกกับ DBMS จริง ให้ตัดสินใจในเอกสารการออกแบบทางเทคนิคอื่นที่เจาะจงกว่านี้
- เอกสาร Advisory Chatbot ไม่มี entity ของตัวเองในสคีมานี้ (ดูเหตุผลในหัวข้อ "สมมติฐาน / คำถามที่เปิดไว้")
- ชื่อ entity ในเอกสารนี้อ้างอิงให้สอดคล้องกับชื่อที่ระบุไว้แล้วใน [[high-level-architecture|high-level-architecture]] หัวข้อ 5 มากที่สุด (เช่น เอกสารหลักสูตร = Course Document, ชุดเกณฑ์ = Criteria Set, เอกสารเกณฑ์มาตรฐาน = Criteria Source Document, กฎเกณฑ์ = Extracted Rule) ยกเว้น entity "ผลตรวจสอบ (Consistency Check Result)" ที่ถูกแตกรายละเอียดเพิ่มเติมเป็น 2 entity ในเอกสารนี้ (ดูหัวข้อสมมติฐาน)

## 3. รายละเอียดแต่ละ Entity

เรียงตามลำดับที่ปรากฏใน ER Diagram ข้อ 2:

### 3.1 ผู้ใช้งาน

คำอธิบาย: ตัวแทนขั้นต่ำของผู้กระทำในระบบ spec ไม่ได้ระบุระบบสมาชิก/authentication ไว้ตรงๆ แต่ระบุบทบาท "ผู้จัดทำหลักสูตร" และ "แอดมิน" ชัดเจนในหลายจุด จึงเพิ่ม entity นี้ขั้นต่ำเพื่อให้ entity อื่นอ้างอิงกลับไปยังผู้กระทำได้ (เป็นสมมติฐานที่ผู้ใช้ยืนยันแล้ว — ดูหัวข้อสมมติฐานท้ายเอกสาร)

| Field | ประเภท | บังคับ/ไม่บังคับ | คำอธิบาย |
| --- | --- | --- | --- |
| ชื่อ | Text | บังคับ | ชื่อของผู้ใช้งาน |
| บทบาท | Enum | บังคับ | ค่าที่เป็นไปได้: ผู้จัดทำหลักสูตร, แอดมิน |

ความสัมพันธ์ที่เกี่ยวข้อง:
- ผู้ใช้งาน 1 คน จัดทำเอกสารหลักสูตรได้หลายเล่ม (1-N)
- ผู้ใช้งาน (แอดมิน) 1 คน สร้างชุดเกณฑ์ได้หลายชุด (1-N)
- ผู้ใช้งาน 1 คน อัปโหลดเอกสารเกณฑ์มาตรฐานได้หลายไฟล์ (1-N)
- ผู้ใช้งาน (แอดมิน) 1 คน อนุมัติกฎเกณฑ์ได้หลายข้อ (1-N ไม่บังคับ — มีค่าเฉพาะกฎเกณฑ์ที่ผ่านการอนุมัติแล้ว)
- ผู้ใช้งาน 1 คน สั่งตรวจสอบความสอดคล้องได้หลายรอบ (1-N)

### 3.2 เอกสารหลักสูตร

คำอธิบาย: ไฟล์ มคอ.2 ล่าสุดของแต่ละหลักสูตร ไม่เก็บ version history (อัปโหลดซ้ำแทนที่ไฟล์เดิมทันที)

| Field | ประเภท | บังคับ/ไม่บังคับ | คำอธิบาย |
| --- | --- | --- | --- |
| ชื่อหลักสูตร | Text | บังคับ | ชื่อของหลักสูตรที่เอกสารนี้เป็นตัวแทน |
| ไฟล์เอกสาร (มคอ.2) | File/Media | บังคับ | ไฟล์ มคอ.2 ที่อัปโหลด (PDF/Word) |
| วันที่อัปโหลดล่าสุด | Date/Time | บังคับ | วันที่ที่ไฟล์นี้ถูกอัปโหลด/แทนที่ครั้งล่าสุด |
| ผู้จัดทำ | Reference → ผู้ใช้งาน | บังคับ | ผู้ใช้งานที่อัปโหลด/เป็นเจ้าของเอกสารหลักสูตรนี้ |

ความสัมพันธ์ที่เกี่ยวข้อง:
- ผู้ใช้งาน 1 คน จัดทำเอกสารหลักสูตรได้หลายเล่ม (1-N)
- เอกสารหลักสูตร 1 เล่ม มีข้อมูลรายวิชาที่สกัดได้หลายรายวิชา (1-N)
- เอกสารหลักสูตร 1 เล่ม ถูกสั่งตรวจสอบความสอดคล้องได้หลายรอบ (1-N)
- เอกสารหลักสูตร 1 เล่ม อาจถูกอ้างอิงเป็น "เอกสารหลักสูตรอื่นที่เกี่ยวข้อง" ในรายการจุดที่ไม่สอดคล้องได้หลายรายการ (1-N ไม่บังคับ — เฉพาะกรณีประเภทเป็นความไม่สอดคล้องข้ามเล่ม)

### 3.3 ข้อมูลรายวิชาที่สกัดได้

คำอธิบาย: ข้อมูลรายวิชาระดับสรุปต่อรายวิชาต่อเอกสาร (ค่าที่ถือเป็นทางการหลังยืนยันครบทุกจุดที่พบ)

| Field | ประเภท | บังคับ/ไม่บังคับ | คำอธิบาย |
| --- | --- | --- | --- |
| รหัสวิชา | Text | บังคับ | รหัสวิชาของรายวิชา |
| ชื่อวิชา | Text | บังคับ | ชื่อของรายวิชา |
| หน่วยกิต | Number | บังคับ | จำนวนหน่วยกิตของรายวิชา |
| คำอธิบายรายวิชา | Text | ไม่บังคับ | คำอธิบายเนื้อหารายวิชา |
| เอกสารหลักสูตรที่เกี่ยวข้อง | Reference → เอกสารหลักสูตร | บังคับ | เอกสารหลักสูตร (มคอ.2) ที่ข้อมูลรายวิชานี้สกัดมาจาก |

ความสัมพันธ์ที่เกี่ยวข้อง:
- เอกสารหลักสูตร 1 เล่ม มีข้อมูลรายวิชาที่สกัดได้หลายรายวิชา (1-N)
- ข้อมูลรายวิชาที่สกัดได้ 1 รายวิชา มีจุดที่พบข้อมูลในเอกสารได้หลายจุด (1-N)

### 3.4 จุดที่พบข้อมูลรายวิชาในเอกสาร

คำอธิบาย: แต่ละจุดที่รายวิชาเดียวกันปรากฏซ้ำในเล่ม มคอ.2 เดียวกัน พร้อมค่าที่ AI สกัดได้ ณ จุดนั้นและสถานะยืนยันเฉพาะจุด (ก่อนยืนยันค่าที่จุดต่างๆ อาจไม่ตรงกัน ซึ่งคือสิ่งที่ระบบต้องตรวจจับ)

| Field | ประเภท | บังคับ/ไม่บังคับ | คำอธิบาย |
| --- | --- | --- | --- |
| ข้อมูลรายวิชาที่สกัดได้ | Reference → ข้อมูลรายวิชาที่สกัดได้ | บังคับ | รายวิชาที่จุดนี้เป็นหนึ่งในจุดที่พบ |
| ตำแหน่ง/หน้าที่พบ | Text | บังคับ | ตำแหน่ง/หน้าในเอกสารที่พบรายวิชานี้ |
| ค่าที่สกัดได้ ณ จุดนี้ (รหัสวิชา/ชื่อ/หน่วยกิต/คำอธิบาย) | Text | บังคับ | ค่าที่ AI สกัดได้จริง ณ จุดนี้ ก่อนการยืนยัน/แก้ไข |
| สถานะยืนยัน | Enum | บังคับ | ค่าที่เป็นไปได้: รอยืนยัน, ยืนยันแล้ว |

ความสัมพันธ์ที่เกี่ยวข้อง:
- ข้อมูลรายวิชาที่สกัดได้ 1 รายวิชา มีจุดที่พบข้อมูลในเอกสารได้หลายจุด (1-N)

### 3.5 ชุดเกณฑ์

คำอธิบาย: ชุดเกณฑ์มาตรฐานหลักสูตรที่แอดมินสร้างและตั้งชื่อได้อย่างยืดหยุ่น

| Field | ประเภท | บังคับ/ไม่บังคับ | คำอธิบาย |
| --- | --- | --- | --- |
| ชื่อชุดเกณฑ์ | Text | บังคับ | ชื่อของชุดเกณฑ์ |
| ปี/ช่วงเวลาที่บังคับใช้ | Text | ไม่บังคับ | ปี/ช่วงเวลาที่ชุดเกณฑ์นี้บังคับใช้ (ยังไม่กำหนดโครงสร้างตายตัว — ดูหัวข้อสมมติฐาน) |
| ระดับการศึกษา | Text | ไม่บังคับ | ระดับการศึกษาที่ชุดเกณฑ์นี้ครอบคลุม (ยังไม่กำหนดโครงสร้างตายตัว — ดูหัวข้อสมมติฐาน) |
| ขอบเขต/สาขา | Text | ไม่บังคับ | ขอบเขต/สาขาที่ชุดเกณฑ์นี้ครอบคลุม |
| สถานะ | Enum | บังคับ | ค่าที่เป็นไปได้: รอตรวจสอบ (pending), เปิดใช้งาน (active) |
| ผู้สร้าง | Reference → ผู้ใช้งาน | บังคับ | ผู้ใช้งาน (แอดมิน) ที่สร้างชุดเกณฑ์นี้ |

ความสัมพันธ์ที่เกี่ยวข้อง:
- ผู้ใช้งาน (แอดมิน) 1 คน สร้างชุดเกณฑ์ได้หลายชุด (1-N)
- ชุดเกณฑ์ 1 ชุด มีเอกสารเกณฑ์มาตรฐานได้หลายไฟล์ (1-N)
- ชุดเกณฑ์กับรอบตรวจสอบความสอดคล้องเป็นความสัมพันธ์ N-N (หนึ่งรอบตรวจสอบเลือกอ้างอิงได้หลายชุดเกณฑ์พร้อมกัน, ชุดเกณฑ์หนึ่งชุดถูกใช้ในหลายรอบตรวจสอบได้)

### 3.6 เอกสารเกณฑ์มาตรฐาน

คำอธิบาย: ไฟล์เกณฑ์ที่แอดมินอัปโหลดเข้าชุดเกณฑ์ สะสมได้หลายไฟล์ต่อชุด

| Field | ประเภท | บังคับ/ไม่บังคับ | คำอธิบาย |
| --- | --- | --- | --- |
| ไฟล์เอกสาร | File/Media | บังคับ | ไฟล์เกณฑ์มาตรฐานที่อัปโหลด (PDF/Word) |
| วันที่อัปโหลด | Date/Time | บังคับ | วันที่ที่ไฟล์นี้ถูกอัปโหลด |
| ชุดเกณฑ์ที่สังกัด | Reference → ชุดเกณฑ์ | บังคับ | ชุดเกณฑ์ที่เอกสารนี้ถูกอัปโหลดเข้าไป |
| ผู้อัปโหลด | Reference → ผู้ใช้งาน | บังคับ | ผู้ใช้งานที่อัปโหลดเอกสารนี้ |

ความสัมพันธ์ที่เกี่ยวข้อง:
- ชุดเกณฑ์ 1 ชุด มีเอกสารเกณฑ์มาตรฐานได้หลายไฟล์ (1-N)
- ผู้ใช้งาน 1 คน อัปโหลดเอกสารเกณฑ์มาตรฐานได้หลายไฟล์ (1-N)
- เอกสารเกณฑ์มาตรฐาน 1 ไฟล์ สกัดกฎเกณฑ์ได้หลายข้อ (1-N)

### 3.7 กฎเกณฑ์

คำอธิบาย: กฎที่ AI สกัดจากเอกสารเกณฑ์มาตรฐานโดยอัตโนมัติ ต้องผ่านการอนุมัติจากแอดมินก่อนใช้งานจริง ชุดเกณฑ์ของกฎเกณฑ์หนึ่งข้อสืบทอดได้ผ่านเอกสารต้นทาง → ชุดเกณฑ์ที่สังกัด (ไม่มี Reference ตรงไปยังชุดเกณฑ์ซ้ำซ้อน)

| Field | ประเภท | บังคับ/ไม่บังคับ | คำอธิบาย |
| --- | --- | --- | --- |
| เนื้อหากฎเกณฑ์ | Text | บังคับ | เนื้อหาของกฎเกณฑ์ที่สกัดได้ |
| เอกสารต้นทาง | Reference → เอกสารเกณฑ์มาตรฐาน | บังคับ | เอกสารเกณฑ์มาตรฐานที่กฎเกณฑ์นี้ถูกสกัดมาจาก |
| สถานะ | Enum | บังคับ | ค่าที่เป็นไปได้: รอตรวจสอบ (pending), อนุมัติแล้ว (approved) |
| ผู้อนุมัติ | Reference → ผู้ใช้งาน | ไม่บังคับ | ผู้ใช้งาน (แอดมิน) ที่อนุมัติกฎเกณฑ์นี้ มีค่าเมื่อสถานะเป็น approved เท่านั้น |

ความสัมพันธ์ที่เกี่ยวข้อง:
- เอกสารเกณฑ์มาตรฐาน 1 ไฟล์ สกัดกฎเกณฑ์ได้หลายข้อ (1-N)
- ผู้ใช้งาน (แอดมิน) 1 คน อนุมัติกฎเกณฑ์ได้หลายข้อ (1-N ไม่บังคับ)

### 3.8 รอบตรวจสอบความสอดคล้อง

คำอธิบาย: หนึ่งครั้งของการกดเริ่มตรวจสอบเอกสารหลักสูตรหนึ่งเล่มเทียบกับชุดเกณฑ์ที่เลือก

| Field | ประเภท | บังคับ/ไม่บังคับ | คำอธิบาย |
| --- | --- | --- | --- |
| วันที่ตรวจสอบ | Date/Time | บังคับ | วันที่/เวลาที่สั่งเริ่มตรวจสอบ |
| เอกสารหลักสูตรที่ตรวจสอบ | Reference → เอกสารหลักสูตร | บังคับ | เอกสารหลักสูตรที่ถูกตรวจสอบในรอบนี้ |
| ผู้สั่งตรวจสอบ | Reference → ผู้ใช้งาน | บังคับ | ผู้ใช้งานที่กดเริ่มตรวจสอบรอบนี้ |

ความสัมพันธ์ที่เกี่ยวข้อง:
- เอกสารหลักสูตร 1 เล่ม ถูกสั่งตรวจสอบได้หลายรอบ (1-N)
- ผู้ใช้งาน 1 คน สั่งตรวจสอบได้หลายรอบ (1-N)
- ชุดเกณฑ์กับรอบตรวจสอบความสอดคล้องเป็นความสัมพันธ์ N-N (หนึ่งรอบตรวจสอบเลือกอ้างอิงได้หลายชุดเกณฑ์พร้อมกัน ตามที่ spec บังคับให้เลือกได้มากกว่า 1 ชุด, ชุดเกณฑ์หนึ่งชุดถูกใช้ในหลายรอบตรวจสอบได้)
- รอบตรวจสอบความสอดคล้อง 1 รอบ มีรายการจุดที่ไม่สอดคล้องได้หลายรายการ (1-N)

### 3.9 รายการจุดที่ไม่สอดคล้อง

คำอธิบาย: รายการย่อยของสิ่งที่ตรวจพบว่าไม่สอดคล้องกันในรอบตรวจสอบหนึ่งรอบ (ทั้งภายในเล่ม ข้ามเล่ม และเทียบกับเกณฑ์) — สอดคล้องกับสิ่งที่ [[high-level-architecture|high-level-architecture]] เรียกว่า Finding ภายใน entity "ผลตรวจสอบ (Consistency Check Result)"

| Field | ประเภท | บังคับ/ไม่บังคับ | คำอธิบาย |
| --- | --- | --- | --- |
| ประเภท | Enum | บังคับ | ค่าที่เป็นไปได้: ไม่สอดคล้องภายในเล่ม, ซ้ำซ้อน/ไม่สอดคล้องข้ามเล่ม, ไม่ตรงกับเกณฑ์มาตรฐาน |
| คำอธิบายจุดที่ไม่สอดคล้อง | Text | บังคับ | คำอธิบายรายละเอียดของจุดที่ตรวจพบว่าไม่สอดคล้อง |
| ตำแหน่ง/หน้าที่พบ | Text | บังคับ | ตำแหน่ง/หน้าในเอกสารที่พบจุดไม่สอดคล้องนี้ |
| รอบตรวจสอบที่เกี่ยวข้อง | Reference → รอบตรวจสอบความสอดคล้อง | บังคับ | รอบตรวจสอบที่รายการนี้เป็นผลลัพธ์มาจาก |
| เอกสารหลักสูตรอื่นที่เกี่ยวข้อง | Reference → เอกสารหลักสูตร | ไม่บังคับ | เอกสารหลักสูตรอีกเล่มที่ถูกเทียบด้วย มีค่าเฉพาะกรณีประเภทเป็น "ซ้ำซ้อน/ไม่สอดคล้องข้ามเล่ม" |

ความสัมพันธ์ที่เกี่ยวข้อง:
- รอบตรวจสอบความสอดคล้อง 1 รอบ มีรายการจุดที่ไม่สอดคล้องได้หลายรายการ (1-N)
- เอกสารหลักสูตร 1 เล่ม อาจถูกอ้างอิงเป็นเล่มที่เทียบด้วยในรายการจุดที่ไม่สอดคล้องได้หลายรายการ (1-N ไม่บังคับ)

## สมมติฐาน / คำถามที่เปิดไว้

- เอกสาร Advisory Chatbot (การสนทนา/คำถาม-คำตอบ) ไม่มี entity ในสคีมานี้ เนื่องจาก spec [[../../01-requirements/01-spec/20260823-03-advisory-chatbot|20260823-03-advisory-chatbot]] ระบุชัดเจนว่าไม่บันทึกเนื้อหาสนทนาเป็นส่วนหนึ่งของฐานความรู้ถาวร
- entity "ผู้ใช้งาน" เป็นสมมติฐานขั้นต่ำที่เพิ่มเข้ามาเพื่อรองรับ traceability ("ใครกระทำ") เนื่องจาก spec ไม่ได้ระบุระบบสมาชิก/authentication ไว้โดยตรง รอการยืนยัน/ขยายรายละเอียดเพิ่มเติมตอนออกแบบระบบสมาชิกจริง
- ฟิลด์ "ปี/ช่วงเวลาที่บังคับใช้" และ "ระดับการศึกษา" ของชุดเกณฑ์ ยังไม่ได้กำหนดว่าเป็นรายการค่าคงที่ (Enum) หรือข้อความอิสระ — เลือกเป็น Text ไปก่อนเนื่องจาก spec ระบุว่า "ไม่ผูกตายตัวกับโครงสร้างปี พ.ศ./ระดับการศึกษาเพียงอย่างเดียว"
- ตัวระบุเฉพาะ (identifier) ของแต่ละ entity เป็นสิ่งที่มีอยู่โดยนัยเท่านั้น (เพื่อให้ Reference field อ้างอิงได้) เอกสารนี้ยังไม่กำหนดชื่อ/รูปแบบของตัวระบุเฉพาะจริง เนื่องจากเป็นรายละเอียดการ implement ที่ผูกกับ DBMS/technology ซึ่งไม่ใช่ขอบเขตของ conceptual data model ฉบับนี้
- entity "รอบตรวจสอบความสอดคล้อง" และ "รายการจุดที่ไม่สอดคล้อง" ในเอกสารนี้ เป็นการแตกรายละเอียดเพิ่มเติมจาก entity เดียว "ผลตรวจสอบ (Consistency Check Result)" ที่เคยระบุไว้ใน [[high-level-architecture|high-level-architecture]] หัวข้อ 5 ให้ชัดเจนขึ้นในระดับ conceptual data model (แยกความหมายของ "หนึ่งครั้งของการกดตรวจสอบ" ออกจาก "รายการย่อยที่พบว่าไม่สอดคล้อง" ซึ่งมีได้หลายรายการต่อหนึ่งรอบ) — ไม่ใช่การขัดแย้งกับ high-level-architecture
