# Prototype v1 — 2026-08-23

## สโคป

ครอบคลุม user journey "[[../20260823-01-user-journey-course-coordinator-upload|ผู้จัดทำหลักสูตร อัปโหลดและตรวจสอบเอกสาร มคอ.2]]" ทั้ง flow ตั้งแต่อัปโหลดไฟล์ มคอ.2 → เลือกชุดเกณฑ์มาตรฐาน → ตรวจสอบความสอดคล้อง (ภายในเล่ม + ข้ามเล่ม) → ดูรายงานผลตรวจสอบ ตรงกับฟีเจอร์ใน [[../../../01-requirements/02-plan/feature-list|feature-list]] ดังนี้:

- 01. อัปโหลดและจัดการไฟล์ มคอ.2 (`Must have`)
- 02. เลือกชุดเกณฑ์มาตรฐานก่อนเริ่มตรวจสอบ/สนทนา (`Must have`)
- 03. ตรวจสอบความสอดคล้องภายในเล่มเดียวกัน (`Must have`)
- 04. ตรวจสอบความสอดคล้อง/ซ้ำซ้อนข้ามเล่มหลักสูตร (cross-document) (`Should have`)
- 05. รายงานผลตรวจสอบ (`Must have`)

Requirement ต้นทาง: [[../../../01-requirements/01-spec/20260812-01-tqf2-consistency-check|ระบบตรวจสอบความสอดคล้องของเอกสารรายละเอียดหลักสูตร (มคอ.2)]]

เวอร์ชันนี้เป็น prototype แบบ **interactive จิ้มเล่นได้จริง** — ทุกหน้ามี vanilla JavaScript inline ให้คลิก/โต้ตอบได้จริง (จำลองอัปโหลด, toggle เลือกชุดเกณฑ์, จำลองสถานะการตรวจสอบ, กรอง/ขยายรายการรายงานผล) และเชื่อมโยงกันด้วยลิงก์ระหว่างไฟล์ .html ให้เดินหน้า-ถอยหลังได้จริงในเบราว์เซอร์ ทุกหน้ามี stepper bar เดียวกัน 4 ขั้น (อัปโหลด → เลือกชุดเกณฑ์ → ตรวจสอบ → รายงานผล)

เพิ่มเติม (2026-08-24): ขยายสโคปให้ครอบคลุมฝั่ง **แอดมิน** ตาม journey "[[../20260823-03-user-journey-admin-manage-criteria-knowledge-base|แอดมิน จัดการฐานความรู้เกณฑ์มาตรฐานหลักสูตร]]" เฉพาะฟีเจอร์ 06 และ 07 (ไม่รวมฟีเจอร์ 08 เนื่องจากเป็นพฤติกรรมระบบที่ integrate อยู่ในหน้า 03-processing.html/04-report.html เดิมแล้ว ไม่ใช่หน้าจอฝั่งแอดมินใหม่):

- 06. จัดการฐานความรู้เกณฑ์มาตรฐานหลักสูตร (สร้างชุดเกณฑ์ + อัปโหลดเอกสาร) (`Must have`)
- 07. ตรวจสอบ แก้ไข และอนุมัติกฎเกณฑ์ที่ AI สกัดมา (`Must have`)

Requirement ต้นทางของส่วนที่เพิ่ม: [[../../../01-requirements/01-spec/20260823-02-criteria-knowledge-base|ระบบจัดการฐานความรู้เกณฑ์มาตรฐานหลักสูตร (Knowledge Base) สำหรับแอดมิน]]

หน้าจอฝั่งแอดมิน (05-07) ใช้ breadcrumb + admin zone badge แทน stepper 4 ขั้นของฝั่งผู้ใช้งานทั่วไป เพื่อสื่อว่าเป็นคนละบทบาท คนละ flow กัน

เพิ่มเติม (2026-09-01): ขยายสโคปให้ครอบคลุม journey "[[../20260823-02-user-journey-course-coordinator-chatbot-advisory|ผู้จัดทำหลักสูตร ขอคำแนะนำระหว่างร่างหลักสูตรผ่านแชทบอท]]" (ฟีเจอร์ 09) ที่ยังไม่เคยมี prototype มาก่อน ด้วยหน้าจอใหม่ 08-09 (เลือกชุดเกณฑ์ → สนทนากับแชทบอท) และปรับปรุงหน้า 01/02/03 ให้ตรงกับ [[../../../01-requirements/01-spec/20260812-01-tqf2-consistency-check|tqf2-consistency-check]] ที่อัปเดตเมื่อ 2026-08-31 (เพิ่มขั้นตอนตรวจสอบความสมบูรณ์ของเอกสารเทียบสารบัญ TOC, สกัดข้อมูลรายวิชาให้ผู้ใช้ตรวจสอบ/ยืนยัน ในหน้าใหม่ 01b, และเพิ่มการ์ดแสดงผลตรวจจับประเภทหลักสูตรในหน้า 03) หน้าจอใหม่ 08-09 ใช้ breadcrumb แบบเดียวกับหน้า 05-07 (ไม่ใช่ stepper 4 ขั้นของฝั่งอัปโหลดเอกสาร) เพราะเป็นคนละ flow

## สมมติฐาน / คำถามที่เปิดไว้

- ชื่อไฟล์ตัวอย่าง มคอ.2, ชื่อชุดเกณฑ์ตัวอย่าง 4 ชุด, และรายการจุดไม่สอดคล้อง 4 ตัวอย่างในหน้ารายงานผล เป็นข้อมูลจำลอง (mock data) ที่คิดขึ้นเพื่อสาธิต UI เท่านั้น ไม่ใช่ข้อมูลจริง
- หน้า "กำลังตรวจสอบ" จำลองการเปลี่ยนสถานะทันทีต่อการคลิกปุ่ม "จำลองตรวจสอบ" โดยไม่มี delay/animation จริง เนื่องจากยังไม่มีข้อมูล performance จริงของระบบ (ตามคำถามเปิดใน [[../../../01-requirements/01-spec/20260812-01-tqf2-consistency-check|tqf2-consistency-check]] หัวข้อ NFR)
- ครอบคลุม journey "[[../20260823-03-user-journey-admin-manage-criteria-knowledge-base|จัดการฐานความรู้เกณฑ์มาตรฐานของแอดมิน]]" แล้วในหน้า 05-07 (เพิ่มเมื่อ 2026-08-24) เฉพาะฟีเจอร์ 06 และ 07 — ครอบคลุม journey "[[../20260823-02-user-journey-course-coordinator-chatbot-advisory|แชทบอทให้คำแนะนำ]]" แล้วเช่นกัน (เพิ่มเมื่อ 2026-09-01) ด้วยหน้าจอ 08 (เลือกชุดเกณฑ์) และ 09 (สนทนากับแชทบอท)
- รายชื่อชุดเกณฑ์ตัวอย่างในหน้า 05 (dashboard), ชื่อกฎเกณฑ์ตัวอย่าง 5 ข้อในหน้า 07, และชื่อเอกสารตัวอย่างที่อัปโหลดในหน้า 06 เป็นข้อมูลจำลอง (mock data) เพื่อสาธิต UI เท่านั้น ไม่ใช่ข้อมูลจริง
- ปุ่ม "ปฏิเสธ (Reject)" ในหน้า 07 แสดงเป็นตัวอย่างต้นแบบ (คลิกแล้วแสดงข้อความอธิบายเท่านั้น ไม่มีผลลัพธ์จริง) เนื่องจาก spec ต้นทาง [[../../../01-requirements/01-spec/20260823-02-criteria-knowledge-base|criteria-knowledge-base]] ยังเปิดคำถามไว้ว่าการปฏิเสธกฎเกณฑ์ควรมีผลลัพธ์อย่างไร — รอการตัดสินใจเพิ่มเติมก่อนออกแบบ interaction จริง (ปรับปรุงแล้ว 2026-09-12 — ทำงานจริงแล้ว ดูหัวข้อเพิ่มเติมด้านบน)
- หน้า 06 จำลองการ "สกัดกฎเกณฑ์ด้วย AI" ด้วย toast + delay สั้น (700ms) ก่อนพาไปหน้า 07 เพื่อสื่อสารว่าเป็นกระบวนการที่ต้องใช้เวลาจริงในระบบจริง โดยไม่ผูกกับตัวเลข performance จริงใดๆ (ยังไม่มีข้อมูล NFR ของเวลาสกัดกฎเกณฑ์)
- หน้า 01b: ข้อความ banner แจ้งเตือน TOC ไม่ครบ ("ภาคผนวก ค: ตารางเปรียบเทียบหลักสูตร") และตารางข้อมูลรายวิชาที่สกัดได้ 5 แถว (รวมแถวสถานะ "โปรดตรวจสอบ" 1 แถว) เป็นข้อมูลจำลอง (mock data) เพื่อสาธิต UI เท่านั้น ไม่ใช่ผลลัพธ์จากการสกัดข้อมูลจริง
- หน้า 03: การ์ด "ตรวจพบประเภทหลักสูตร" แสดงข้อความตัวอย่างคงที่ (หลักสูตรปรับปรุง พ.ศ. 2569 จากหลักสูตรวิศวกรรมคอมพิวเตอร์ พ.ศ. 2564) เป็น mock data ไม่ได้ผูกกับผลตรวจจับจริงจากไฟล์ที่อัปโหลดในหน้า 01
- หน้า 08-09: ชื่อชุดเกณฑ์ที่ให้เลือก/ปักหมุดในหน้าสนทนา, เนื้อหาบทสนทนาตัวอย่างทั้ง 2 คู่ (คำถามทั่วไปและเนื้อหาร่าง), และคำตอบ AI ที่คำตอบวนใช้เมื่อผู้ใช้พิมพ์ข้อความใหม่ (mockReplies 3 แบบ) เป็นข้อมูลจำลองเพื่อสาธิต UI เท่านั้น ไม่ได้เชื่อมกับฐานความรู้เกณฑ์มาตรฐานจริงหรือโมเดล AI จริงแต่อย่างใด
- ป้ายระดับความมั่นใจ (มั่นใจสูง/กลาง/ต่ำ) และการอ้างอิงข้อกฎ/ข้อเกณฑ์รายข้อในหน้า 09 เป็นตัวอย่างสาธิตรูปแบบการแสดงผลเท่านั้น ยังไม่ผูกกับวิธีคำนวณ/ประเมินความมั่นใจจากโมเดล AI จริง ตามคำถามเปิดในสเปกต้นทาง [[../../../01-requirements/01-spec/20260823-03-advisory-chatbot|advisory-chatbot]]
- ปุ่ม "ไม่เห็นด้วยกับคำตอบนี้" ในหน้า 09 คลิกแล้วแสดงข้อความยืนยันในหน้าเดียวกันทันที (mock บันทึก log) ไม่มีการเชื่อมต่อ backend จริงและไม่มีหน้าจอสรุปภาพรวมสำหรับแอดมินในเวอร์ชันนี้
- ครอบคลุมฟีเจอร์ 12 "สมัครสมาชิกและเข้าสู่ระบบ" และ 13 "แอดมินจัดการบทบาทผู้ใช้" แล้วในหน้า 10-12 (เพิ่มเมื่อ 2026-09-12)
- หน้า 10 (เข้าสู่ระบบ): การ "เข้าสู่ระบบสำเร็จ" ในหน้าต้นแบบนี้จำลองแบบง่ายมาก — ตรวจแค่ว่ากรอกอีเมล/รหัสผ่านครบ (ไม่ตรวจสอบความถูกต้องจริง) แล้ว redirect ไปหน้า 05 (แอดมิน) เสมอ ไม่ได้แยกปลายทางตามบทบาทจริงของผู้ใช้ตามที่ journey [[../20260912-06-user-journey-signup-login|signup-login]] อธิบายไว้ (เช่น ผู้ใช้งานทั่วไปควรไปหน้าอัปโหลด มคอ.2, ผู้บริหารควรไปหน้าแดชบอร์ด) เนื่องจากยังไม่มีระบบยืนยันตัวตน/บทบาทจริงเบื้องหลัง
- หน้า 12 (จัดการผู้ใช้งานและบทบาท): รายชื่อผู้ใช้ 5 คนเป็นข้อมูลจำลอง (mock data) การเปลี่ยนบทบาทผ่าน dropdown อัปเดตเฉพาะฝั่งหน้าจอทันทีเพื่อสาธิต UI เท่านั้น ไม่ได้เชื่อมต่อการตรวจสอบสิทธิ์ที่ backend จริงตามที่ NFR ของ [[../../../01-requirements/01-spec/20260912-05-authentication-user-roles|authentication-user-roles]] กำหนดไว้ — แถวบัญชีตนเอง (สมมติเป็น "สุดา คุณวุฒิ") ถูกล็อกไม่ให้แก้ไขบทบาทตามที่ FR ข้อ 5 กำหนด
- หน้า 05/07 (อัปเดต 2026-09-12): ปุ่ม "ลบชุดเกณฑ์นี้" (หน้า 05) และ "ลบ" ต่อกฎเกณฑ์ย่อยแต่ละข้อ (หน้า 07) เป็นการจำลอง (mock) การลบแบบ cascade/รายข้อในฝั่งหน้าจอเท่านั้น ไม่มีการลบข้อมูลจริง — ปุ่ม "เปิดใช้งานชุดเกณฑ์นี้" ในหน้า 07 เปลี่ยนจากการ auto-activate ทันทีที่อนุมัติครบ (แบบเดิม) เป็นการให้แอดมินกดยืนยันเองเมื่อกฎเกณฑ์ทุกข้อถูกตรวจแล้ว (อนุมัติหรือไม่อนุมัติครบ) เพื่อให้สอดคล้องกับกรณีที่มีกฎเกณฑ์ถูกปฏิเสธปนอยู่ด้วย
- หน้า 10-11: banner แจ้งเตือน/ข้อผิดพลาดภายในการ์ดฟอร์ม (เช่น "อีเมลหรือรหัสผ่านไม่ถูกต้อง") ใช้ border-radius แบบ Medium (8px) แทนที่จะเป็น radius 0 แบบ "Banner แจ้งเตือนเต็มความกว้าง" ที่ DESIGN.md ระบุไว้สำหรับ banner ระดับหน้าเพจ เนื่องจาก banner ในหน้านี้อยู่ภายในการ์ดฟอร์มที่มีขอบมนอยู่แล้ว ไม่ใช่ banner เต็มความกว้างของหน้าจอ — เป็นการตีความที่สมเหตุสมผลตามบริบท ไม่ใช่ค่าที่ DESIGN.md ระบุไว้ตรงๆ
- (อัปเดต 2026-09-12) ซ่อมช่องว่างที่ agent `test-case-writer` ตรวจพบระหว่างเขียน Acceptance Criteria/Test Case ของฟีเจอร์ 12-13: (1) หน้า 11 (สมัครสมาชิก) เพิ่มการตรวจสอบรูปแบบอีเมลอย่างง่าย (ต้องมี @ และมีข้อความก่อน/หลัง + โดเมน) ก่อน submit ตาม AC-12-04/TC-12-004/TC-12-005 — แสดง error message สีแดงใต้ช่องอีเมลตามสไตล์ error ของ Text Input ใน DESIGN.md โดยไม่ submit ฟอร์ม (2) เพิ่มปุ่ม "ออกจากระบบ" ข้าง admin zone badge ในหน้า 05, 06, 07 และ 12 ตาม AC-12-05/TC-12-006 คลิกแล้วจำลอง redirect ไปหน้า 10 (`10-login.html`) เป็นลิงก์ธรรมดา ยังไม่มีการจบ session จริงฝั่ง backend
