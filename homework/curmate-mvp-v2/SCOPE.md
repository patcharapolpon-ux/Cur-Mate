## สิ่งที่ต่อ Firestore จริงแล้ว (ต่างจาก prototype ต้นฉบับที่เป็น mock ล้วน)

- **05**: อ่านรายการ `criteriaSets` จริงจาก Firestore มาแสดงเป็นการ์ด แทนการ hardcode 5 การ์ดตัวอย่าง การ์ดคลิกได้ทุกสถานะ (pending พาไปตรวจ/อนุมัติ, active พาไปดู/แก้ไขอีกครั้งที่หน้า 07 — ปรับเมื่อ 2026-09-06 เดิม active คลิกไม่ได้เลย)
- **06**: กดปุ่ม "บันทึกและสกัดกฎเกณฑ์" จะเขียนเอกสารใหม่ลง `criteriaSets` จริง (status: `pending`) ก่อนพากลับไปหน้ารายการ (05) (เดิมพาไปหน้า 07 โดยตรง — เปลี่ยนเมื่อ 2026-09-06 เพราะหน้า 07 ไม่มี `rules` ให้ตรวจจนกว่าจะ seed เพิ่มเอง)
- **07**: อ่านค่าจาก URL query string `?setId=...` เพื่อดึง `rules` เฉพาะของชุดเกณฑ์นั้นจาก Firestore ปุ่ม "อนุมัติ", "ไม่อนุมัติ" (เพิ่มเมื่อ 2026-09-06) และ "อนุมัติทั้งหมด" เขียนสถานะจริงกลับไปที่ `rules/{id}` (แก้เฉพาะ field `status` เป็น `approved`/`rejected` เท่านั้น ไม่แตะ field อื่น) พร้อมเพิ่มแถวใน `rules/{id}/reviewLog` ทุกครั้ง
- **07 → เปิดใช้งานชุดเกณฑ์ (เพิ่มเมื่อ 2026-09-06)**: เมื่อกฎเกณฑ์ย่อยทุกข้อในชุดถูกตรวจแล้ว (อนุมัติหรือไม่อนุมัติครบ ไม่จำเป็นต้องอนุมัติทั้งหมด) จะมีปุ่ม "เปิดใช้งานชุดเกณฑ์นี้" ปรากฏขึ้น กดแล้วเขียน `criteriaSets/{setId}` (แก้เฉพาะ field `status` เป็น `active`) จริงที่ Firestore — หน้า 05 จะอ่านค่านี้ตรงๆ ตอนโหลดหน้า (badge สถานะที่หัวหน้า 07 เองก็อ่านค่าจริงจาก `criteriaSets.status` เท่านั้น ไม่คำนวณเดาจากจำนวนการ์ดที่ตรวจแล้วอีกต่อไป — เดิมเป็นบั๊กที่ badge ขึ้น "เปิดใช้งาน" แต่ไม่เขียนกลับ Firestore จริง)
- **07 → แก้ไขชุดเกณฑ์หลังเปิดใช้งานแล้ว (เพิ่มเมื่อ 2026-09-06)**: ตอนสถานะเป็น "เปิดใช้งาน" จะมีปุ่ม "แก้ไขชุดเกณฑ์นี้อีกครั้ง" (มี `confirm()` ถามยืนยันก่อน) กดแล้วเขียน `criteriaSets/{setId}.status` กลับเป็น `pending` — เมื่อไม่ใช่ `active` แล้ว กฎเกณฑ์ย่อยแต่ละข้อที่เคยอนุมัติ/ไม่อนุมัติไปแล้วจะมีปุ่ม "แก้ไข" ปรากฏข้างป้ายสถานะ กดแล้วเลือกอนุมัติ/ไม่อนุมัติใหม่ได้ (สลับ approved ↔ rejected ได้ เขียนกลับ Firestore + เพิ่มแถว `reviewLog` ทุกครั้งเหมือนการตัดสินใจครั้งแรก) — ถ้าชุดเกณฑ์ยังเป็น `active` อยู่ ปุ่ม "แก้ไข" นี้จะไม่ปรากฏ (ล็อกไว้)
- **บั๊ก (แก้แล้วเมื่อ 2026-09-06)**: ปุ่ม "เปิดใช้งานชุดเกณฑ์นี้" ไม่หายไปจาก banner ตอนโหลดหน้าใหม่ทั้งที่ set เป็น `active` แล้ว (เห็นทั้งปุ่ม "เปิดใช้งาน..." และ "กลับไปหน้ารายการ" พร้อมกัน) — สาเหตุคือ CSS ของ `.btn { display: inline-flex }` ทับ default ของ attribute `hidden` ทำให้ `.hidden = true` ทาง JS ไม่มีผล แก้โดยเพิ่ม `[hidden] { display: none !important; }` ในหน้า 07
- **05 → ลบชุดเกณฑ์ (เพิ่มเมื่อ 2026-09-06)**: ทุกการ์ดมีปุ่ม "ลบชุดเกณฑ์นี้" กด `confirm()` ถามยืนยันก่อนทุกครั้ง (ยกเลิกแล้วไม่ลบ) ยืนยันแล้วลบ `criteriaSets/{id}` จริงพร้อม**ลบพ่วง (cascade)** `rules` ทุกข้อของชุดนั้นและ `reviewLog` ใต้แต่ละข้อด้วย กันไม่ให้มีข้อมูลค้างอ้างอิง `criteriaSetId` ที่ไม่มีอยู่จริง — ลบได้ทุกสถานะ ไม่ล็อกตอน active
- **07 → ลบกฎเกณฑ์ย่อย (เพิ่มเมื่อ 2026-09-06)**: การ์ดกฎเกณฑ์แต่ละใบมีปุ่ม "ลบ" คู่กับปุ่มอนุมัติ/ไม่อนุมัติ (หรือคู่กับปุ่ม "แก้ไข" ถ้าตัดสินใจแล้ว) กด `confirm()` ถามยืนยันก่อนทุกครั้ง (ยกเลิกแล้วไม่ลบ) ยืนยันแล้วลบ `rules/{id}` จริงพร้อม `reviewLog` ทั้งหมดใต้ข้อนั้น — **ล็อก (ซ่อนปุ่ม) เหมือนปุ่ม "แก้ไข" ตอนชุดเกณฑ์เป็น `active`** ต้องกด "แก้ไขชุดเกณฑ์นี้อีกครั้ง" ก่อนถึงจะลบข้อย่อยได้ ถ้าลบจนกฎเกณฑ์ในชุดเหลือ 0 ข้อ ระบบจะไม่ถือว่า "ตรวจครบแล้ว" (กันปุ่มเปิดใช้งานชุดเกณฑ์ว่างเปล่าโผล่ผิดๆ)

## Firestore Security Rules (เพิ่มเมื่อ 2026-09-08)

เพิ่มไฟล์ [firestore.rules](./firestore.rules) บังคับสิทธิ์จริงที่ระดับฐานข้อมูล (ไม่ใช่แค่ผ่าน UI อีกต่อไป) ตรงตาม [ACL.md](./ACL.md) ทุกจุด — ต้อง copy เนื้อหาไปวางเองที่ Firebase Console (โฟลเดอร์นี้ไม่มี Firebase CLI ตั้งค่าไว้)

- **ผู้ไม่ login**: ทำอะไรกับทุก collection ไม่ได้เลย
- **users**: อ่านได้เฉพาะของตัวเอง หรือ ADMIN อ่านของใครก็ได้; สมัครสมาชิกใหม่ (`create`) บังคับ role เป็น `STAFF` เสมอ (กันคนแก้ payload เองแล้วตั้ง role เป็น ADMIN ตอนสมัคร); แก้ role คนอื่นได้เฉพาะ ADMIN และห้ามแก้ของตัวเอง (ซ้อนกับที่ UI บังคับไว้อยู่แล้ว เป็นชั้นป้องกันที่สอง)
- **criteriaSets**: ADMIN อ่าน/เขียน/ลบได้ทุกสถานะ; STAFF อ่านได้เฉพาะ `status == "active"` เท่านั้น (บังคับผ่าน query filter ที่ dashboard.js ใช้อยู่แล้วพอดี), สร้างได้เฉพาะ ADMIN และต้องระบุ `uploadedBy` เป็น uid ตัวเอง
- **rules**: อ่าน/เขียน/ลบ ADMIN ล้วน; STAFF อ่านได้เฉพาะกฎเกณฑ์ที่ชุดแม่ (`criteriaSets`) เป็น `active` แล้ว (เช็คด้วย `get()` ข้ามไปที่ document แม่ตอน evaluate rule)
- **rules/{id}/reviewLog**: ADMIN ล้วนทั้งอ่าน/เขียน, บังคับ `adminId` ต้องตรงกับผู้ login จริงตอนสร้างแถวใหม่
- **จุดที่ตั้งใจ "ไม่" ล็อก** (ต่างจาก UI ที่ล็อกไว้): การแก้ไข/ลบกฎเกณฑ์ย่อยตอนชุดเกณฑ์เป็น `active` (ปุ่ม "แก้ไข"/"ลบ" ที่หน้า 07 ล็อกไว้ด้วย UI) ไม่ได้ถูกบังคับซ้ำในระดับ rules เพราะ dashboard.js ต้องลบ `rules` แบบ cascade ได้ทุกสถานะตอนลบทั้งชุดเกณฑ์ทิ้ง — ถ้าบังคับล็อกในนี้ด้วยจะทำให้ cascade delete ของชุดที่ `active` พังไปด้วย จึงปล่อยให้พฤติกรรมนี้เป็น business rule ระดับ UI เท่านั้น (ไม่ใช่ช่องโหว่ความปลอดภัย เพราะยังจำกัดแค่ ADMIN ทำได้อยู่ดี)
- **ผลกระทบต่อ seed.html**: `js/seed.js` เขียนข้อมูลตรงๆ โดยไม่ login และกำหนด document id เอง (ไม่ใช่ auth.uid ของผู้เขียน) — เมื่อ publish กฎชุดนี้แล้ว `seed.html` จะใช้ไม่ได้อีกต่อไป (permission denied ทุกแถว) ถ้าต้อง seed ข้อมูลใหม่ ให้สลับกลับไปตั้ง Firestore เป็น test rules ชั่วคราว ทำเสร็จแล้วค่อย publish ไฟล์นี้กลับ (error message ใน `seed.js` เตือนเรื่องนี้ไว้อยู่แล้วตั้งแต่แรก)

## ระบบจัดการบทบาท (เพิ่มเมื่อ 2026-09-07)

ดูตารางสิทธิ์แบบเต็มใน [ACL.md](./ACL.md) — สรุปการเปลี่ยนแปลงหลัก:

- **role เปลี่ยนจากข้อความไทยเป็นโค้ดภาษาอังกฤษ**: `role` field ใน `users/{uid}` เปลี่ยนจาก `"แอดมิน"`/`"ผู้จัดทำหลักสูตร"` เป็น **`"ADMIN"`**/**`"STAFF"`** (สั้นกว่า ผู้ใช้เลือกเอง) — บัญชีที่สมัครไว้ก่อนหน้านี้ด้วยค่า role แบบเก่าต้องแก้ field `role` ให้ตรงกับค่าใหม่เอง (ผ่าน Firebase Console หรือหน้า `manage-users.html` ถ้ามี ADMIN คนอื่นแก้ให้ได้)
- **เอา dropdown เลือกบทบาทออกจากหน้าสมัครสมาชิก**: บัญชีใหม่ทุกบัญชีจาก `signup.html` ได้ role `STAFF` เสมอ — ผู้ใช้ระบบ (อาจารย์ผู้สอน) ตั้งใจให้ตั้งค่า ADMIN คนแรกของระบบด้วยมือเองผ่าน Firebase Console โดยตรง (ไม่ได้ทำ auto-bootstrap ในโค้ด)
- **หน้าใหม่ `manage-users.html`** (+ `js/manage-users.js`): ADMIN ล้วน (role อื่นเข้าไม่ได้) แสดงตาราง `users` ทั้งหมด พร้อม dropdown เปลี่ยน role รายคน เขียนกลับ Firestore ทันที — **แถวของบัญชีตัวเองแก้ไม่ได้** (บังคับด้วย UI: dropdown ถูกแทนที่ด้วยข้อความอ่านอย่างเดียวถ้า uid ตรงกับผู้ login อยู่)
- **หน้า 05/07 เปิดให้ role `STAFF` เข้าดูได้แบบอ่านอย่างเดียว** (เดิมเป็น ADMIN ล้วน 100%): STAFF เห็นเฉพาะชุดเกณฑ์สถานะ `active` ในหน้า 05 (ไม่เห็น `pending`), คลิกเข้าไปหน้า 07 จะไม่เห็นปุ่มอนุมัติ/ไม่อนุมัติ/ลบ/เปิดใช้งาน/แก้ไขใดๆ เลย เห็นแค่ badge สถานะของแต่ละกฎเกณฑ์เท่านั้น — ถ้าพยายามเปิด URL หน้า 07 ของชุดที่ยัง `pending` ตรงๆ (แก้ hash เอง) จะเจอข้อความปฏิเสธแทนเนื้อหา
- **หน้า 06 ยังเป็น ADMIN ล้วน 100%** เหมือนเดิม (สร้างชุดเกณฑ์ใหม่ถือเป็นสิทธิ์จัดการ ไม่ใช่แค่อ่าน)
- **ยังไม่ implement**: ฟีเจอร์ "นำหลักสูตรเข้าเพื่อตรวจสอบ" และ "เลือกใช้ชุดเกณฑ์" สำหรับ STAFF (เป็นคนละฟีเจอร์กับที่การบ้าน v2 นี้ทำอยู่ — ดูหมายเหตุใน ACL.md)

## ชุดเกณฑ์จากเอกสารจริง (เพิ่มเมื่อ 2026-09-06)

นอกจาก `cs001`/`cs002` (ข้อมูลสมมติเดิม) เพิ่มชุดเกณฑ์ที่สกัดจากเอกสารราชการจริง 3 ชุด — **ข้อความ (`ruleText`) สกัดด้วยมือจากตัวเอกสาร แทนขั้นตอน "AI สกัดกฎเกณฑ์" ที่ยังไม่ได้ทำจริงในเวอร์ชันนี้** (ดูหัวข้อขอบเขตที่ยังไม่ทำด้านบน) ทั้งหมดตั้งสถานะเป็น `pending` โดยตั้งใจ เพื่อให้ทดลอง flow ตรวจสอบ/อนุมัติ (หน้า 07) กับเนื้อหาจริงแทนประโยคสมมติ:

| criteriaSetId | ชื่อชุดเกณฑ์ | จำนวน rules | ที่มา |
| --- | --- | --- | --- |
| `cs003` | เกณฑ์มาตรฐานหลักสูตรระดับปริญญาตรี พ.ศ. 2565 | 15 (r006-r020) | ประกาศคณะกรรมการมาตรฐานการอุดมศึกษา เรื่อง เกณฑ์มาตรฐานหลักสูตรระดับปริญญาตรี พ.ศ. 2565 — ราชกิจจานุเบกษา เล่ม 139 ตอนพิเศษ 212 ง, 9 กันยายน 2565 |
| `cs004` | เกณฑ์มาตรฐานหลักสูตรระดับปริญญาโท พ.ศ. 2565 | 12 (r021-r032) | ประกาศคณะกรรมการมาตรฐานการอุดมศึกษา เรื่อง เกณฑ์มาตรฐานหลักสูตรระดับบัณฑิตศึกษา พ.ศ. 2565 (เฉพาะส่วนปริญญาโท) — ฉบับเดียวกัน |

หมายเหตุการตัดสินใจ:

- เอกสารต้นฉบับ "เกณฑ์มาตรฐานหลักสูตรระดับบัณฑิตศึกษา" ครอบคลุม 4 ระดับ (ป.บัณฑิต/ป.บัณฑิตชั้นสูง/ปริญญาโท/ปริญญาเอก) ในฉบับเดียว แต่ schema `criteriaSets` มีฟิลด์ `degreeLevel` เดียวต่อชุด — จึงแยกเป็นคนละ criteriaSet ตามระดับแทนการยัดรวม โดยเลือกทำเฉพาะปริญญาโทและปริญญาเอก (2 ระดับหลักที่ใช้บ่อย) ไม่ได้แยกชุด ป.บัณฑิต/ป.บัณฑิตชั้นสูงเพิ่มเติม เพราะมีเนื้อหาน้อยและซ้ำแพทเทิร์นกับปริญญาโทมาก
- แต่ละชุดคัดสรร ~12-15 ข้อที่หลากหลาย (หน่วยกิตรวม/สัดส่วนหมวดวิชา/คุณวุฒิอาจารย์/เกณฑ์จบการศึกษา) แทนการดึงครบทุกอนุข้อของเอกสารจริง (ซึ่งมีรายละเอียดคุณวุฒิอาจารย์ผู้สอบ/ที่ปรึกษาวิทยานิพนธ์ซ้ำแพทเทิร์นกันมาก) เพราะจุดประสงค์ของการบ้านนี้คือสาธิต flow การอนุมัติ ไม่ใช่ทำ mapping กฎหมายให้ครบถ้วน
